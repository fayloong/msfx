# ADR 0004: 数量对账恢复"数量对比"（shl 字段发现推翻 ADR 0002 量纲结论）

- 状态：已接受（2026-08-17）
- 关联代码：`scripts/check_quantity.php`、`src/ApiClient.php`（`sumBillDetailCount`）、`src/TaskFetcher.php`（`fetchBillQuantities`）
- 推翻：ADR 0002 的"两数量纲无法统一"结论（决策 4"移除 sumBillDetailCount"被逆转，恢复该解析方法）
- 对应 spec：`.scratch/quantity-check/spec.md`

## 背景

ADR 0002 判定"数量对账退化为是否上传检查"的根因是：平台申报的 `min_pkg_count` 是最小包装数（中包装码/件码按件内盒数展开申报），本地只有追溯码数，**两数量纲无法统一**，含中包装码的单据必然误报（62 条量纲假阳性）。

## 新发现（2026-08-17 grilling 会话实测）

用户提出用 `select SUM(lingsshl) from v_pf_phlrmx` 对比平台 `min_pkg_count` 求和，实测发现 SQL Server 明细视图的 **`shl`（数量）字段就是"已展开到最小包装单位"的数量**：

- 整件行：`shl = baozhshl(包装数) × jlgg(件规格)`——件码按件内盒数展开的映射一直在 SQL Server 里，只是当初查的是 `wms_dzjg`（追溯码表）而非明细视图
- 零散行：`shl = lingsshl(零散数量)`
- 入库侧 `shl` 与 `rkshl`（实收）近 7 天零差异样本，无歧义

4 样本实测（本地 `SUM(shl)` == 平台 `min_pkg_count` 求和，全等）：

| 场景 | 单号 | 本地 SUM(shl) | 平台 min_pkg_count 求和 |
|------|------|--------------|------------------------|
| 零散出库 | XSOWMS00998311 | 50 | 50 |
| 件码出库（1 个中包装码） | XSOWMS00997350 | 5 | 5 |
| 整件入库（2 件 × 件规格 300） | JHGWMS00062697 | 600 | 600 |
| 真实拆分出库（5973 码展开） | JHOWMS00012659 | 7168 | 3500 + 3668 |

量纲问题可解：比较口径统一为**最小包装单位数**，数量对账恢复对比。

## 决策

1. **数量对账恢复"数量对比"**：**查询范围仅针对 check_bill_status 已确认"上传成功"的单据**（upload_logs `source='batch_check' AND response_status='上传成功'` 按 rq 筛选——未上传的由 check_bill_status 以任务状态承担，数量对账不重复查询）。本地应有数量 = `SUM(shl)`（出库 `v_pf_phlrmx` 按 `djbh`、入库 `v_sjdmx_mx` 按 `ysdjbh`，基线单号 `IN` 列表聚合而非 `rq` 过滤——`rq` 字符串比较在明细视图不可靠）；平台实际数量 = 跨拆分子单累加 `min_pkg_count`。判定：`actual ≠ expected` → `数量不符`（响应含 `{djbh, rq, expected, actual, sub_bills}`）；相等 → 传齐零记录；全序列查不到 → `信息不存在`（防御分支）。**基线剔除本地非药品行**（spkfk.jixing 含商品/食品/消杀/用品/器械/化妆品/消毒剂/敷料/试剂/材料/设备等）——平台是药品追溯平台，外部系统不申报非药品（08-15 实测 35 条"数量不符"中 16 条纯属此类，剔除后归零）。**幂等升级为整日清理**（每轮先删目标日期全部 quantity_check 记录，旧全量基线时代残留自动清除）。
2. **查询策略"相等即停，不等查尽"**：原始单号查到且相等即停（未拆分大头单 1 次调用）；原始单号查不到或数量不等继续查 `_1.._9` 直到查不到（上限 10 次），跨子单累加——防止外部系统"原单号+拆分并存"场景漏计。
3. **恢复 `ApiClient::sumBillDetailCount()`**：累加 `min_pkg_count`（单药品关联数组/多药品列表两种结构），返回 `null` = 无法核对（无明细结构、任一行缺 `min_pkg_count`——缺字段不按 0 处理），与 `isBillFound` 同置静态方法层。
4. **无法核对跳过**（不写任何记录）：本地 `SUM(shl)` 为 NULL（明细无行）、平台响应解析失败——异常数据/结构不产生假告警。
5. **保留 ADR 0002 其余结论**：幂等"先删后写"（历史误报随重跑自动清除）、API 间隔 1s、平台限流本轮熔断、运行窗口避开 check_bill_status（cron 21:10 每天一次）、基线用轻量查询不写库。

## 后果

- 正向：恢复"整单没传齐"的检测能力（实测检出 JHOWMS00012655 疑似申报差异：本地 16799 vs 平台 16798 差 1，待人工确认）；外部系统拆分上传场景（原始单号查不到但子单传齐）不再误判"未上传"。
- **已知精度边界（实测发现，08-15 验证；2026-08-18 用户确认收尾）**：剔除本地非药品行后，"数量不符"剩余差异全部可归因于**本地零售规格 ≠ 平台生产规格**的药品——**企业内部最小销售单位与平台最小销售单位不一致**（企业按盒卖、平台按支作为最小单位，**尤其是注射剂**，大概率求和对不上；如氨咖黄敏胶囊 本地 10粒/盒 → 50 盒 vs 平台 500粒/盒 → 1、注射用青霉素钠 20 瓶 vs 平台 1 盒 20瓶/盒、脑得生片 本地 30 大盒 vs 平台 90 小盒）。本地 `shl` 按本地最小包装（零售规格）计数、平台 `min_pkg_count` 按平台注册规格（生产包装）申报——同数量不同包装数。机制本身已验证精确（实测单 19 行中 18 行逐行相等，仅规格差异行不符）。"数量不符"当前语义是"疑似差异"告警，运维以 response 中的 expected/actual/sub_bills 人工复核。**本阶段无更优解**：精确对账需要药品级"本地销售规格 → 平台注册规格"映射（依赖平台药品规格查询与映射表维护），列入 backlog。
- 代价：每天全量查询次数增加（相等即停策略下绝大多数单 1 次调用，预估 ~800 次 × 1s ≈ 13 分钟，21:10 开跑 ~21:25 结束）。
- 注意事项：件码展开映射（`baozhshl × jlgg`）与非药品剔除（spkfk.jixing）依赖 SQL Server 明细视图/基础资料口径，若上游数据口径变更需重新验证 4 样本与 08-15 基线。
