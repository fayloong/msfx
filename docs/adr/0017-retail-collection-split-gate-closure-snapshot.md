# 零售采集由「过滤」改「分流」：外部已上传可见、计数门卫、状态闭环、全量快照

- 状态：已接受（2026-10-02）
- 推翻：[ADR 0007](0007-retail-no-platform-reconciliation.md) 修订注一那条测试阶段临时口径（`NOT EXISTS` 整批过滤）——见该 ADR 修订注三
- 相关：[ADR 0011](0011-retail-retransmit-metadata-and-manual-trigger.md) 补注（零售批量上传脚本：能力已备、暂不启用）、[ADR 0013](0013-retail-two-year-retention.md)（2 年下限，本文未改）、[ADR 0016](0016-retail-upload-state-writeback.md)（回写，读侧口径随之扩展）

本文记一次口径反转**作为一个整体**的四个决定：采集**分流**（票 02）、**计数门卫**（票 04）、**状态闭环**（票 03）、**全量快照**（票 05）。它们分散在四张票里实现，但回答的是同一个问题——门店单据由外部系统上传，本项目要「**可见** + 人工补传」，那么在既看不见、又猜不出「今天到底有没有新单」的情况下，怎么让这套机制自洽。设计与实测见 `.scratch/retail-collection-split/spec.md`。

## Context

2026-09-30 的测试阶段把 `NOT EXISTS(dyt.bs_msfx.dbo.update_state)` 加回采集 SQL，**外部系统已上传的单整批挡在采集之外**（ADR 0007 修订注一）。当时接受两条代价，其中一条在**日常使用**里很快变成硬伤：已上传的单在页面上不可见——「这张单到底传没传、是谁传的」只能回源库查。ADR 0007 自己早就把这类过滤判为不可取（"核对恰恰需要看见它们"），测试阶段那句"回收或重新评估"就是留给出账的。

除了可见性，还有三处缺口：

- **每一轮采集都全量重扫源库**，源库什么都没变时照跑；日志里也看不出「真的没新单」与「脚本压根没跑」的区别。
- **一张单先以「等待上传」落进本地、之后外部系统把它传成了，本地不会有任何反应**——任务永远挂在补传队列里，人去点补传会白调一次平台（申报不可逆）。采集只在写入新行时看判据，**不回头改已有行**。
- 将来系统要接管门店上传时，只有页面上的逐条补传 / 批量重传，**没有一个能挂进 cron 的批量入口**（这一条的落点是票 06 的 `scripts/upload_pending_retail.php`——**能力已备、暂不启用**，决策与代价记在 [ADR 0011](0011-retail-retransmit-metadata-and-manual-trigger.md) 的补注，不在本文的四个决定之内）。

## Decision

### 1. 采集由「过滤」改为「分流」（票 02）

单据**全采进来**，按同一张源库状态表一分为二：**已上传的**写成一条「外部上传」记录进已上传记录页（`source='retail_external'`、`response_status='上传成功'`、`task_id=0`、`request_status` 留 NULL——本项目没发起请求，写「请求成功」是失真；`response` 写一段出处 JSON），**不建任务**；**未上传的**照旧建「等待上传」任务由人补传。

- **判据只有一处**：源库 `dyt.bs_msfx.dbo.update_state` 里有该单号（`bill_state` 实测全为 `'1'`，判存在即判已上传）。表名常量只此一处：`App\RetailExternalUploads::TABLE`（采集、回写、门卫共用）。
- 采集 SQL 里多取一个 **`EXISTS` 标志列**。**必须 EXISTS 不能 JOIN**——该表无主键无唯一约束，实测 67,856 行里 **82 个单号是多行**，JOIN 会把结果集放大。
- 判定收在 `App\RetailExternalUploads::decide()`（已上传→记录 / 未上传→任务 / 本地已有痕迹→跳过）。**两条分支的幂等判据不同**：已上传的单只看"有没有成功记录"（已有任务行**不拦**它——那条是本地待办痕迹，由状态闭环翻正），未上传的单是"任务行**或**成功记录任一存在"就跳过。合成一个集合会让已上传分支误跳过、记录写不出来。
- 不变量：**同一 `(company, djbh)` 最多一条成功记录**。
- 已知限制**保留**：状态表**无企业列**，跨门店同名单号在这张表里自身就会串。这条代价 ADR 0007 已记，本次不消除——它影响的是"判得准不准"，不再是"看不看得见"。

### 2. 计数门卫（票 04，`App\RetailCollectionGate`）

**闭环之后、采集之前**先数三个数——**当日单据总数 / 已上传 / 未上传**（范围与 cron 采集一致：当日 + 四种门店单据类型 + 2 年下限——下限由脚本开头算的那一份传进来，两处同一个值；第三个是前两个的派生值，一并存下来只为人工对账）——与基线比对：**三个数都没变就跳过整轮采集**，并打印原因。基线 `data/fetch_bill_counter_retail.json`（**与批发的 `fetch_bill_counter.json` 各一个**：两个脚本共写一个文件会互相踩，一边写 `{date,count}`、另一边写 `{date,total,uploaded,unuploaded}`，彼此的判定都被对方喂成"格式非法 → 视为无基线"）。

六处刻意：

- **基线只在整轮采集成功之后写**（`guard()` 把采集收成闭包，"抛异常即不写基线"因此是构造上的性质）。否则"落库跑到一半失败"会被记成"没变化"，从此永久跳过。
- **计数查询失败 = 无基线、照常采集**，不是跳过——门卫跳过的是一整轮采集，方向必须朝"宁可多跑一轮"（**与批发那边刻意相反**：批发计数失败即跳过本次；零售没有第二道兜底，漏采就是整天单据在页面上不存在）。
- **顺序红线：必须插在状态闭环之后**——门卫跳的是整轮采集，而闭环不在它的覆盖范围里（见下条）。
- `--all` 绕过（快照的计数口径是两年窗口，不是当日）。`--dry-run` **压根不调 `guard()`**：门卫的产物是基线，预演写了它，下一轮 cron 就会判"三个数没变"而少采一轮。
- **两张表都要去重成派生表**再 `count()`：`zsm_ls` **自己**就有完全重复行（321 平均 2.08 行/单、最多 120 行、14 列值全同），不去重数出来的是**行数**——首跑实测 111 行 vs 采集的 55 张单。去重后与采集脚本那句"拉取到 N 张单据"逐字相等。
- 计数 SQL 的形状受限：**SQL Server 不允许在聚合里套子查询**（`sum(case when exists(...) then 1 else 0 end)` 直接报错），故换成"状态表去重成派生表 + LEFT JOIN + `count()`"。**非聚合**的 `case when exists(...)` 才允许，采集 SQL 因此不受这条限制。

### 3. 状态闭环（票 03，并入 `App\RetailExternalUploads`）

**每轮采集开跑前**，拿**本地待办清单**（还挂着「等待上传」的门店任务 ＋ 零售企业的补传失败记录）按单号 IN 分块去状态表核对，外部系统**后来**才传成的痕迹就地翻正：

- **任务行** → 翻 `已处理` + `上传成功`（`request_status` 刻意不动——本项目从没为这张单发起过请求），**保留痕迹、不删行**。
- **失败记录** → **不改写历史**，改为**追加**一条「外部上传」记录（失败页那条随后被既有的同单号判重自动隐藏）。
- **本地已有成功记录时只翻任务行**，不追加。

四处刻意：① **按清单查、不按日期扫源库**——待办是**跨日**的（昨天的单今天才被传成一样要能翻），挂在"当次采集结果"上就永远漏掉；② **不受计数门卫约束**（它不扫源库大表，清单通常几十到几百条）；③ **源库查不通时一条都不翻**（"不知道"不等于"没上传"），只记一条 JSONL 警告；④ **调用点在采集之前**——采集失败/空批次都不该让它漏跑一轮，而它追加的成功记录会让同轮采集的 `decide()` 判 SKIP（两条路径对"已上传"给同一个结论）。

**红线**：定位一律用 `(company, djbh)`，绝不用裸 `djbh`（生产库里裸单号并不唯一，乙店的成功记录会把甲店的待办整条吞掉）。批发行一个字段不动。

### 4. 全量快照 `--all` 与预演 `--dry-run`（票 05）

`--all` = 最近 2 年（ADR 0013 的下限始终在）的一次性快照入口，**按分流规则落库，但未上传的历史单一律不建任务**——一次跑出几万条「等待上传」人工处理不现实，还会把待补传这份工作清单的信号淹没；工作队列由日常采集按日累积。判定是 `decide(..., buildTasks: false)` 落到 `ACTION_COUNT_ONLY`，**日常口径一字不改**（只有快照传这个参数）。

代价是窗口内未上传的历史单在本系统里**不可见**，所以跑完必须把那个数打印出来，让欠账是**可查的数**：脚本末句"窗口内未上传 N 单（其中 M 单本地已有痕迹，不重复写），其余 K 单未建任务"——**K 才是欠账**（未上传且本地无痕迹）。

`--dry-run` 预演只读源库、只统计并打印「将写入 N 单 / M 码」，**不落任何库、不发任何平台调用**，且**不经过门卫、不跑状态闭环**（两者的产物都是写库）。快照与日常**共用同一条流式代码**（`SqlSrvHelper::queryEach` 逐行消费 + `order by ls.bill_code` 让同单号连续 + 每 500 张落一批一次事务），内存与窗口规模无关。

## 排除的方案

- **让 `update_state` 当采集门卫（即测试阶段的过滤）**：ADR 0007 初判已排除——它会把已上传的单全部隐藏，而核对恰恰需要看见它们。测试阶段临时加回后，代价在日常使用里兑现（运维只能回源库查"这张单传没传"），本次改回"全采进来再分流"。
- **采集时顺手翻正已有行**（把已上传 + 有任务行的那格直接判 UPDATE）：采集只该按判据写**新行**，回头改历史是闭环的职责——两者混在一起后，"这条任务为什么被翻"就再也说不清了。
- **闭环按日期扫源库**（挂在本轮采集结果上）：跨日的单永远漏掉——本地待办是跨日的，源库的查询窗口不是。
- **失败记录改写成成功记录**（而不是追加一条）：那会造出"来源失真"的历史——那条记录是人工补传失败的真实证据，抹掉它等于篡改事故记录。追加 + 既有判重隐藏，两个事实都留得住。
- **快照把未上传的历史单也建成任务**：几万条「等待上传」会把真正要处理的欠账淹没；且那些单多半已无从处置（超期的已被 2 年下限挡掉，剩下的也未必有人力逐条点）。
- **给零售批量上传脚本加"数量未变就跳过"那类门卫**：上传不可逆，跳过判据写错就是"该传的没传"，而它省下的只是几次查询（见 spec §6）。

## Consequences

**三条已知代价（运维要记住的）**

1. **「外部上传」记录只有三个月的窗口**：`cleanup_logs.php` 按 `created_at` 清 3 个月前的 `upload_logs`，一视同仁——快照写进去的那批记录、日常分流写进去的记录都在内。三个月后要回看"某张单是谁传的"，只剩源库状态表与 JSONL。
2. **门卫省不掉源库扫描**：门卫计数实测 **47–59ms**（冷启动 761ms），而当日采集查询是 **80–153ms**——**同一量级**。门卫省的是本地那段（去重、认领、写库），**不是**性能优化：它的价值是**日志里能区分「今天真没新单」与「脚本压根没跑」**。别拿"省扫描"当它的理由。
3. **快照是一次性视图、会自然过期，需要时重建**：三个月后那批记录被清理，而窗口内未上传的历史单压根没进本系统（`ACTION_COUNT_ONLY`）。重建 = 再跑一次 `--all`（幂等，重跑全部跳过）。日常采集按日累积的是"从今天起"的工作队列，不会自动补上历史。

**其余后果**

- **「外部上传」的来源名说的是"分流结果"，不保证是外部系统传的**：本项目人工补传成功后也往同一张表回写（ADR 0016），所以这条记录只表示"采集时状态表里已有该单号"。要分清得看那批单的历史（本项目补传的会另有一条 `retail_retry` / `manual` 日志）。见 ADR 0016 的读侧补句与 CONTEXT.md 的同处说明。
- **测试阶段的欠账了结**：ADR 0007 修订注一那句"测试结束后要么回收、要么按新证据重新评估"到此结案（回收已不可能——那正是被推翻的口径；这里是按新证据重新评估的结果）。
- **快照只写过一次，别挂 cron**：`--all` 跑一次即可；日常 cron 走的是不带参数的当日采集。
- **新脚本一旦启用即反转 ADR 0011 的人工触发决策**——这条代价记在 [ADR 0011](0011-retail-retransmit-metadata-and-manual-trigger.md) 的补注里（含"能力已备"与"暂不启用"两个事实），本文不重复登记。
- **批发链路、补传的三关 fail-closed、三个检查脚本的取数口径（只查批发主体）一个字未变**：本次只动门店采集的落库分流与新增能力；上传装配、平台调用策略（间隔、重试）全在范围外。
