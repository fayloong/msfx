# 门店与凭据 1:1：配置层拒绝多套，补传不再由人指定凭据

- 状态：已接受（2026-09-30）

**推翻 [ADR 0006](0006-credential-as-routing-subject.md) 的"门店与凭据 1:N"**（以及 [ADR 0008](0008-retail-claim-by-platform-id.md) 随之引入的 `primary`/备用凭据语义）。

用户 2026-09-30 明确：**每个门店在本项目中会有专门的一套凭据，不会使用第二个**。此前"一门店可能有多套 AppKey、备用授权在主授权被平台限流时顶替"的设想（ADR 0006 的第 3 轮澄清）不再成立——于是"由人在页面上显式选凭据"从一道安全闸变成了一个纯粹的误操作入口：下拉里永远只有一个答案，但**选错的可能性并没有消失**（尤其是将来某天真的配了第二套时，选中哪一套就是"用哪个主体申报"）。

## Context

- ADR 0006 立论时，凭据套数是未知量（"每个门店的 appkey、SECRETKEY 都不相同，每个门店也可能存在多套"），故把选择权留给**配置 + 人**：结构里声明多套、`primary` 标默认、页面下拉选实际用的那套。
- 工单 06 / 07 落地后，页面上的这一步是真实存在的操作（单条补传弹窗、手动上传页门店分支各一个下拉）。而部署配置里 16 家企业**每家恰好一套**（凭据位键都是 `main`），于是这道选择在实践中的形态是"每店一个只有一项的下拉"，两处 PHP 头部为渲染它各维护一份"凭据位键 + label + 是否配齐"的出后端口径。
- 补传是**不可逆的平台申报**，"用哪套凭据"就是"以哪个主体申报"。当一个选择没有第二个选项时，它不提供任何保护，只提供出错的机会。

## Decision

1. **门店与凭据 1:1**：`App\Enterprise::validate()` 在企业声明超过一套凭据时**拒绝载入**（配置错误，不是警告）。`primary` 字段仍在结构里解析，但单套时代不参与任何决策。
2. **补传用哪套凭据不由调用方给**：`App\RetailRetransmit::retransmit()` 不再接收凭据键，内部走新增的 `Enterprise::credentialFor($company)`（该企业那套，含 `key`）；两个端点（`tasks_retry_retail` / `tasks_batch_retry_retail`）入参随之去掉 `credential`。**少一个可传错的参数，就少一条把单据报到错误主体的路径**——这与"守卫放在服务端而不是调用方"是同一条理由。
3. **页面不再渲染凭据下拉**，只保留"这家能不能补传"一个事实：`Enterprise::retailCredentialReady()` 返回 `门店名 => 凭据是否已配齐`，两个视图共用（此前各自拼一份凭据清单）。不可补传的两种原因照旧分开显示——`未识别`（真异常）与`待配凭据`（预期内状态）。

## Consequences

- **`upload_tasks.credential` 列保留**（审计值）：采集时预填该门店那套的键，补传写回同一套。它仍不参与去重键（`(company, djbh)`，见 ADR 0006/0008），只是"这次实际用了哪套"的事实记录。
- **"多套凭据的自动分发规则"不再需要讨论**：ADR 0006 里"本轮不实现自动分发规则，等有真实数据再补"的欠账随本决定一并消失——不存在第二套，也就没有分发。
- **限流顶替的退路没有了**：主授权被平台限流时没有备用凭据可切。限流仍按 AppKey 计，若真出现限流，处置方式是错峰或换凭据**位**（改配置里那唯一一套的值），不是页面上切一套。
- **回头的成本已知**：若将来真有门店要第二套（例如平台要求不同主体分账申报），需要同时改三处——`validate()` 放开多套、`Enterprise::credentialFor()` 改为需要显式选择、页面把下拉加回来（`retailCredentialReady()` 的摘要不够用，得重新出凭据位键与 label）。本决定把这笔账记在这里，而不是让它变成一个隐性假设。
- **`未识别` 与 `待配凭据` 的语义不变**：前者是认领失败（真异常），后者是授权未到手（预期内），页面照旧分别提示并禁用补传。
