# 任务状态词表统一：门店采集单也用「等待上传」

- 状态：已接受（2026-10-01）

> **本 ADR 撤销 [ADR 0007](0007-retail-no-platform-reconciliation.md) 第 22 行"零售任务状态用新值 `待补传`，不复用 `等待上传`"一条**，理由是该条自己写明的解除条件已经兑现（见下）。ADR 0007 的其余结论（零售不做平台对账、只采集 + 人工补传）全部不变。

## Context

**`待补传` 的由来**：ADR 0007（2026-09-29）当年写下这条，是因为 `upload_pending.php` 当时**按 `task_status='等待上传'` 取全部任务且无企业过滤**，凭据写死河药——门店单若以 `等待上传` 落库，那个 cron 会用河药 AppKey 走 kyt 接口把门店单据申报到河药主体名下。文章里同时写了解除条件：

> `upload_pending.php` 取数口径必须同步加企业过滤

**该条件已兑现**，且此后又加了一道纵深防御：

| 闸 | 位置 | 现状（2026-10-01） |
|---|---|---|
| 取数白名单 | `scripts/upload_pending.php:42` | `WHERE task_status = '等待上传' AND company = ?`（`Enterprise::wholesaleSubject()`）——**白名单，不是排除法** |
| 状态查询白名单 | `scripts/check_bill_status.php:64` | 同款 `AND company = ?` |
| fail-closed 守卫 | `src/UploadService.php`（`resolveContext`） | 企业 / 接口族 / 凭据三关，非批发 kyt 整批拒传，不发一次调用；写在 Service 层是为了护住"直接 `new UploadService()`"的调用方 |

门店单的 `company` 是门店名，**在取数那一步就进不了白名单**；ADR 0007 当年担心的路径已经断了。守卫只是第二道。

**`待补传` 的代价则一直在付**：门店单在操作者最常用的页面（上传任务页）**默认不可见**。该页任务状态默认 `等待上传`、单据日期默认最近 7 天，而"所属企业下拉不算关键词"（不丢弃默认日期）——两条默认叠加，选门店就是恒 0 条。2026-10-01 生产库实测：

| 门店 | 默认口径 | 切「待补传」 | 待补传 + 近 7 天 |
|---|---|---|---|
| 新江分店 | 0 | 597 | 99 |
| 白田分店 | 0 | 1 | 0 |

数据一条没少（`source='retail'` 6,137 行），是状态值把它挡在默认视图外——用户因此直接问"为什么选择门店都没有数据"。

## Decision

1. **状态词表统一为两个值**：`等待上传`（未处理）/ `已处理`（终态）。门店采集单与批发一样落 `等待上传`，`待补传` 退出词表。
2. **采集落库值改在 `fetch_bills_retail.php`**，并加一条幂等迁移（`scripts/init_db.php`）把历史行一并统一。不迁移的话，本 ADR 要解决的可见性问题对 6,135 行存量原样存在。
3. **页面按值改**：上传任务页删掉 `待补传` 选项与徽标（门店单此后与批发行同色，区分靠"所属企业"列与来源列）；手动上传页门店分支的默认选中项改为 `等待上传`，行内按钮判定 `task_status === '等待上传' ? '补传' : '重传'`。
4. **分工一字不动**：门店单仍只人工补传（`source='retail'` 判定）、cron 仍只取批发主体、补传失败仍翻 `已处理`（ADR 0011）。本 ADR 只改**状态值**，不改任何取数口径。

## 排除的方案

- **保留 `待补传`，改前端**（选门店时自动把状态切到 `待补传` 并丢掉默认日期）：要动的是"用户没改过的默认值"，属于无声改变筛选行为；且两个状态值让每个新页面、每次新筛选都要再回答一遍"门店单算哪种"。统一值把这个问题从词表里删掉。
- **只在页面上把 `待补传` 显示成 `等待上传`**（显示层别名）：库里两个值、界面一个值，下一个写 SQL 的人仍要面对"为什么有两套"。别名不是统一。
- **顺手把仪表盘"等待上传"卡片限定为批发主体**：本 ADR 明确不做（见 Consequences 第 2 条），那是筛选口径统一的另一件事。

## Consequences

- **`等待上传` 对门店单不再是字面承诺**：cron 不会取走它们，要人点"补传"。**安全保障因此完全落在取数白名单上**——`upload_pending.php` 的 `AND company = ?` 一旦被删或被改成排除法，门店单就会被河药主体误传（不可逆）。这是本 ADR 之后最该守住的一条：`CONTEXT.md` 的词条里已写明，取数白名单的注释里也写明。纵深还有 `UploadService::resolveContext`，但那是第二道，不是第一道。
- **仪表盘"等待上传"卡片会计入门店待补传**（`src/views/dashboard.php:23` 无企业过滤，迁移当天由 ≈29 跳到 6 千余，此后随采集增长）。已知后果，**本 ADR 不改**——CLAUDE.md 早已记明该页是筛选口径的第 5 份拷贝、另行统一；本 ADR 只登记这个跳变，避免下一个人把它当成 bug 从头查。
- **`待补传` 成为历史值**：迁移后库里不应再有。迁移写成幂等（`UPDATE ... WHERE task_status='待补传'`），第二次跑影响 0 行——留它是为了将来若从旧备份恢复出该值，`init_db.php` 一跑就自愈。代价是：**若将来有人给 `待补传` 赋予新含义，会被这条迁移静默改写**，故词表里不再启用这个值。
- **上传任务页单据日期默认最近 7 天这件事没变**：近 7 天没单的门店（白田、郦江）统一后仍需手动放宽日期才看得见。那是日期筛选的性质，与状态值无关，本 ADR 不碰。
- **`未识别` 行一并迁移**：它们本就该出现在默认视图里被人看见（该页对 `未识别` 有整行标红 + 红色徽标的处置），统一后自动进入。
