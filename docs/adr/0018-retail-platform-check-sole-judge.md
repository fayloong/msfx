# 门店单判据统一到平台核查：暂时停用源库状态表（分流 / 闭环 / 门卫的两个数）

- 状态：已接受（2026-10-05）——**暂时**，附恢复路径
- 暂停：[ADR 0017](0017-retail-collection-split-gate-closure-snapshot.md) 的第 1 节（分流）、第 2 节里的两个数（已上传/未上传）、第 3 节（状态闭环）、第 4 节的快照落库口径；[ADR 0007](0007-retail-no-platform-reconciliation.md) 修订注三里"以状态表为判据"的那半
- 相关：[ADR 0016](0016-retail-upload-state-writeback.md)（**回写保留**，本文只动读侧）、[ADR 0011](0011-retail-retransmit-metadata-and-manual-trigger.md)（补传人工触发，未动）

票：`.scratch/retail-platform-check/issues/03-platform-check-sole-judge.md`。

## Context

门店单据由外部系统上传，本项目只做「可见 + 人工补传」（ADR 0007）。判「这张单到底传没传」有过两条判据：

1. **源库状态表**（`dyt.bs_msfx.dbo.update_state`）——2026-10-02 起用它做**采集分流**（已上传→写「外部上传」记录不建任务）与**状态闭环**（本地待办按它翻正）。它免费、每 30 分钟一轮，但记的是**外部系统的行为**，不是平台的承诺。
2. **平台核查**（`check_bill_status_retail.php`，`lsyd.query.upbilldetail`）——2026-10-05 建，拿各门店自己的凭据直接问平台，天然按企业隔离。

判据 1 的失效方式很安静：外部系统**写了状态却没真传成**时，那张单会被判成"已上传"→ 不进补传队列（分流）或很快被翻掉（闭环）→ **本地再也看不见它**，而平台上一片空白。2026-10-02 的源库探测已经确认外部系统正在故障中（当日 94 张单只有 3 张被标已上传，两年窗口整体却约 65% 有标记）。用户 2026-10-05 拍板：**暂时不再以那张表作判据**。

## Decision

**门店单「是否已上传」的判据统一到平台核查这一条**；源库状态表在**读侧整体退出**（只保留写侧）。

| 面 | 改动 |
|---|---|
| 采集 SQL | 去掉 `case when exists(状态表…) as uploaded` 标志列——`fetch_bills_retail.php` 从此**不碰**那张表 |
| 采集落库 | **不分流**：单据一律建「等待上传」任务（本地已有任务行/成功记录则跳过，幂等判据不变）。`decide()` 去掉 `$uploaded` 参数与 `ACTION_RECORD` 分支；`tally()` 的 `records` 与 `record()` 随之删除 |
| 状态闭环 | `closeLoop()` **停接**（保留方法，docblock 写明恢复路径）。`closureActions()` / `applyActions()` 一字未动——平台核查走的就是它们 |
| 计数门卫 | 三个数退成**一个数（当日总数）**：不再 JOIN 状态表；基线形状 `{date, total}`；带旧键的基线判为旧版、视为无基线照常采一轮 |
| 全量快照 `--all` | 保留入口但**退成只统计**：所有单落 `ACTION_COUNT_ONLY`，**一个字节都不写**（含认领告警 JSONL）。用途只剩"欠账是个可查的数" |
| 回写 | **保留**（`App\UpdateStateWriter` 一个字未动）——写出去是告诉外部系统"别再传"，与本地判据无关 |

## 排除的方案

- **只拆分流、保留闭环**：同一个判据、同一种失效方式——单子会先入队、再被那张表翻掉，绕一圈还是静默消失（见票 03 的决策表）。
- **按凭据就绪情况分而治之**（已配凭据的 5 家停闭环、其余保留）：队列最干净，但等于让那张表继续当 2/3 门店的判据，与"统一到平台核查"相悖；两种判据并存时，"这张单为什么被翻"又要看门店才知道。
- **停掉回写**：那会让外部系统重复上传本项目已补传成功的单；且回写与"信不信它的读"是两件事。
- **门卫照旧数三个数**：后两个数读的正是那张表，外部系统写得乱时它们一直在变，门卫会一直判"有变化"而丢掉省轮次的作用。
- **重验历史**：旧判据写下的 47,826 条 `retail_external` 记录（`response.judged_by` 是那张表）在本地已有成功记录，进不了 `pendingItems()`，本票**不重新核查**——按 `judged_by` 筛出来分批走平台核查是另一票的事。

## Consequences

**代价（明知故犯，运维要知道）**

1. **10 家未配凭据的门店 + `未识别` 的单翻不了正**：平台核查的 `groupByCompany()` 对它们整组跳过（没有 `ref_ent_id`，这条判据不成立）。它们的单会**一直挂在「等待上传」**（当前这类待办约 3,000 条），既不消失也不会被误翻。凭据配齐之日这些单自动进入核查范围。
2. **队列变长**：外部系统已上传的单也不再有"不建任务"这条捷径，先入队、等平台核查（白天每 30 分钟一轮 + 逐单 30 分钟门卫）翻正。已上传记录页上那条「外部上传」记录**因此晚一步出现**，且出处 JSON 的 `judged_by` 是平台接口名（不再是那张表）。
3. **`update_state` 的读侧判据"停用"而非"删除"**：`closeLoop()` 与 `ACTION_RECORD` 那套代码从 git 历史里还在，恢复路径见下。停用期间那张表**仍被写**（回写），所以它不会因为没人读而失去意义——它是**给外部系统看的**。

**恢复路径（"暂时"的另一半，按此顺序加回）**

1. `decide()` 加回 `$uploaded` 参数与 RECORD 分支、`ACTION_RECORD` 常量、`tally()` 的 `records`、`record()`——见本 ADR 那一次提交之前的样子（`git log -- docs/adr/0018-…` 的上一条）
2. `fetch_bills_retail.php` 的 SQL 加回 `case when exists(select 1 from … update_state us where us.bill_code=ls.bill_code) then 1 else 0 end as uploaded`（**必须 EXISTS 不能 JOIN**：该表无主键、无唯一约束，实测 82 个单号多行）与 `flushRetailBatch()` 的 RECORD 分支
3. 把 `RetailExternalUploads::closeLoop($source)` 那次调用接回采集之前（**顺序红线**：闭环在前、门卫在后）
4. 门卫 `counts()` 加回两个数与 JOIN，基线形状回到 `{date,total,uploaded,unuploaded}`——**必须同时改 `read()` 的形状校验**，否则旧基线一律判非法
5. `--all` 的 `buildTasks: false` 回到"只写已上传记录"

**恢复的前提**：外部系统恢复稳定、且"它写了状态就是真传了"这条重新成立。恢复前先回源库核对一次（状态表里的单号抽样去平台查）——这正是停用的那件事。
