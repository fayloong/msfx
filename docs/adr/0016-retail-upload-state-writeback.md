# 零售上传成功后回写源库 update_state：单条自动提交、SQL 侧幂等、失败不影响上传

- 状态：已接受（2026-10-02）
- 推翻：[ADR 0007](0007-retail-no-platform-reconciliation.md) 的"`update_state` 从不回写"一条

用户 2026-10-02 要求：零售门店上传成功后，往 `dyt.bs_msfx.dbo.update_state` 插入
`(bill_code, 1)`。需求与验收见 `.scratch/retail-chain/issues/18-retail-upload-state-writeback.md`。

## Context

零售单据由外部系统上传，本项目只做"可见 + 人工补传"（ADR 0007）。外部系统用
`dyt.bs_msfx.dbo.update_state`（`bill_code` + `bill_state` 两列）判断"这条单传过了没有"——
本项目采集侧的 `NOT EXISTS(update_state)` 过滤读的就是它（2026-09-30 测试阶段口径；**该口径已于 2026-10-02 改为「分流」，见 [ADR 0007](0007-retail-no-platform-reconciliation.md) 修订注三**——判据仍是这张表，读法不同）。
ADR 0007 当时判定本项目**从不回写**它，理由是"那是外部系统的私有状态表"；代价是人工补传成功后
外部系统不知情，会重传（平台返回"该单据号已存在"，白跑一轮），两边认知不一致。

ADR 0007 自己把这条列为待办："手动补传是否导致外部系统重复上传（本项目不回写 `update_state`），
作为独立议题另行确认。"本 ADR 就是那个议题的结论。

## Decision

1. **零售上传成功后回写**：`RetailRetransmit` 在全部子单跑完后，若**全部成功**
   （`上传成功` / `单据重复` 都算成功），写一条 `(原始单号, '1')`。拆单时写原始单号——
   `update_state` 是外部系统按 `zsm_ls.bill_code` 过滤的表，子单号 `单号_1` 对它没有意义；
   **任一子单失败就不写**（平台上只有半截，外部系统仍须处理它）。
2. **写操作绝不包在本地事务里**。探测实证：`BEGIN TRAN` 后写链接服务器会尝试启动分布式事务，
   而该链接服务器的 OLE DB 访问接口（`SQLNCLI10`）报"无法启动分布式事务"（MSDTC 被禁）——
   包了必失败。单条自动提交的 INSERT 则可行（真写 + 删除实测通过）。
3. **幂等靠 SQL 自身**：`INSERT INTO ... SELECT ?, ? WHERE NOT EXISTS (SELECT 1 FROM ... WHERE bill_code = ?)`。
   该表**无主键、无唯一约束**（只有一个非唯一非聚集索引 `(bill_code, bill_state)`，存量 67,842 行、
   `bill_state` 全为 `'1'`，且**已有同号多行先例**——外部系统自己也重复写），所以不指望约束兜底，
   也不采用"先查后插"两步（有竞态、多一次往返）。
4. **失败不影响上传结果**：上传已不可逆，回写只是尽力而为的后续动作。写失败记一条 JSONL 警告
   （`type=update_state_write_failed`），**不抛异常、不进 `upload_logs`**——后者是上传结果日志，
   写进去会在失败记录页冒出既非上传也非失败的记录，污染唯一的告警出口（ADR 0007 已定的口径，
   与 `name_unmatched` 同款处理）。
5. **三个入口全覆盖**：落点在 `RetailRetransmit`，补传 / 批量重传的零售那批 / 门店手工建单
   （含 xlsx 导入）自动都在内。手工建的单外部系统同样不知情，回写语义与补传一致。
6. **存量回填**：上线前已补传成功的 8 个零售单号（判据从 `upload_logs` 取：零售企业 +
   `上传成功`/`单据重复`）用一次性脚本 `scripts/backfill_update_state.php` 回填，幂等可重跑。

## 排除的方案

- **用本地事务包住写入**：MSDTC 被禁，必然失败（探测实证）。且即便可行，本地事务也覆盖不到
  远程表——它的价值本就有限。
- **先 SELECT 判断再 INSERT**：两步之间有竞态，多一次往返；且远程表自己都容忍重复行，
  为它加一层并不原子的一致性检查不划算。
- **依赖表约束（唯一键）去重**：那是外部系统的表，本项目无权改结构；且增量重复的后果只是
  多一行冗余状态（`EXISTS` 判断不受影响），不值得为它推动对方改表。
- **只写"上传成功"、不写"单据重复"**：两者对这张表是同一个事实（单据已在平台上），
  分两个口径写会让"该不该写"在页面与链路之间有第二套解释。
- **写失败重试**：补传是人工触发、结果即时呈现，重试会把延迟加到操作者身上；且失败原因
  （源库不可用）多半不会在一次会话内自愈。记警告、由人择机重传即可——重传会重新触发回写。

## Consequences

- **外部系统不再重传本项目已申报的门店单**：`update_state` 与 `upload_logs` 两个判重来源
  对同一事实给出一致答案。
- **回写只增不减**：本项目对 `update_state` 只有 `INSERT`，没有 `UPDATE`/`DELETE`。
  仓库里的写入路径仅 `UpdateStateWriter::markUploaded()` 与回填脚本两处，都走同一段 SQL。
- **`fetch_bills_retail.php` 的分流与回写形成闭环**：采集读同一张表把单据一分为二——已在表里的
  写成「外部上传」记录、不在的才进补传队列（**2026-10-02 票 02 由 `NOT EXISTS` 过滤改为此，
  见 [ADR 0007](0007-retail-no-platform-reconciliation.md) 修订注三**）；补传成功后表里有了记录，
  同一单不会再被采回补传队列——采集判重（`upload_logs`）是第二道，两者互为冗余。
- **读侧口径随之扩展（票 02 记）**：这张表原本只反映**外部系统**的进度；回写上线后它同时反映
  **本项目**的进度。后果之一是采集侧那条记录的来源名「外部上传」（`retail_external`）说的是
  **分流结果**——采集时该单号已在表里——**不保证一定是外部系统传的**，也可能是本项目补传后
  回写的。要分清得看该单有没有本项目自己的 `retail_retry` / `manual` 日志（见 CONTEXT.md
  「外部上传」词条的同一处说明）。
- **MSDTC 这条约束写进了代码注释**：将来若有人想给回写加事务（或把 `markUploaded()` 挪进某个事务块），
  注释与 ADR 都会指出它会失败。
- **告警出口只有 JSONL，但 JSONL 的写法只有一处**：`LogWriter::writeJsonlOnly()` 是"不写 `upload_logs`
  的 JSONL 追加"的公共入口（`write()` 与它共用私有的 `appendJsonl()`），回写的
  `update_state_write_failed` 与采集的 `retail_claim_name_unmatched` 都走它——code-review 指出这三处
  曾各写一份同形状的追加代码（2026-10-02 收口）。
- **探测留下的唯一痕迹已清除**：真写验证用 `__PROBE_` 假单号，验证后立即 DELETE，
  表内行数与探测前一致（0 残留）。

## 修订注一：读侧口径再扩一条——平台核查（2026-10-05）

本 ADR 记的"读侧口径随之扩展"，当时说的是**一条**判据（源库状态表）同时反映外部系统与本项目的进度。
2026-10-05 起补上**第二条判据**：`scripts/check_bill_status_retail.php` 拿各门店自己的凭据调
`alibaba.alihealth.drugtrace.top.lsyd.query.upbilldetail`（参数 `bill_code` + `ref_ent_id`）直接问平台。

- **为什么还要一条**：状态表是**外部系统的行为**，不是平台的承诺——外部系统传了单却没写它，
  本项目就永远不知道，任务一直挂在「等待上传」，人只能赌一次补传（撞上"该单据号已存在"返回
  `单据重复`才算收场）。平台查询是只读的、带 `ref_ent_id`、**天然按企业隔离**（状态表没有企业列，
  判据只能按裸单号比对——ADR 0007 记的那条已知代价，闭环那层无法消除）。
- **写进去的东西不变**：翻正后的落库形状与状态闭环逐项一致（任务行翻「已处理」+「上传成功」、
  `request_status` 不动；失败记录**追加**一条「外部上传」记录、不改写历史）——判定与落库
  `RetailExternalUploads` 那套一行没重写，本 ADR 关于"回写只增不减""来源名说的是分流结果"的
  结论都不受影响。第三条路径写的**也是** `source='retail_external'`，靠记录里 `response` 的
  `judged_by` 字段（平台接口名）与状态表那条分清。
- **边界**：取不到凭据的门店（`未识别` / 待配凭据）整组跳过——没有 `ref_ent_id` 这条判据不成立；
  脚本手动跑、不进 cron（与 `upload_pending_retail.php` 同一态度：验证充分前不装常驻任务）。
