# ADR 0001: check_bill_status 采用按单据新鲜度门卫

- 状态：已接受（2026-08-01）
- 关联代码：`scripts/check_bill_status.php`、`scripts/init_db.php`

## 背景

`check_bill_status.php` 用于批量查询单据在码上放心平台的上传状态，cron 原每 30 分钟一次，每次对全部待查单据（约 300 条）逐个调 API（0.5s 间隔，约 2.5 分钟）。大部分单据是"等待上传/信息不存在"的长期滞留项，每次全量重查是大量重复的外部 API 调用，存在限流风险。

需求是提高 cron 频率以更快发现"被其他路径上传"的单据，同时用最少的 API 请求完成刷新。

## 决策

1. **按单据粒度的新鲜度门卫（per-record freshness），而非整体门卫**：`upload_tasks` 与 `upload_logs` 各新增 `last_checked_at` 列（幂等迁移于 `init_db.php`），查询只拉 `last_checked_at IS NULL OR last_checked_at <= 阈值` 的单据。整体门卫（集合指纹无变化则全部跳过）被否决：一条新单据进入集合会触发全量重查，请求次数不是最少，且会延迟发现外部状态变化。
2. **阈值统一 30 分钟**（常量 `CHECK_INTERVAL_MINUTES`），不按来源区分——"信息不存在"来源当前仅约 15 条，分阈值收益 <5% 不值得增加逻辑分支。
3. **更新规则**：API 查询成功（含"信息不存在"）才 touch `last_checked_at`；API 异常与循环内"已确认在平台跳过"不 touch，下次 cron 自动重查。新单据 `last_checked_at` 为 NULL，天然立即查。
4. **cron 频率提到 8-20 点每 5 分钟一次**；稳态下单次只查约 1/6 集合（约 50 条、25 秒），每日请求量约 1.4 万次，由阈值锚定，暂不加每日请求上限保险丝（上线观察日志后再定）。
5. 状态存 SQLite 新列而非 JSON 状态文件（fetch_bill_counter.json 同款思路被否决）：集合 300+ 且动态变化，JSON 与库数据脱节、单据删除后残留，且与 `updated_at` 语义（被上传/编辑等多路径 touch）混淆。

## 后果

- 正向：高频 cron 下对无变化单据零 API 请求；发现外部上传的延迟由阈值（≤30 分钟 + cron 粒度）锚定；新单据立即查。
- 代价：每张单据需维护一个时间戳列；"信息不存在"单据 30 分钟内即使平台已录入也不会被发现（可接受）。
- 注意事项：Web 编辑任务不重置 `last_checked_at`（决策：保持改动面最小，延迟 ≤30 分钟可接受）。
