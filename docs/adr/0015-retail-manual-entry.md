# 门店手工新增单据：对手方按名称查平台、按发货/收货语义落位，元数据不由人录

- 状态：已接受（2026-10-01）

用户 2026-10-01 要求把手动上传页的**门店分支**从"已采集单据的补传清单"改成与批发同构的
"**在线新增 + xlsx 批量导入**"，理由是那份清单与上传任务页重复。本文记由此定下的几条难改决定，
以及它**推翻/保留**了此前哪些结论。需求与验收见 `.scratch/retail-chain/issues/14-retail-manual-entry.md`。

## Decision

1. **门店分支 = 在线新增 + xlsx 导入**，撤掉补传清单（连同 `api/manual_retail_tasks.php`、
   `api/tasks_batch_retry_retail.php`、`RecordQuery` 的第 4 类 `retail_tasks` 与导出的同名分支）。
   补传只剩一个入口：**上传任务页**门店行（`source='retail'`）的"补传"按钮——
   门店行按企业筛、按状态筛、导出、编辑、删除都在那一页，不必在手动上传页再养一份。
2. **单据类型只认门店那四种**（`104`/`203`/`321`/`116`），其中 **`321`/`116` 不填"往来单位名称"**：
   它们走 `lsyd.uploadretail`，接口里根本没有对手方入参（对手是消费者，不是平台注册的往来单位）。
   `104`/`203` 走 `lsyd.uploadinoutbill`，`fromUserId`/`toUserId` 是平台必填，故要名称。
3. **对手方的 entId 由"人填的名称"查出**（`App\EntDirectory`：`ent_list` 缓存 → 平台的 `listparts` 查询），
   查询必须用**该门店自己的凭据与其 `ref_ent_id`**——用错主体的编码查，查到的是别人名下的往来单位。
   查不到即**拒绝建单**（不落库、不发上传调用），不带着空 ID 上平台。
4. **落位按 SDK docblock 的发货/收货语义**：`104` 调拨入库（本店收货）→ `from=对方`、`to=本店`；
   `203` 调拨出库（本店发货）→ `from=本店`、`to=对方`。对手方三列**只对调拨两类写**（`321`/`116`
   走的是没有对手方入参的接口，三列留空——只有"这条单的对手是谁"有唯一说法，才不会在页面上出现
   第二种解释）；其中 `physic_type` 取常量 `3`（源表 `zsm_ls.physic_type` 实测全表恒为 3，
   批发链路同样硬编码 `"3"`）。
5. **落库用采集单的同一个 `source='retail'`**（不新开取值）：上传任务页的"补传"按钮判定、门店徽标、
   以及 `cleanup_logs` 的 2 年超期清理都认这一个值，加第二个值就要在几处白名单里各补一笔，
   漏一处就是静默错误。代价是来源列显示"零售采集"、分不出手工录入——要分辨看日志的 `source`
   （手工建单记 `manual`，补传记 `retail_retry`）。
6. **2 年下限同样适用于手工建单**：日期早于 `App\RetailRetention::cutoffDate()` 直接拒——
   平台不接受 2 年前的单据，手工建一张出来同样补传不出去，不如在建单那一刻就说清楚。

## 与 ADR 0011 的关系：推翻一条，加强一条

- **推翻**："元数据必须取自采集时落库的记录、不提供从零手工录入"。手工建单没有源表行可取，
  `from_user_id`/`to_user_id`/`physic_type` 只能现场确定——那条结论的前提（"本轮不查平台"）也不成立了。
- **加强**："不由人录平台 ID"。人录的是**往来单位名称**，平台 ID 由服务端查出来；页面上没有任何
  可以填平台 ID 的地方。ADR 0011 担心的"录错了察觉不了"，在"名称查不到就拒建单"这里反而更早暴露。
- 其余结论不变：补传仍只人工触发、失败也翻 `已处理`、`credential` 列仍是审计值。

## ⚠️ 与 ADR 0010 的一处已知不一致（待确认项未解除）

ADR 0010 定的采集链路是**照搬源表同名列、不按发货/收货语义翻转**——源表 `104`/`203` 的
`from_user_id` 都只有总部一个值，两列不随调拨方向翻转。手工建单没有源表可照搬，只能按语义合成，
于是**同一种 `203` 单据在两条路径上可能落到相反的 from/to**。

这不是本 ADR 能解决的：ADR 0010 那条待确认项（203 究竟该不该反向）仍需外部系统工程师拍板，
**确认后两条路径要一起对齐**——采集侧改 `RetailRequestAssembler` 的取值，手工侧改
`RetailManualEntry::endpoints()`。`tests/retail_manual_test.php` 把手工侧现在的取值钉住，
届时改哪边、怎么改，从测试就能看出来。

## 排除的方案

- **让人直接填平台 ID**（`fromUserId`/`toUserId`）：手抄 32 位 hex 几乎必然出错，且错在"报给谁"这个
  不可逆的维度上。ADR 0011 已排除，本 ADR 维持。
- **对手方固定取总部**（源表实测 104/203 的对方 ID 恒为总部，本店 ID 在凭据里，两个 ID 都在配置中）：
  零查询、零歧义，但门店间调拨会报到错误主体，且"往来单位"这个词就变成了摆设。
- **新开 `source='retail_manual'`**：来源列能一眼分开手工与采集，代价是上传任务页的按钮判定/徽标/下拉
  与 `cleanup_logs` 的 2 年清理都要各加一笔——**漏掉清理那一笔会让超期单静默滞留**（白名单是 fail-closed
  的：新值不在里面就永远不被清理）。要分辨手工与采集，日志的 `source` 已经答得很清楚。
- **保留补传清单**：它与上传任务页是同一张表、同一批操作的第二个实现，只会在两侧漂移。
  用户 2026-10-01 判定"重复"，撤掉。

## Consequences

- **手工建的单能被补传**：任务行落在同一张表、同一个 `source`，`RetailRetransmit` 读的也是落库行——
  上传任务页的"补传"按钮对它天然生效，`from/to` 两列在建单时已写定。
- **对手方 ID 建单即冻结**：页面上改"往来单位名称"不会重解析 ID，故上传任务页的编辑弹窗对
  **零售行隐藏该字段**（留着就是一处"改了不生效"的静默陷阱；采集行的该列本就是空）。
- **`.env` 那笔留债还上了**：`ApiClient::queryEntInfo()` 的 `ref_ent_id` 不再是写死的河药值，改由调用方
  按申报主体传入；`UploadService::resolveEntId()` 一并委托 `EntDirectory`（河药凭据的 `ref_ent_id`
  本就取自 `.env` 同一个键，批发行为不变——副本 + 离线桩实测：批发 `listparts` 的 `ref_ent_id`
  与改动前一致）。
- **门店 AppKey 未必被授权 `listparts`**：门店凭据若调不动该接口，`104`/`203` 的手工建单会以
  "往来单位查不到"被拒（fail-closed，不会错报主体）。`321`/`116` 不受影响——它们不查对手方。
  这一点待生产实测确认；若确实调不动，需要另找查往来单位的接口（或退回到"人填名称 + 后台维护名录"）。
- **验证方式**：写路径（落库 → 装配 → 出网参数 → 日志 → 翻状态）在**项目副本**上用**离线桩**端到端跑通，
  全程没有碰平台（桩只认发给它的请求，不转发）。见工单 14 的验收记录。
- **批量补传一度没有出口，同日补回**（本决策的连带后果 → 已由工单 15 消解）：撤掉的门店清单同时是零售
  **批量**补传的入口，而上传任务页的"批量重传"当时只走批发 kyt、批次里混入零售行会被整批拒传。
  **2026-10-01 修订（[工单 15](../../.scratch/retail-chain/issues/15-retail-batch-retransmit.md)）**：该端点已按行分流——
  `source='retail'` 的行逐条走 `RetailRetransmit`、其余仍走 `UploadService`，混批不再互相拖累，跨门店勾选允许
  （凭据仍按行取）。本 ADR 的决策 1（撤清单）不变：**撤的是那份与上传任务页同形的清单，不是批量这个能力**——
  页面侧只补回确认框的三处点名，门店行的补传/筛选/导出仍在同一张表上。见 CLAUDE.md「零售单据上传 → 入口」。
