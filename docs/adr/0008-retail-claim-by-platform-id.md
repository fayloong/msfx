# 零售门店认领以平台 ID 为键；去重键退回 (company, djbh)

- 状态：已接受（2026-09-29）

零售单据采集入库时，**以门店的平台 ID 作为认领键**（源表 `from_user_id` / `to_user_id`，即凭据里的 `ent_id` / `ref_ent_id`），门店名只在 ID 缺失时作回退；同时把落库记录的去重键从三元组 `(company, credential, djbh)` **退回二元组 `(company, djbh)`**，`credential` 降级为审计列。

## Context

原设计（见 ADR 0006）定的是"`oper_ic_name` 与配置门店名精确相等"认领、`(company, credential, djbh)` 三元组去重，且去重键放三元的理由是"主体 A 传成功不代表主体 B 传成功"。2026-09-29 对 `dyt.msfx.dbo.zsm_ls`（119,522 行）做只读探测后，两条前提都不成立了。

**事实一：门店名认不了单。** `oper_ic_name` 在 `321 使用出库` / `116 消费者退货入库` 这两类**消费级**单据上**全空**——共 101,288 行、占全表 84.7%。只有 `104 调拨入库` / `203 调拨出库`（8,153 行）有门店名。若照原设计实现，**85% 的门店单据谁都认领不到**，全部堆成"未识别"。

**事实二：真正的门店标识是平台 ID。** `from_user_id` / `to_user_id` 才是门店的平台 ID：321/116 的门店在出库方向 `from_user_id`（19 个不同值），104/203 的门店在入库方向 `to_user_id`。实测 321/116 的 20 个非空 `from_user_id` **20/20** 都能由 104 的「`oper_ic_name` ↔ `to_user_id`」对照认到门店——即一张对照表覆盖全部单据类型。

顺带解决的问题与暴露的脏数据：

- 凭据文件里的门店名用**半角括号** `()`、源库用**全角** `（）`，5/5 全部不命中。改用 ID 认领后，名字从"功能前提"降级为"显示 + 回退"，这个坑自动失效
- 一个门店确有**多个**平台 ID：新江分店 2 个（旧 entId 用到 2025-07、新 refEntId 自 2024-03 起，两段都在用）、雅居乐分店 4 个（含一个把数字 `0` 写成字母 `o` 的源库错值）
- 源表 `ref_ent_id` 列**不是门店的**（全表单一值，属总部主体），故上传时的 `refUserId` 只能取门店自己凭据里的值
- `321` 存在**完全重复行**（同一 `bill_code` 最多 120 行，14 列值全同、无任何区分列），采集必须先对源表去重，否则关联追溯码会被放大最多 120 倍
- `bill_type` 还有第五种 `999`（10,081 行，与 `104` 零 `bill_code` 重叠、语义未明）——用户判定**不采**，只采 `104`/`203`/`321`/`116` 四种

**事实三：三元组去重的前提不存在。** 用户答复了多套凭据的成因——门店可授权给不同开发者，但**目前只保留 1 个授权，第二个仅在主授权被平台限流时顶替，而数据量小基本不会限流**。这推翻了"两个主体各传一遍"的假设：既然备用凭据只是主凭据的替身，三元组不但不提供保护，反而**允许同一张单用两套凭据各传一次**，在平台上产生重复申报——恰恰是备用凭据永远不该做的事。

## Consequences

- 认领实现为 `App\Enterprise::claim()`（`src/Enterprise.php`）：按单据类型选列取 ID → 命中任一登记 ID 即认领；ID 缺失回退 `oper_ic_name`；都匹配不上 → `未识别` 照常入库
- 门店的**全部**平台 ID（含历史值与源库错值）登记在 `config/enterprises.local.php` 的 `ids` 里，按企业 key 归属；配置自检（`Enterprise::validate()`）强制"同一 ID 不得属于两家企业"与"凭据的 `ref_ent_id`/`ent_id` 必须在该企业 `ids` 内"
- 去重键退回 `(company, djbh)`：新增任务与"该单是否已上传成功"的判定都不再看凭据
- `credential` 列保留：采集时预填该企业的 primary 凭据键（表达"默认会用哪套"），补传时若人工切到备用凭据则由补传流程覆盖该行——它只回答"这次实际用了哪套"，不参与任何键
- 删除 `Credential.bill_types`（成因已排除"按单据类型分授权"这一维度，死字段比缺字段更危险）；新增 `primary`，且**声明在结构文件** `config/enterprises.php` 里——"哪套是默认授权"是结构性事实，不随密钥是否到手变化
- 新增**待配凭据**状态：企业有名字与平台 ID 但没密钥时，单据照常认领入库，页面标"待配凭据"、禁用补传。它是正常状态，与 `未识别`（配置漏店/源库改名的真异常信号）区分开
- 门店名仍需与源库**一字不差**（含全角括号）——它现在只影响页面显示与 ID 缺失时的回退，写错的后果从"认领不到"降级为"显示不好看 + 极少数无 ID 行认领不到"
- 本 ADR **修订而非推翻** ADR 0006：其核心（凭据是路由主体、门店与凭据 1:N、路由键是 `(企业, 单据类型)`）不变，被改的只是去重键与 `Credential` 的字段构成
