# 门店数据 2 年保留期：超期单据既不采集也不留存

- 状态：已接受（2026-09-30）

## Context

平台**不接受 2 年前的单据**——这是对接的硬性约束，2026-09-30 拿到平台原话。当日 13:52 有人补传宝源店 `WRKA0300000598`（单据日期 2023-07-19），平台返回（证据留在 `upload_logs` id=44298）：

```json
{"msg_code":"FAIL","sub_msg_code":"FAIL_BIZ_PARAM_BILL_TIME_BEFORE_ERROR",
 "msg_info":"单据上传失败！:系统不支持上传2年前单据(您上传的是2023-07-19 00:00:00)，请确认提交的单据时间是否正确",
 "response_success":"false"}
```

在此之前，门店数据的留存没有任何期限概念：`fetch_bills_retail.php --all`（一次性全量快照入口）会把源库里所有"外部系统尚未上传"的历史单一律入库，其中就包含 2023 年的。实测生产库中 `rq` 超 2 年的门店待补传单有 236 条（2023-08-13 ~ 2024-08-12）。

这些单在待补传清单里是一个**没有出口的队列**：操作者看得见、点得动，点了就被平台拒，然后在失败记录页留下一条 `上传失败`。它与"外部系统漏传、等我们来补"的正常欠账长得一模一样，但处置方式相反——后者要补，前者补不了也不该出现。

## Decision

1. **保留期定为 2 年**，截止日相对今天滚动（今天 2026-09-30 → 2024-09-30；**早于**该日即超期，截止日当天保留）。年数是平台的，不是本项目可调的参数，落成 `App\RetailRetention::YEARS`。
2. **两个落点，共用同一个截止日**：
   - **入口** `fetch_bills_retail.php`：采集 SQL 始终带 `bill_time >= 截止日`。`--all` 的语义因此由"全部历史快照"变为"最近 2 年的快照"（票 03 记录的旧口径数字重跑会变小，不是回归）。显式指定一个超期日期时直接拒绝并退出 1。
   - **出口** `cleanup_logs.php`：新增一条清理，`source='retail' AND rq < 截止日` 的 `upload_tasks` 删除。
3. **清理判据是 `rq`（单据日期），不是 `created_at`**：前两条清理判的是"记录存了多久"，这条判的是"单据本身多老"。`--all` 下差别最明显——2023 年的单据是今天才采进来的，但它昨天就该过期。
4. **只动门店链路**（`source='retail'`）。批发链路有自己的清理（`cleanup_logs` 按 `updated_at` 清已处理任务），且其 `rq` 全在 2 年内，本决定不越界。

## Consequences

- **只堵入口不够，出口必须有清理**——这是本 ADR 最容易被漏掉的一半：**今天合法的单据，两年后就不合法了**。存量的过期是随时间自然发生的，不是采集时的属性。若只加采集过滤，规则上线当天清完的清单会在两年后原样长回来。
- **超期数据被删是不可逆的**（本地），但**源库仍保有原始单据**：将来若平台放宽年限，`--all` 仍可重采。真正的丢失面是"这期间没人做过补传尝试"这个事实——而那个事实本来也不会发生（平台必拒）。
- **失败记录页那条 2023 年的补传失败日志不删**（用户 2026-09-30 选定）：它是真实发生过的事故记录，且 `cleanup_logs` 已按 `created_at` 在 3 个月后自动清掉。本决定只清待补传队列，不清日志。
- **"正好满 2 年当天"的判定未知**：边界取"截止日当天保留"。若平台严格拒绝满 2 年当天的单据，那一天会多留一天——量级个位数，次日即被清理，不做特殊处理。
- **回收成本已知**：若平台将来放宽年限（如改为 3 年），三处要一起动——`RetailRetention::YEARS`、以及两处调用点的注释里"2 年"的措辞（后者是文档债，不是逻辑）。这正是把它收敛成一个常量的理由：逻辑只有一处。
