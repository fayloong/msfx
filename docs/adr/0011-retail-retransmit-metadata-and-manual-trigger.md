# 零售补传：装配元数据入库（无回填）、人工单条触发、失败也算"已处理"

- 状态：已接受（2026-09-30）

> **2026-10-01 修订（任务状态词表统一，[ADR 0014](0014-unify-task-status-waiting-upload.md)）**：本文里提到的 `待补传` 一律读作 `等待上传`——门店采集单与批发共用一个状态值了（`待补传` 退出词表，`init_db.php` 把残留值归一）。**本文的结论全部不变**：三列入库无回填、元数据只取自落库行、失败也翻 `已处理`、日志来源 `retail_retry`、`104`/`203` 的警告。尤其"失败也算已处理"不受影响——任务表仍是待处理队列，"补传没成功"的出口仍是失败记录页。

> **2026-09-30 修订（工单 07）**：本 ADR 的**装配与落库结论全部不变**（三列入库无回填、元数据只取自落库行、失败也翻 `已处理`），但触发方式那一句被推翻——决策 3 与"排除的方案"里的**批量补传**已被 [工单 07](../../.scratch/retail-chain/issues/07-manual-upload-company-switch-and-batch.md) 实现（手动上传页选定门店后勾选清单批量补传，用户 2026-09-29 在 to-tickets 轮定的"补传入口做两处"）。
>
> 两条边界随之补齐，批量并没有放宽原有的谨慎：**整批限同一门店**（混入别家门店的 id 整批拒绝，一次请求里出现两家门店没有正当来由）、**逐条隔离**（一条被拒只影响它自己，其余照常补传）。"每个人工触发的申报都要看得清单号"这条没变——页面列出单号/日期/类型/码数，勾选与二次确认都在人手上。
>
> **`104`/`203` 仍不真传**（ADR 0010 的发货/收货语义待外部系统工程师确认）：批量入口把这条风险放大成一批，故页面在确认框里对本批含 `104`/`203` 的情形**显式警告**。
>
> **2026-09-30 修订（[ADR 0012](0012-credential-one-per-store.md)）**：本文决策 3、决策 4 与"排除的方案"里的**"由人显式选凭据""人工切到备用凭据"已被推翻**——门店与凭据定为 1:1，每家企业恰一套，补传由服务端按门店取（`Enterprise::credentialFor()`），页面没有凭据下拉、两个端点入参不含 `credential`。其余结论（三列入库无回填、元数据只取自落库行、失败也翻 `已处理`、日志来源 `retail_retry`、`104`/`203` 的警告）不变；`credential` 列仍是审计值，只是写回的永远是该门店那套。

工单 06 把零售补传从"一条装配好的请求"（工单 05）接通到**真实申报**：页面选凭据 → `src/api/tasks_retry_retail.php` → lsyd 接口 → 日志与任务状态。本文记三件事后难以改动的决定——装配要的三列怎么入库、补传由谁触发、失败的任务算不算处理完——以及首次真传实测到的平台行为。

## Context

- **装配要的三个字段没有落库来源**（工单 05 遗留）：`RetailRequestAssembler` 的输入需要 `from_user_id` / `to_user_id` / `physic_type`，而 `upload_tasks` 没有这三列、采集脚本也没落（连 `physic_type` 都没 `SELECT`）。补传的元数据**必须**来自采集时落库的记录——票面明确"不提供从零手工录入"：手工录 4 个平台 ID 几乎必然出错，且本轮不查平台，录错了察觉不了。
- **补传是向平台的真实申报，不可逆**：外部系统用的是哪套 AppKey 尚未确认；若它已用另一个主体传过同一张单，本项目补传可能造成重复申报（见 `docs/adr/0007` 与 spec 的"外部依赖"表）。
- **已入库的 231 条零售行缺这三列**（工单 03 验收时采集的），不处理就永远补不出去。

## Decision

1. **三列入 `upload_tasks`**（`from_user_id` / `to_user_id` / `physic_type`；采集时从源表照搬、SQL 用 `MIN()` 取确定性代表值），**没有历史回填**——批发行走 kyt 接口根本不用这三列，零售行的值只能从源表现采，回填不出来。
2. **旧行删除后按日期重采**（2026-09-30 执行：231 条 → 删 → 重采 2026-09-29 / 2026-09-30 / 2023-07-19）。因为 `(company, djbh)` 去重会跳过已存在的行，**不删就补不上值**；删除前 `sqlite3 .backup` 到 `/root`（不入仓），重采以源库现状为准（顺带带上采集后新增/补录的单据）。
3. **补传只人工触发、由人显式选凭据**：不做 cron、不做多套凭据的自动分发规则（由人指定比猜一套规则可靠）。
   ~~只单条~~ → **2026-09-30 工单 07 修订：两个入口都人工触发**——数据页单条 + 手动上传页选定门店后批量（见文首修订块）。
4. **失败也翻 `已处理`**，并把该行 `credential` 覆盖为**这次实际用的那套**（采集时预填 primary，人工切备用由补传覆盖）。

## 排除的方案

- **写一次性回填脚本补三列**：补不出"源库已补录的追溯码"（`trace_codes` 仍是旧快照），且留下一个跑完即废的脚本；而重采的代码路径本来就要改（采集脚本加三列 + 采集 SQL 加 `MIN(physic_type)`），多维护一条一次性路径不如复用采集。代价是 `created_at` 刷新，接受。
- **不删旧行、补传时回源库现查三列**：补传链路上多一次源库往返，并且破坏"装配是零网络纯函数"这条接缝约束（`docs/adr/0010` 已排除）。
- **补传失败把任务退回 `待补传`**：与批发链路不一致（那里也是"已处理"），且任务表是**待处理队列**、不是重试计划表——"补传没成功"的出口是失败记录页（`api/failed.php` 的 `NOT EXISTS` 只排除 `上传成功`/`单据重复`）。失败后要再试，是在任务页按"已处理"筛出该行重传。
- ~~**批量补传**：零售的批量需求由"采集 + 人工逐条"覆盖；每一次申报都不可逆，人看清单号再传比批量可靠。~~
  **2026-09-30 工单 07 推翻**：票量摆在这儿（单店积压可到几十张），逐条点会在页面上磨掉操作者的注意力，反而更容易点错。改为：批量入口仍在人手上（列清单、勾选、显式选凭据、二次确认），并加了整批限同一门店与逐条隔离两条边界；`104`/`203` 的确认框里额外警告（ADR 0010 待确认项）。

## Consequences

- **缺三列的零售行补不出去**：SDK 请求类自己的 `check()` 会把空的 `physicType` 拦下（fail-closed，不会错报主体），操作者看到的是一条带单号的拒绝消息。将来遇到这类行，修法同样是重采该日期。
- **平台对业务拒绝也返回网关级 `success=true`**：实测「存在已出售的码」这类业务拒绝也是 `{"success":true, ..., "msg_code":"FAIL"}`。因此补传的进度与汇总按**业务结果**计（`上传成功`/`单据重复` 算成功，其余算失败），不照搬 `ApiClient::execute` 的 `success`（那是网关级：无 `code` 错误即 true）——否则一次真实失败会显示成绿色 [成功]、汇总写成"成功 1"。批发链路不在此改动范围内（既有行为，另行处理）。
- **两个 lsyd 接口的响应与 kyt 是同一套 TOP 信封**（`result.msg_code` / `msg_info` / `response_success`），故 `ApiClient::resolveUploadResponseStatus`（原 `UploadService` 的私有方法，本票上移到 `ApiClient`，与 `isBillFound` / `sumBillDetailCount` / `sumPkgAmount` 这些响应解析器同处）**两个接口族通用**。实测映射：`SUCCESS` + `response_success=true` → `上传成功`；`msg_info` 含"该单据号已存在" → `单据重复`；`msg_code=FAIL` → `上传失败`。
- **`单据重复` 不进失败记录页**（2026-09-30 实测可见数为 0）。排除它的是 `api/failed.php` 的**第一条条件** `response_status NOT IN ('上传成功','单据重复')`——`单据重复` 自身就不满足它。第二条那个按 `(company, djbh)` 的 `NOT EXISTS` 管的是另一件事："同一单号后来传成功了，它的旧失败记录不再显示"。两条都是既有口径，不是本票引入的。
- **补传失败的任务从"待补传"里消失**（翻成"已处理"）是刻意的：`待补传` 的含义是"还没被人处理过的门店单据"。
- **`docs/adr/0010` 的待确认项仍未确认**：首次真传刻意选了 `321`（`uploadretail`，只用 `refUserId`，不碰 `fromUserId`/`toUserId`/`physicType`）。`104`/`203` 的真传仍需外部系统工程师确认发货/收货语义后再做；**批量入口（工单 07）只是把这条风险显式警告出来，没有解除它**——`104`/`203` 的真传实测仍是欠账。
- **补传面对的现实**：平台对**已被申报过的销售单**返回业务错误「存在已出售的码」——即补传不是"重放"，而是真的在申报；外部系统若已传过同一张单，本项目会得到业务错误而不是静默重复。首次真传的三单结果（1 成功 / 1 上传失败 / 1 单据重复）见 `.scratch/retail-chain/issues/06-retail-single-retransmit.md`。
