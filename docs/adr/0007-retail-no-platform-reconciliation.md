# 零售连锁本轮只做采集与手动补传，不做平台状态查询与数量对账

- 状态：已接受（2026-09-29）；**下方"去掉 `update_state` 过滤"一条于 2026-09-30 被测试阶段临时口径推翻**（见修订注一）；**"`update_state` 从不回写"一条于 2026-10-02 被 [ADR 0016](0016-retail-upload-state-writeback.md) 推翻**（见修订注二）；**过滤本身于 2026-10-02 改为「分流」**（见修订注三，测试阶段至此结束）

接入零售连锁的第一阶段，零售侧**不调用任何码上放心查询接口**，只做三件事：从 `dyt` 源库采集单据入库、Web 展示、人工手动补传。源库的 `dyt.bs_msfx.dbo.update_state` 表**从不回写**。（本条初稿写的是"不读也不写"，**2026-09-30 修订**为"只读、用来过滤"，**2026-10-02 再修订**为"只读过滤 + 本项目上传成功后回写"——见下方两条修订注。）

> **修订注一（2026-09-30，测试阶段临时口径）**：用户指示测试阶段把 `NOT EXISTS(dyt.bs_msfx.dbo.update_state)` 过滤加回采集 SQL，理由是"待补传清单里不该有外部系统已经传过的单"。## Context 里判定的两条代价依旧成立，只是测试阶段接受：① 已上传的单在页面上不可见；② `update_state` 无企业列，跨门店单号重复时它自身会串。同批还改了采集 SQL 的形状：**单条 `LEFT JOIN` 取代"先头后码"两步**，去重从 SQL 挪到 PHP 侧。**日期过滤保留**——cron 只采当日；外部系统的历史欠账另开 `scripts/fetch_bills_retail.php --all` 一次性全量快照入口（不带 `bill_time` 条件，跑一次即可、不挂 cron）。**测试结束后要么回收、要么按新证据重新评估本 ADR**——回收前以 CLAUDE.md / CONTEXT.md 的"零售单据采集"章节为准。

> **修订注二（2026-10-02，工单 18）**：用户要求"零售门店上传成功后，插入 `dyt.bs_msfx.dbo.update_state (bill_code, 1)`"——**"从不回写"一条就此推翻**。决策、探测证据与被排除的方案见 [ADR 0016](0016-retail-upload-state-writeback.md)。要点：回写落在 `App\RetailRetransmit`（**全部子单成功后**，写原始单号）→ `App\UpdateStateWriter`；幂等靠 `INSERT ... WHERE NOT EXISTS`（该表无主键无唯一约束），**不能包本地事务**（写链接服务器起不了分布式事务，探测实证），写失败只记 JSONL 警告、不影响上传结果。它与**采集侧的判据**形成闭环：本项目补传成功的单不会再被采回补传队列（修订注一那条过滤已于 2026-10-02 改为分流，见修订注三——闭环本身不变，只是判据从"过滤"变成"分流"）。上线前已补传成功的 8 个单号由 `scripts/backfill_update_state.php` 一次性回填（幂等可重跑，2026-10-02 已执行）。

> **修订注三（2026-10-02，票 02）：测试阶段结束，采集由「过滤」改为「分流」**。单据**全采进来**，按同一张状态表一分为二——**已上传的**写成一条「外部上传」记录进已上传记录页（`source='retail_external'`、`response_status='上传成功'`、`task_id=0`、`request_status` 留 NULL：本项目没发起请求；`response` 写一段出处 JSON），**不建任务**；**未上传的**照旧建「等待上传」任务由人补传。判定收在 `App\RetailExternalUploads::decide()`（已上传→记录 / 未上传→任务 / 本地已有痕迹→跳过），采集 SQL 里多取一个 `EXISTS` 标志列（**判据必须 EXISTS 不能 JOIN**——该表无唯一约束、实测 82 个单号多行，JOIN 会放大结果集）。**⚠️ 本条（分流）与随之而来的状态闭环已于 2026-10-05 停用**（外部系统不稳定，那张表的痕迹不再是证据；读侧整体停用、判据统一到平台核查），见 [ADR 0018](0018-retail-platform-check-sole-judge.md)。
>
> **## Context 里"去掉过滤"那个决定就此以另一种形式兑现**：过滤确实去掉了（这正是本 ADR 的原始判断——"核对恰恰需要看见它们"），但已上传的单不再像初稿设想的那样只是"可见"，而是**与待办队列分开落库**。修订注一那两条代价里的①（已上传的单在页面上不可见）随之消解；②（该表无企业列、跨门店单号重复时自身会串）仍在，只是不再影响"看不看得见"。测试阶段那句"回收或重新评估"到此结案（见 `.scratch/retail-collection-split/spec.md` §1/§4）。
>
> 同批工作的其余三件**不在此注范围**：状态闭环（外部系统后来把某张单传成了 → 本地待办痕迹自动翻正）是票 03；计数门卫是票 04；`--all` 快照的"只写已上传记录"新语义是票 05。本注落笔时它们均未实现；**2026-10-02 票 07 复核：三件均已落地，四个决定合并记入 [ADR 0017](0017-retail-collection-split-gate-closure-snapshot.md)**（分流 + 门卫 + 闭环 + 快照，含三条已知代价）。

## Context

用户判定"暂时搁置对账功能，暂时没有很好的办法可以对账"，具体原因有二：

1. 零售的 `321 使用出库` / `116 消费者退货入库` 是**消费者级**单据，跑批发的两级对账流水线无从落地——第 1 级要 `skwms_new` 明细视图的 `SUM(shl)` 做本地数量基线（零售在 `dyt` 库，且不确认有数量列），第 2 级要 `searchbill.detail` 返回 `min_pkg_count` 做码级折算（零售对应接口的 `showCode` / `dealStatus` 语义尚未确认）。
2. 零售单据由外部系统上传，本项目定位是检查而非补传。**在半成品状态下打平台接口，错误口径会持续产出脏状态**——现有唯一的告警出口是 Web 失败记录页，一旦混入大量口径错误的"信息不存在"，这个出口就失效了。不做比做错更可取。

源采集 SQL 原本带 `NOT EXISTS(dyt.bs_msfx.dbo.update_state)` 过滤，本 ADR 一并决定**去掉**它：该过滤会把"外部系统已上传的单"全部隐藏，而核对恰恰需要看见它们；`update_state` 是外部系统的私有状态表（只有单号 + 上传状态两列，**无企业列**，跨门店单号重复时它自身就会串），不能当本项目的采集门卫。

> ⚠️ **本条已于 2026-09-30 被测试阶段临时口径推翻**（过滤加回），见文首修订注。上述两条代价未消失，只是测试阶段接受；测试结束需回收或重新评估。

- 门店单据的价值在本阶段是"**可见**"：采集入库 + 按门店归属展示 + 匹配不上时标"未识别"照常入库（丢单比错标更危险，必须能看见"有单没被认领"）
- `zsm_ls_code` 是否含数量列、两个 lsyd 查询接口的入参语义，都是**恢复对账时才需要**的前置；本阶段不阻塞
- 手动补传只支持"重传已采集单据"（元数据取自落库记录），**不提供从零手工录入**——手工录 4 个平台 ID（from/toUserId + refUserId + entId）几乎必然出错，且本阶段不查平台，录错了察觉不了
- 手动补传是否导致外部系统重复上传（本项目不回写 `update_state`），作为独立议题另行确认
