# 零售连锁本轮只做采集与手动补传，不做平台状态查询与数量对账

- 状态：已接受（2026-09-29）；**下方"去掉 `update_state` 过滤"一条于 2026-09-30 被测试阶段临时口径推翻**（见修订注）

接入零售连锁的第一阶段，零售侧**不调用任何码上放心查询接口**，只做三件事：从 `dyt` 源库采集单据入库、Web 展示、人工手动补传。源库的 `dyt.bs_msfx.dbo.update_state` 表**从不回写**。（本条初稿写的是"不读也不写"，**2026-09-30 修订**为"只读、用来过滤"——见下方修订注。）

> **修订注（2026-09-30，测试阶段临时口径）**：用户指示测试阶段把 `NOT EXISTS(dyt.bs_msfx.dbo.update_state)` 过滤加回采集 SQL，理由是"待补传清单里不该有外部系统已经传过的单"。## Context 里判定的两条代价依旧成立，只是测试阶段接受：① 已上传的单在页面上不可见；② `update_state` 无企业列，跨门店单号重复时它自身会串。同批还改了采集 SQL 的形状：**单条 `LEFT JOIN` 取代"先头后码"两步**，去重从 SQL 挪到 PHP 侧。**日期过滤保留**——cron 只采当日；外部系统的历史欠账另开 `scripts/fetch_bills_retail.php --all` 一次性全量快照入口（不带 `bill_time` 条件，跑一次即可、不挂 cron）。**测试结束后要么回收、要么按新证据重新评估本 ADR**——回收前以 CLAUDE.md / CONTEXT.md 的"零售单据采集"章节为准。

## Context

用户判定"暂时搁置对账功能，暂时没有很好的办法可以对账"，具体原因有二：

1. 零售的 `321 使用出库` / `116 消费者退货入库` 是**消费者级**单据，跑批发的两级对账流水线无从落地——第 1 级要 `skwms_new` 明细视图的 `SUM(shl)` 做本地数量基线（零售在 `dyt` 库，且不确认有数量列），第 2 级要 `searchbill.detail` 返回 `min_pkg_count` 做码级折算（零售对应接口的 `showCode` / `dealStatus` 语义尚未确认）。
2. 零售单据由外部系统上传，本项目定位是检查而非补传。**在半成品状态下打平台接口，错误口径会持续产出脏状态**——现有唯一的告警出口是 Web 失败记录页，一旦混入大量口径错误的"信息不存在"，这个出口就失效了。不做比做错更可取。

源采集 SQL 原本带 `NOT EXISTS(dyt.bs_msfx.dbo.update_state)` 过滤，本 ADR 一并决定**去掉**它：该过滤会把"外部系统已上传的单"全部隐藏，而核对恰恰需要看见它们；`update_state` 是外部系统的私有状态表（只有单号 + 上传状态两列，**无企业列**，跨门店单号重复时它自身就会串），不能当本项目的采集门卫。

> ⚠️ **本条已于 2026-09-30 被测试阶段临时口径推翻**（过滤加回），见文首修订注。上述两条代价未消失，只是测试阶段接受；测试结束需回收或重新评估。

## Consequences

- **零售任务状态用新值 `待补传`，不复用 `等待上传`**。这是本 ADR 最要紧的一条：`scripts/upload_pending.php:35` 现按 `task_status = '等待上传'` 取全部任务且**无企业过滤**，第 61 行 `new UploadService()` 凭据写死河药——零售单据若以 `等待上传` 落库，该 cron 会**用河药 AppKey 走 kyt 接口把门店单据申报到河药主体名下**，这是传到平台上的不可逆错误。`upload_pending.php` 取数口径必须同步加企业过滤
- `check_bill_status.php` / `check_failed_logs.php` / `check_quantity.php` 三个脚本一律排除零售记录——**实现为 `company` 白名单**（只查批发主体），不用"排除零售/其他来源"的排除法：排除法 fail-open，将来新增来源漏改条件就会拿河药凭据去查门店单号（2026-09-29 工单 02 落地）
- **零售记录保留在 `api/failed.php`（失败记录页）可见**（2026-09-29 工单 02 修订本条；初稿写的是"也不出现在失败记录页"）：检查脚本根本写不出零售日志，所以失败页上的零售记录必然是**人工补传失败**——那是操作者唯一能看见"补传没成功"的聚合出口，排掉它等于让补传失败无声无息。判重（`NOT EXISTS`）限定同一企业，零售不会被同号批发成功单顶掉
- 门店单据的价值在本阶段是"**可见**"：采集入库 + 按门店归属展示 + 匹配不上时标"未识别"照常入库（丢单比错标更危险，必须能看见"有单没被认领"）
- `zsm_ls_code` 是否含数量列、两个 lsyd 查询接口的入参语义，都是**恢复对账时才需要**的前置；本阶段不阻塞
- 手动补传只支持"重传已采集单据"（元数据取自落库记录），**不提供从零手工录入**——手工录 4 个平台 ID（from/toUserId + refUserId + entId）几乎必然出错，且本阶段不查平台，录错了察觉不了
- 手动补传是否导致外部系统重复上传（本项目不回写 `update_state`），作为独立议题另行确认
