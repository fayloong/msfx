## 要交付的行为

用户 2026-10-01 先问"为什么上传任务模块，选择门店都没有数据"，诊断见下；随后给定做法（原话）：

> 统一改为"等待上传"

即：**门店采集单不再落 `待补传`，与批发共用一个状态值 `等待上传`**。

**采集与补传的分工一个字不变**——门店单仍只人工补传、`upload_pending.php` 仍只取批发主体、失败仍翻 `已处理`。变的只是**状态词表**：一个值 `等待上传`，加上终态 `已处理`。

## 诊断（`待补传` 造成的可见性缺陷）

上传任务页有两条默认筛选（`src/views/upload_tasks.php`）：

1. 任务状态默认 `等待上传`（第 58 行硬编码 `selected`）
2. 单据日期默认最近 7 天（第 328-337 行；且"所属企业下拉不算关键词"，第 409-414 行注释写明是刻意的）

门店采集单落库是 `待补传`，于是**选门店 + 不切状态 = 恒 0 条**。生产库实测（2026-10-01）：

| 门店 | 默认口径 | 切「待补传」 | 待补传 + 近 7 天 |
|---|---|---|---|
| 新江分店 | 0 | 597 | 99 |
| 白田分店 | 0 | 1（2026-05-19） | 0 |
| 郦江分店 | 0 | 26（截至 2026-05-20） | 0 |

全库 `source='retail'` 6,137 行（6,135 待补传 / 2 已处理），数据一直在，是状态值把它挡在了默认视图外。

## 为什么现在可以撤销 ADR 0007 那条

ADR 0007 第 22 行原文给的**解除条件**是"`upload_pending.php` 取数口径必须同步加企业过滤"——该条件已于 2026-09-29（工单 02）兑现，而现在还有第二道闸：

| 闸 | 位置 | 现状 |
|---|---|---|
| 取数白名单 | `scripts/upload_pending.php:42` | `WHERE task_status = '等待上传' AND company = ?`（`Enterprise::wholesaleSubject()`），**白名单而非排除法** |
| 状态查询白名单 | `scripts/check_bill_status.php:64` | 同款 `AND company = ?` |
| fail-closed 守卫 | `src/UploadService.php`（`resolveContext`） | 非批发 kyt 一律拒传，整批拒、不发一次调用 |

ADR 0007 当年写下的风险路径（"该 cron 会用河药 AppKey 走 kyt 接口把门店单据申报到河药主体名下"）在**取数那一步就已经断了**：门店单的 `company` 是门店名，进不了白名单。守卫只是纵深防御。

反过来，`待补传` 的代价是实打实的：门店单在操作者最常用的那个页面（上传任务页，按门店筛选）**默认不可见**，而这正是本票的由来。

## 范围

### 1. 采集落库值

`scripts/fetch_bills_retail.php` 第 236 行 INSERT 的 `'待补传'` → `'等待上传'`；同文件与 `src/RetailRetention.php` 的注释同步（那里把超期单据叫"留在待补传清单里"）。

### 2. 页面

- **`src/views/upload_tasks.php`**：任务状态下拉删掉 `待补传` 这一项（第 59 行）、徽标表删 `'待补传'`（第 358 行）。门店单此后与其他待上传单同色 —— 区分靠已有的"所属企业"列与来源列，不再靠状态色。
- **`src/views/manual_upload.php`**（门店分支）：状态下拉的默认选中项 `待补传` → `等待上传`（第 196 行）、徽标表（第 437 行）、行内按钮判定 `task_status === '待补传' ? '补传' : '重传'` → `=== '等待上传'`（第 660 行）。已处理的行仍是"重传"——**这个出口不因本票改变**。

### 3. 端点注释

`src/api/manual_retail_tasks.php`、`src/api/tasks_batch_retry_retail.php`、`src/api/tasks_retry.php`、`src/api/tasks_batch_retry.php` 里引用旧值的注释。

后两个是批发重传端点，**逻辑不动**：它们在异常时"逐条恢复为各自调用前的状态"而不是统一写 `等待上传`。那条判断仍然对，只是理由要改写——原理由举的是"零售是待补传"，现在改为"在已处理的行上点重传，失败后不该把它拖回待上传队列"。

### 4. 数据迁移

`scripts/init_db.php` 加一条**幂等**迁移：`UPDATE upload_tasks SET task_status='等待上传' WHERE task_status='待补传'`。可重复执行（第二次影响 0 行），不加重建/回填那套判据。

**必须跑**：不迁移的话，历史 6,135 行仍留在旧值上，本票要解决的"选门店没有数据"原样存在。

### 5. 本票不动的

- **仪表盘 `src/views/dashboard.php:23`** 的"等待上传"卡片**无企业过滤**，统一后会把门店待补传一并计入（≈29 → ≈6,164）。这是已知后果，**本票不改**（CLAUDE.md 早已记明该页是筛选口径的第 5 份拷贝、另行统一）。见下方"已知后果"。
- **上传任务页的单据日期默认最近 7 天**：本票不碰。近 7 天没单的门店（白田、郦江）在统一后仍需手动放宽日期才看得见，那是日期筛选的性质，与状态值无关。
- `未识别` 的 51 行照常迁移（它们本就该在默认视图里被人看见、标红）。

## 已知后果

1. **`等待上传` 对门店单不再是字面承诺**：cron 不会取走它们（白名单），要人点"补传"。文档在 `CONTEXT.md` 的词条里把这点写明，免得下一个人照着字面以为会自动传。
2. **仪表盘计数跳变**（见上），需要时另行开票。
3. **失败记录页的出口不变**：补传失败翻 `已处理`，"没传成功"仍只在失败记录页可见（ADR 0011）。
