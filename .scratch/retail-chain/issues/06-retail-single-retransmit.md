# 06: 零售单条补传（数据页重传入口与落库）

- Status: done（2026-09-30）

- 关联：spec.md §8/§11、docs/adr/0006-credential-as-routing-subject.md、docs/adr/0007-retail-no-platform-reconciliation.md、docs/adr/0011-retail-retransmit-metadata-and-manual-trigger.md

## 要交付的行为

在上传任务页看到一条"待补传"的门店单据，选一套凭据点补传，**单据真的到了平台**，结果落进日志与任务状态；
同时操作者能分辨哪些单据**不能**补传、以及为什么。

## 范围

**入口**

- 上传任务页的零售行打开补传入口（取代工单 03 里被关掉的重传按钮）
- 用户**显式选择凭据**（下拉显示 `门店名（label）`；门店只有一套时显示门店名）——本轮**不做**多套凭据的自动分发规则，由人指定比猜一套规则可靠
- **不提供从零手工录入**：元数据（日期 / 类型 / 追溯码 / 单号）全部取自采集时落库的记录。手工录 4 个平台 ID 几乎必然出错，且本轮不查平台，录错了察觉不了
- 后端按企业类型分发；**不改造批发路径的既有行为**（批发的手动上传、单条/批量重传保持原样）

**装配与调用**

- 装配走工单 05 的纯函数；请求类与追溯码上限走 `App\Enterprise::route()`
- 限速与重试沿用现有约定：API 间隔 0.33s、仅网络错误重试 3 次（间隔 30s）、业务错误不重试

**落库**

- 写 `upload_logs`：带 `company` / `credential` / `task_id`，来源值要能与既有来源（cron / manual / batch_check / batch_retry / quantity_check）区分开
- 翻 `upload_tasks`：`task_status` → `已处理`，`response_status` 按平台返回

**禁用态（都要在页面上写清原因）**

- `未识别` 的行：这是**真异常信号**（配置漏了门店，或源库改了名），必须由人去查，不能补传
- **待配凭据**的门店：名字与平台 ID 齐备、单据能正常认领，但 AppKey/SECRETKEY 还没到手（15 家里当前有 10 家如此）。这是**预期内的正常状态**，与 `未识别` 不是一回事

**页面**

- 已上传页表格加"所属企业"列，让补传成功的门店单据能按企业认出来
- **失败记录页不动**：零售的人工补传失败照常出现在那里（检查脚本写不出零售日志，所以失败页上的零售记录一定来自人工补传——那是操作者唯一能看见"补传没成功"的聚合出口）；`check_failed_logs.php` 对该记录的自动复查在工单 02 已排除

## 实现笔记（超出票面的必要处理）

- **装配要的三列没有落库路径（票面前提缺口，开工前已问用户，定案：删旧行重采）**：`init_db.php` 幂等加
  `from_user_id` / `to_user_id` / `physic_type`（无历史回填），`fetch_bills_retail.php` 的采集 SQL 加 `MIN(physic_type)`、`INSERT` 落三列。
  已入库的 231 条（工单 03 采集）删除后按 2026-09-29 / 2026-09-30 / 2023-07-19 重采 → 233 条（含 12:05 cron 新采的 2 条），三列取值与源库一致（104/203 的 `to_user_id` 有值、321/116 只有 `from_user_id`、`physic_type` 全为 3）。删除前 `sqlite3 .backup` 到 `/root/msfx-backup-2026-09-30-1206.db`（不入仓）
- **旧行处理顺序**：必须**先改代码再删数据**——`fetch_bills_retail` 的 cron（`5,35 0,1,2,3,8-23`）**已装上**（CLAUDE.md 原写"尚未写入 root crontab"，本次已按 `crontab -l` 现状改正），先删后用旧脚本重采会把今天的单又写成缺三列的行
- **响应状态解析上移到 `ApiClient`**：零售补传要用与批发同一套平台语义，照抄一份 25 行判定会变成两份事实。搬过去与 `isBillFound` / `sumBillDetailCount` / `sumPkgAmount` 同处
- **进度/汇总的"成功"按业务结果算**（`上传成功`/`单据重复` 成功，其余失败）：实测平台对业务拒绝也返回网关级 `success=true`（`存在已出售的码` 那次就是），照搬会把真实失败显示成绿色 [成功]、汇总写成"成功 1"——这是本票真传时**实测暴露并修掉**的缺陷
- **来源值用 `retail_retry`**（不复用 `retail`）：`retail` 在任务表里是"采集来的门店单据"，日志里再用同一个值就分不清"采集"与"补传"；两页的来源标签/下拉已同步（失败记录页按票面"不动"未改，`retail_retry` 在那里显示为原值）
- **`CheckMaxListSize` 逼出拆单逻辑**：SDK 的 `check()` 会在超过接口上限时抛异常，故补传按 `Enterprise::route()` 的 limit 拆单（沿用 `单号_1` 约定）。实测零售单张码数上限 1,718，10000/3500 都不触发——这条分支是给"外部系统当初也传不上去的超大单"留的补传出口
- **失败也翻"已处理"**（照票面）：任务表是待处理队列，"补传没成功"的出口是失败记录页；失败后要重试，是在任务页按"已处理"筛出该行再传
- **异常时不复位任务状态**（与批发链路的 `tasks_retry` / `tasks_batch_retry` 刻意不同）：这条链路上任务行只在平台调用**之后**被写，所以异常要么发生在第一次调用之前（任务行没被动过）、要么发生在某个子单已完成之后（那一写就是真实结果）。照搬批发那套"复位成调用前的状态"反而会把已记录的结果抹成 NULL。实测：六条 fail-closed 拒绝跑完后 `task_status`/`request_status`/`response_status`/`updated_at` 全部原样

## 风险提示（实测更新）

补传是**向平台的真实申报**。外部系统用的是哪套 AppKey 尚未确认——若它已用另一个主体传过同一张单，本项目补传会在平台上造成**重复申报**。

2026-09-30 首次真传给出一条更具体的画面：平台对**已被申报过的销售单**会明确返回业务错误「存在已出售的码」（→ `上传失败`），对**本平台已存在的单号**返回「该单据号已存在」（→ `单据重复`）——
即"重复申报"在这一轮实测里表现为**业务拒绝**而不是静默入库，平台自身的单号唯一性在兜底。但这仍是外部依赖（见 spec 的"外部依赖"表），**上线使用前需要用户确认**哪套 AppKey 是外部系统在用的。
