# 06: 零售单条补传（数据页重传入口与落库）

- Type: task
- Status: ready-for-agent
- Blocked by: 03, 05
- 关联：spec.md §8/§11、docs/adr/0006-credential-as-routing-subject.md、docs/adr/0007-retail-no-platform-reconciliation.md

## 要交付的行为

在上传任务页看到一条"待补传"的门店单据，选一套凭据点补传，**单据真的到了平台**，结果落进日志与任务状态；
同时操作者能分辨哪些单据**不能**补传、以及为什么。

## 范围

**入口**

- 上传任务页的零售行打开补传入口（取代工单 03 里被关掉的重传按钮）
- 用户**显式选择凭据**（下拉显示 `门店名（label）`；门店只有一套时显示门店名）——本轮**不做**多套凭据的自动分发规则，由人指定比猜一套规则可靠
- **不提供从零手工录入**：元数据（日期 / 类型 / 追溯码 / 单号）全部取自采集时落库的记录。手工录 4 个平台 ID 几乎必然出错，且本轮不查平台，录错了察觉不了
- 后端按企业类型分发；**不改造批发路径的既有行为**（批发的手动上传、单条/批量重传保持原样）

**装配与调用**

- 装配走工单 05 的纯函数；请求类与追溯码上限走 `App\Enterprise::route()`
- 限速与重试沿用现有约定：API 间隔 0.33s、仅网络错误重试 3 次（间隔 30s）、业务错误不重试

**落库**

- 写 `upload_logs`：带 `company` / `credential` / `task_id`，来源值要能与既有来源（cron / manual / batch_check / batch_retry / quantity_check）区分开
- 翻 `upload_tasks`：`task_status` → `已处理`，`response_status` 按平台返回

**禁用态（都要在页面上写清原因）**

- `未识别` 的行：这是**真异常信号**（配置漏了门店，或源库改了名），必须由人去查，不能补传
- **待配凭据**的门店：名字与平台 ID 齐备、单据能正常认领，但 AppKey/SECRETKEY 还没到手（15 家里当前有 10 家如此）。这是**预期内的正常状态**，与 `未识别` 不是一回事

**页面**

- 已上传页表格加"所属企业"列，让补传成功的门店单据能按企业认出来
- **失败记录页不动**：零售的人工补传失败照常出现在那里（检查脚本写不出零售日志，所以失败页上的零售记录一定来自人工补传——那是操作者唯一能看见"补传没成功"的聚合出口）；`check_failed_logs.php` 对该记录的自动复查在工单 02 已排除

## 验收

- [ ] 一条待补传单据补传成功：平台上能查到该单（人工核对），已上传页出现该行且带正确的门店名
- [ ] 构造一次平台业务错误：失败记录页出现该行，任务状态正确翻转为 `已处理` + 对应 `response_status`，`upload_logs` 带上了 `company` / `credential`
- [ ] `未识别` 与待配凭据的行补传入口不可用，页面写明原因
- [ ] 批发的手动上传、单条重传、批量重传行为完全不变

## 风险提示（不影响本票开工，但影响上线使用）

补传是**向平台的真实申报**。外部系统用的是哪套 AppKey 尚未确认——若它已用另一个主体传过同一张单，本项目补传会在平台上造成**重复申报**。
这条是外部依赖（见 spec 的"外部依赖"表）；实现不阻塞，但**上线使用前需要用户确认**，未确认前建议只对"确定没被上传过"的单据补传。
