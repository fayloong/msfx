# 07: 手动上传页"所属企业"下拉 + 零售批量补传

- Type: task
- Status: done（2026-09-30）
- Blocked by: 06
- 关联：spec.md §11、docs/adr/0006-credential-as-routing-subject.md、docs/adr/0010-retail-request-parameter-mapping.md、docs/adr/0011-retail-retransmit-metadata-and-manual-trigger.md

## 要交付的行为

进入"手动上传"页，**页面最上方先选"所属企业"**，选定后显示该企业对应的表单内容：

- 选河药 → 就是现在的批发表单（日期 / 单号 / 单据类型 / 往来单位 / 追溯码）
- 选某家门店 → 该门店"待补传"单据的清单，勾选后**批量补传**，元数据全部自动带出，不用手填任何平台 ID

## 范围

**页面切换**

- 顶部加"所属企业"下拉，选项来自 `App\Enterprise::names()`
- 批发分支保持现状（含 xlsx 导入与模板下载——**只保留批发，不分叉模板**）
- 零售分支**不提供从零手工录入**，只显示该门店的待补传清单（单号 / 日期 / 单据类型 / 码数），可多选 → 选凭据 → 批量补传，逐条反馈结果
- 零售的批量需求由"采集 + 批量补传"覆盖，不必做零售 xlsx 导入

**后端**

- 拆独立端点（如 `api/manual_create_retail.php`），**不改造**现有 `manual_create.php` / `manual_import.php`：批发路径已在生产运行且有 `ent_list` 依赖，零售字段与接口完全不同，塞进同一文件会让两边都难读
- 批量与单条（工单 06）**共用**工单 05 的装配与工单 06 的落库逻辑，不要写第二份
- 追溯码上限按该接口取（`lsyd.uploadinoutbill` 10000 / `lsyd.uploadretail` 3500），不是全局 3500

- [x] 选门店：只列出**该门店**的待补传单据；批量补传逐条落 `upload_logs`、逐条反馈成功/失败
  - 清单：`api/manual_retail_tasks.php`（固定口径 该门店 + `source='retail'` + `待补传`，最多 200 条，只回码数不回追溯码）。实测徐洞分店：接口返回 10 条，与 `SELECT djbh ... WHERE company LIKE '%徐洞%'` 直查**逐条、逐序一致**（单号、日期、类型、码数全同）

## 实现笔记

- **共享接缝落在 `App\RetailRetransmit`（开工前问用户拍板）**：票面要求"批量与单条共用 06 的装配与落库逻辑"，但 06 的实现是 `tasks_retry_retail.php` 里的文件级函数，换个端点 include 不了（会执行它的认证/参数解析/exit）。故把 `retailRetransmit` / `uploadRetailSingle` / `updateRetailTaskStatus` 三个函数与四个常量整体提进类，两个端点各自只做「解析请求 + 流式输出」：
  - `tasks_retry_retail.php` 变薄壳，**行为字节级不变**（方法仍抛异常、端点仍发 `_final error`、异常仍不复位任务状态）
  - `tasks_batch_retry_retail.php` 循环调用同一份实现，**逐条 try/catch** 后继续下一条
- **偏离票面字面一处：批量端点叫 `tasks_batch_retry_retail.php`，不是票面举例的 `manual_create_retail.php`**。门店分支**不创建任何单据**（没有从零录入），它是"对已采集任务批量补传"，与 `tasks_retry_retail` 同族命名才诚实（"manual_create" 会让人以为页面能新建门店单据）
- **批量端点整批限同一门店**：入参带 `company`，逐条校验 id 归属，混入别家门店的 id **整批拒绝**（实测注入大湖分店 id 到新江分店的批次 → 400，报文点名是哪条单）；"一次请求里出现两家门店"没有正当来由，挑着传会掩盖调用方/页面的 bug
- **请求级校验 vs 逐条 fail-closed（纵深不是重复）**：非零售企业 / 无此凭据位 / 待配凭据在打开流之前用 400 一次说清（这类情形整批都发不出去，逐条报 N 遍没意义）；真正的关口仍是 `RetailRetransmit` 的逐条三关——页面与服务端各拦一次是有意的，页面只是显示层
- **日志来源值复用 `retail_retry`（开工前问用户拍板）**：先例是批发链路的 `tasks_retry` 与 `tasks_batch_retry` **都**写 `source='batch_retry'`——单条/批量是入口差异、不是数据差异。复用则三个页面的来源标签/徽标/下拉一个字都不用改，失败记录页那个"补传没成功"的唯一出口照旧覆盖两种入口
- **清单接口偏离票面举例**：票面建议"拆独立端点（如 api/manual_create_retail.php）"，实际拆出的是**读**端点 `api/manual_retail_tasks.php`（清单）+ **写**端点 `tasks_batch_retry_retail.php`（补传）。清单没有复用 `api/tasks.php`：那套是数据页的通用筛选（分页 20/页、参数繁多），而这里要的是"全量队列 + 码数"——用通用接口会在浏览器端做归属过滤，分页一错就漏单；**也没有**给它加 `company` 筛选参数，那属于工单 08 的范围（三数据页的筛选与导出）
- **码数由 SQL 数逗号得出，清单不回追溯码**：单张最多 1,718 个码 ≈ 34KB，几百张全量发到页面只是浪费带宽与 DOM。用 `CASE WHEN TRIM(trace_codes)='' THEN 0 ELSE LENGTH(...)-LENGTH(REPLACE(...))+1 END`（空串要单独判，否则会算成 1）
- **清单上限 200 条 + 明示截断**：待补传是队列，正常量级几十条；积压上千条时页面本身也点不动。命中上限时页面提示"仅列出最早的 N 条，处理后再刷新"，不静默截断
- **注（2026-09-30，票 10 推翻上面两条）**：清单已改为**分页**（每页 20 条，取代 200 条截断）并**随列表回 `trace_codes`**（供每行新增的"查看追溯码"按钮）。两条取舍在当时成立——它们针对的是"整个门店几百张一次性发到页面"；分页把量级降下来之后这个前提不再。200 条那条还有个当时没算到的代价：生产库最大的门店有 1,178 条待补传，截断下要看全得刷新 6 次。详见 `issues/10-retail-list-pagination-and-trace.md`。**本票正文（含"验收"里"最多 200 条，只回码数不回追溯码"那句实测记录）保留原样不改**——它记的是当时的真实状态
- **超出票面的必要外溢一处：四个页面补 `321`/`116` 的类型标签**（`upload_tasks` / `uploaded` / `failed` / `manual_upload` 的 `billTypeLabels`）。工单 03 起这两类零售单会入库，但四个页面的标签表都没有它们 → 页面上显示成 `-`；本票的清单是第一次把它们摆在操作者面前，顺手在四处各补一行（纯显示层，判定口径一字未动）
- **`formatProgress` 一处微调**：往来单位为空时回落到 `company`（零售进度行的 `ent_name` 恒为空——门店单据的对手方在源表里，而批发与零售共用同一个日志渲染函数）

## code-review 收口（2026-09-30，fixed point 17b978a）

- **ADR 0011 必须修订（两轴都指到，硬违规）**：该 ADR 决策 3 原文是"补传只人工、**只单条**…不做批量"，"排除的方案"里还列了"批量补传"——本票把它推翻了却一字未改，违反 CLAUDE.md 的文档同步规则。已在 ADR 0011 文首加**修订块**并就地标注被推翻的两处（沿用 ADR 0006 的修订惯例）；据实记下这是用户 2026-09-29 在 to-tickets 轮定的"补传入口做两处"，同时写明批量新加的两条边界（整批限同一门店、逐条隔离），以及"`104`/`203` 仍是欠账"
- **页面默认批发主体改走 `Enterprise::wholesaleSubject()`**（原实现是"取配置里的第一家批发企业"，绕开了 CLAUDE.md 指定的唯一入口；出现第二家批发企业时页面显示的主体与 `manual_create` 实际落库的主体不一致）。它不是恰好一家时页面**不替它猜**：显示一条警告写明"下拉里的批发企业未必是上传实际会用的主体"
- **进度行的形状收进单一处**（`RetailRetransmit::progressLine()` 私有 + `rejectedProgress()` 公开）：原先真实结果与"没能进平台"两种行的 7 个键在类里与批量端点各写一遍，改一处漏一处就会让前端渲染出半个空行
- **批量确认框对 `104`/`203` 显式警告**（ADR 0010 待确认项）：批量会把"方向可能弄反"的风险一次放大成一批，勾选里含调拨单时在二次确认里点名张数与原因。这是**警告不是拦阻**——单条入口同样暴露该风险，本票不改变已有的放行口径
- **删掉一处死代码**：页面 JS 里 `companyOptions` 声明后从未使用（分支切换靠下拉自身的 `data-type`）

**明确不采纳的审查意见（都是判断题，理由记下来备查）**：

- *"三关校验在类里与批量端点各写一遍"*：批量端点那三关是**请求级**的（整批都发不出去的情形用 400 一次说清：非零售企业 / 无此凭据位 / 待配凭据），seam 里的是**逐条**的（真正的可信边界）。合并的后果是待配凭据的门店一次批量刷出几十行一模一样的错误行——比多三行校验更糟。要改的话得先把"这类拒绝该报几次"定下来，本票不做
- *"凭据下拉的 usable/label 规则与 `$retailStores` 构建在 manual_upload 与 upload_tasks 各一份"*：既有形态（06 在任务页先落），两页共用的是 PHP 模板内的局部块，提取需要引入视图级共享助手——工单 08 要整体动这两个页面，留给它一并处理
- *"限速三常量与 `UploadService` 逐字重复"*、*"`total/success/failed` 键名不自带单位"*：前者是 06 已定的"刻意第二份"（不复用批发流水线，理由见 06 票）；后者在两端点各自的注释里写明了单位（单条按子单、批量按单据），前端汇总文案已按入口区分

## 未验到的部分（如实记录）
