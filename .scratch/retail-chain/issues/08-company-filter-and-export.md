# 08: 三数据页"所属企业"筛选与导出

- Type: task
- Status: done（2026-09-30）
- Blocked by: 03, 06
- 关联：spec.md §10、`src/RecordQuery.php`（本票把 4 份筛选拷贝收敛成它）

## 要交付的行为

三个数据页（上传任务 / 已上传 / 失败记录）都能按"所属企业"筛选，导出的 xlsx 里也带着这一列，
且**既有筛选组合的行为一点不变**。

## 范围

**三页**

- 表格加"所属企业"列（上传任务页在 03 已加、已上传页在 06 已加；本票补齐失败记录页并统一三页的呈现）
- 筛选条件加"所属企业"下拉，选项按 `company` 去重（同一门店不重复列）；一门店多套凭据时显示 `门店名（label）`
- 数据来源是 `App\Enterprise` 的企业枚举；`未识别` 也应能在下拉里筛出来

**注意：筛选逻辑在仓库里有 4 份拷贝**

`src/api/tasks.php`、`src/api/uploaded.php`、`src/api/failed.php`、`src/api/export.php` 各写一份 WHERE 构造（`export.php` 的注释自称"与列表 API 保持一致"，实际是第 4 份拷贝）；前端参数构造与列渲染各三份。
**四处都要改到、且语义一致**，否则会出现"页面筛得出来、导出筛不出来"这类漂移。

**导出**

- xlsx 加"所属企业"列 + 接收筛选参数
- **顺带修一个既有漂移**：`export.php` 的失败记录分支里 NOT EXISTS 无条件生效，缺了页面版 `failed.php` 里那句 `source = 'quantity_check' OR` 豁免——结果是**失败记录页看得见的数量对账告警，导出的 xlsx 里会被漏掉**。本票一并修掉

**编辑弹窗**

- 上传任务的编辑弹窗允许改"所属企业"，**需二次确认**（改企业意味着重传要走另一套凭据）
- 注意这个弹窗**在失败记录页被整体复制了一份**，两处都要改

**"关键词忽略默认日期范围"要一并适配**

- 三个页面都有"输入关键词时丢掉默认 7 天日期范围"的逻辑，**企业下拉不能被算作关键词**，否则会连带改变日期默认行为
- 三页的默认 7 天维度还不一致（上传任务页是单据日期、已上传/失败页是任务创建时间），改动时别把维度搞混

**不做**：仪表盘 4 个统计卡片本轮不按企业拆分（等零售接入稳定后再做）

## 实现说明（2026-09-30）

**结构决策：4 份筛选拷贝收敛成 1 份（开工前问用户拍板，选项 B）**

票面点出 4 份拷贝（`tasks` / `uploaded` / `failed` / `export` 各一份 WHERE 构造）后，本票唯一的结构fork是"四处各改一处"还是"合成共享构造器"。选了后者，新增 `src/RecordQuery.php`：三页的 WHERE / SELECT / ORDER 由 `build($type, $query)` 一处产出，四个入口各删 30-100 行改为调用它。

- **漂移因此从"改对了"变成"没有第二份可改错"**：export 的失败记录分支缺 `source = 'quantity_check' OR` 豁免那个 bug，不是"顺手也改了一下"，而是合并后它**物理上不存在了**——页面与导出跑的是同一段代码
- **`build()` 对未知类型抛异常而不是返回空条件**：失败页拿到空 WHERE 会把全表当失败记录吐出来，这是本仓最不该静默的那一处
- **条件与参数在同一段代码里成对追加**（`$add(条件, ...参数)` 闭包）：`?` 与 `$params` 的下标恒等。四处手写时这才是最容易错的地方，合并后它变成构造上的性质
- **前端仍是 3 份各自编辑**（未选选项 C）：项目没有打包器，视图是 PHP 模板内联 `<script>`，共享要新增 `public/js/` 资源与加载路径，超出票面"四处都要改到"的范围
- **`RecordQuery` 不读超全局**：参数由调用方传入，故能对着生产库直接构造任意筛选组合核对（见下"验证证据"）

**编辑任务改"所属企业"必须连带重设 `credential`**

`UploadService::resolveContext` 按 `(company, credential)` 两列取凭据。未识别行的 `credential` 是 NULL，所以"只改 company 不改 credential"会让本功能**最主要的使用场景**（把未识别行指派给正确门店）等于没做——守卫会以"取不到可用凭据"拒传。故：

- `Enterprise` 新增公开口 `defaultCredentialKey(企业名)`（primary 凭据键），PUT 改 company 时据此重设 credential
- 企业不在配置中（含 `未识别`）时它返回 null，照常落库——**不在这里做企业白名单**：守卫刻意在 `UploadService` 而非调用方（"只把 SQL 写对护不住直接调用的脚本"），这里再复制一份白名单就违反了那个决定。实测该行落 null 后守卫明确拒传且报文点名是哪个企业
- `company` 键**缺席**时两列都不动（未刷新的页面/旧调用方不会被误清空）；传空串则 400 并且什么都不写

**票面"一门店多套凭据时下拉显示 `门店名（label）`"当前无可观察效果**：`config/enterprises.php` 16 家企业每家恰好一个凭据位 `main`，生产库 `(company, credential)` 分组也是清一色 `main`。按规格前半句"按 `company` 去重"实现，值就是 `company` 列的值；未识别也在下拉里（它不是一个企业，但确实是 `company` 列的一个取值）

**导出列插在"单据类型"之后**（与三页表格的列顺序一致），不是追加到末尾——票面要求的是"xlsx 里也带着这一列"，位置取与页面一致

**票面外的一处事实记录（未处理）**：核对时发现 `upload_tasks` 有 20 个 `(company, djbh)` 键存在重复行（共超额 21 行，全部 `已处理`，`cron`/`manual` 混合来源）。去重键在文档里写作唯一，但库里没有唯一约束。与本票改动无关，未处理

## 验证证据

- **离线等价（4 份拷贝合并前后）**：把旧的手写 WHERE 逻辑逐字抄进临时脚本，对 34 组筛选组合（三页各自的单号/往来单位/关键词/状态/来源/两类日期范围及其组合）逐组比对新旧 `COUNT(*)`，**全部相同**；`company` 维度另验完整划分（16 家企业 + 未识别的计数之和 == 无条件计数，三表都成立）
- **漂移专项（票面验收第 4 条）**：生产库当前 **0 条** `quantity_check` 记录，活数据上验不出来。故在**临时库副本**（`SQLite3::backup`，源库只读）上给一张"已有上传成功记录"的单号造一条合成告警 → 失败记录页 8 条 / 旧导出 7 条（被 NOT EXISTS 吞掉）/ 合并后的导出 8 条
- **真实 HTTP（票面验收第 1、3 条）**：14 组筛选组合，页面 API 的 `total` 与同源 WHERE 直查库的行数**逐组相等**；三类导出与页面按 `(所属企业, 去重后缀单号)` 做**集合相等**比对，14 组全部相同（导出会因追溯码超 32000 字符而拆行，故行数可多于单据数——如 42148 张单导出 42180 行）
- **关键词全库检索（票面验收第 2 条）**：三页同一关键词，不传日期参数时命中全库（7899 / 7899 / 2 条），带上 7 天默认范围时为 0 条——全库检索确实生效。前端侧另核对三页的"是否忽略默认日期"表达式只引用单号与往来单位，企业下拉未被算作关键词
- **编辑弹窗落库（票面验收第 5 条）**：在**项目临时副本 + 独立 PHP 服务**（127.0.0.1:8199）上验，生产库只读。未识别 → 门店：`company` 与 `credential` 双列落库（credential 变为该门店的 `main`）；不带 `company` 键：只动其余字段；`company` 传空：400 且库中不变；未知企业：落库为 NULL 且守卫拒传
