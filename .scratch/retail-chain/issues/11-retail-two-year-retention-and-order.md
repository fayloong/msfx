## 范围（用户在两处决策点上的选择）

- **落点＝采集入口 + 定期清理**（用户 2026-09-30 选定）。只删一次不够——**存量会随时间自然过期**：今天合法的单据两年后就不合法了；不加清理的话清单逐日累积传不上去的单，规则上线当天做的事三个月后又得重做一遍
- **失败记录页那条 2023 年的补传失败日志（id=44298）保留**：它是真实发生过的事故记录，且 `cleanup_logs` 已按 `created_at` 在 3 个月后自动清掉，无需特殊处理。本票只动 `upload_tasks`，不碰 `upload_logs`

## 实现

**单一事实源 `App\RetailRetention`**：`YEARS = 2` + `cutoffDate()`（相对今天滚动，回 `YYYY-MM-DD`；**早于**它即超期，截止日当天保留）。两个调用点共用——各写各的年数会让超期数据滞留（或采进来又被立刻删），把本规则要解决的问题重新造出来。闰日会溢出（`2024-02-29` → `2022-03-01`），方向恰好安全：宁可多删一天，也不留下平台必拒的那一天。

**入口 `scripts/fetch_bills_retail.php`**：SQL 始终带 `bill_time >= ?`——`--all` 靠它截断（其语义由"全部历史"变为"最近 2 年"）、cron 的当日采集天然满足、显式日期是同一条下限的纵深。显式指定一个早于下限的日期时**直接拒绝并退出 1**（在连源库之前）：静默采回 0 条会被读成"那天真没单据"。

**出口 `scripts/cleanup_logs.php`**：新增第 3 条清理 `DELETE FROM upload_tasks WHERE source = 'retail' AND rq < ?`，判据是 **`rq` 单据日期**——与上面两条（按 `created_at` / `updated_at` 判"记录存了多久"）**口径不同**：一张昨天才采进来的 2023 年单据，昨天就该清掉。**不限任务状态**（保留期是对"门店数据"整体的规定，与用户原话一致；已处理的零售行本就被第 2 条在 3 个月内清掉，两者只是先后）。

**排序 `src/api/manual_retail_tasks.php`**：`ORDER BY rq DESC, id DESC`（原为 `rq ASC, id ASC`）。`rq` 是 TEXT 存 `YYYY-MM-DD`，字符串序即日期序；同日期内按 id 倒序。翻页/勾选集/末页回退等逻辑不受影响（它们与顺序无关）。

## 实现笔记

- **为什么要有 `App\RetailRetention` 这个类**：它只回答一个问题——"门店数据保留多久、截止哪天"。看着像为一行 `strtotime` 建档，但两处调用点**必须同步**：入口按 2 年、出口按 3 年，超期数据会在清单里滞留；入口按 3 年、出口按 2 年，则采进来当天被删。这是"违反了就静默出错"的类型（与 `Enterprise::wholesaleSubject()` 拒绝"不恰好一家"同一条理由），故收敛为单一事实源，而不是各写一份再加注释互相指认
- **清理的判据是 `rq` 不是 `created_at`**：`cleanup_logs` 原有两条都按时间戳判"记录存了多久"，这条判的是**单据本身的日期**。差别在采集 `--all` 时最明显——一张 2023 年的单据是**今天**才采进来的（`created_at` 崭新），但它昨天就该过期了
- **排序改动没有连带影响**：清单的翻页、跨页勾选（`retailSelectedIds`）、末页被传空自动回退（`page > total_pages`）都与顺序无关，本票只换 `ORDER BY`。票 10 实测过的"翻页不重不漏"在倒序下重新验了一遍（见验收）
- **`--all` 的语义变了**：从"全部历史快照"变为"最近 2 年的快照"。票 03 回填的生产首跑数据（`--all` 新增 6258 条）是旧口径下的数字，重跑会少一些——不是回归

## 未验到的部分（如实记录）

- **浏览器端交互未真机验收**：排序是接口层实测的（真实 HTTP + 真实登录），但页面表格、翻页按钮、勾选在倒序下的观感没有真机点过（本机没有浏览器）。首次真机使用时应看一眼：第一页是否确实是最新的单据、末页是否是最早的
- **平台对"正好 2 年"当天的判定未知**：采集与清理都以 `rq < cutoff` 为界，即**截止日当天保留**。若平台严格拒绝"满 2 年当天"的单据，边界那一天会多留一天——量级为个位数，且次日即被清理，未做特殊处理
