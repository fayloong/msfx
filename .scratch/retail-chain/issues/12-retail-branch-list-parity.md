## 要交付的行为

用户 2026-09-30 原话：

> 移植上传任务界面的功能到门店的批量补传界面：1.筛选功能，2.导出xlsx文件功能，3.刷新按钮，4.批量删除按钮，5.增加字段："补传任务创建时间"、操作(编辑、删除、重传)

进入手动上传页并选门店后，门店分支要具备上传任务页那套能力：

1. **筛选**：单号、任务状态、响应状态、单据日期、补传任务创建时间

## 用户拍板的四个决策（2026-09-30）

| 决策点 | 选择 | 后果 |
|--------|------|------|
| 清单范围 | **可切「已处理/全部」**，默认仍「待补传」 | 推翻 07 票"固定口径：该门店 + source=retail + task_status=待补传"里的第三条。补传失败的单翻 `已处理` 后从待补传清单消失（ADR 0011），能切过去才在本页重传，不必再去上传任务页按企业筛 |
| 单据日期默认值 | **不设默认（空=全部）** | 待补传是积压队列，默认藏起 7 天前的单会让人误读成"这家店没单了"。也与现状一致（现在没有日期筛选）。上传任务页那套"关键词时忽略默认 7 天"的补偿逻辑因此**不需要**搬过来 |
| 编辑字段 | **日期、单据类型、单号、追溯码** | 不含"往来单位"（门店单的对手方是源表里的平台 ID，本就没有名称）与"所属企业"（门店分支里改它会把这行挪出当前清单）。`from_user_id`/`to_user_id`/`physic_type` 按 **ADR 0011** 不接受人工录入 |
| 导出形态 | **与门店清单表格对齐** | 列：单号 / 单据日期 / 单据类型 / 追溯码 / 码数 / 补传任务创建时间 / 任务状态 / 响应状态；文件名 `门店补传_YYYY-MM-DD.xlsx` |

## 范围

### 后端

**`src/RecordQuery.php` —— 新增 `TYPE_RETAIL_TASKS`**

门店清单是**第 4 个数据页**，筛选构造同样必须只有一份实现。它复用上传任务页那套参数名（`date_from/to` 指单据日期、`created_from/to` 指任务创建时间），额外带两条**固定口径**：

- `source = 'retail'` 写死（这个页面就是门店采集单，不由调用方给）
- `company = ?` **必填**：缺 company 直接抛 `InvalidArgumentException`，不静默退化成"全部门店的单据混在一条清单里"（与既有那条"未知类型不静默返回空条件"同一个理由）
- 排序 `rq DESC, id DESC`（11 票用户指定的倒序；上传任务页是 `id DESC`，两者刻意不同）

列表 API 与导出**共用这一个 build()**——"导出的行数与页面一致"是构造上的性质，不是靠人核对（08 票已因拷贝漂移吃过一次）。

**`src/api/manual_retail_tasks.php`** —— 改走 `RecordQuery::build(TYPE_RETAIL_TASKS, $_GET)`，保留：登录校验、`Enterprise::isRetail()` 校验、`page_num` 分页（每页 20）、`code_count` 与 `bill_type` 归一化。响应形状不变（页面 JS 依赖 `data/total/page/per_page/total_pages`）。

**`src/api/export.php`** —— 加 `retail_tasks` 分支（列与文件名见上）。`type` 白名单直接来自 `RecordQuery::TYPES`，故加了常量即被认。门店导出在打开流之前先校验 `company` 是**零售企业**（`Enterprise::isRetail`），不满足直接 400 并指名当前值——缺值的 fail-closed 由 `RecordQuery` 的抛异常兜底，端点这层多挡的是「给了个别的企业名」。

## code-review 收口（2026-09-30，fixed point f7d026e）

**改了**

## 实现笔记

- **门店清单成为 `RecordQuery` 的第 4 类，而不是在端点里再写一份 WHERE**：本仓已经因为"四处各写一份"漂移过一次（08 票：失败页看得见的告警导出的文件里没有）。门店清单与上传任务页**同表同列同参数名**，所以只差三条：`source='retail'` 写死、`company` 必填、排序 `rq DESC, id DESC`。这三条写在类里，列表与导出共用——"导出的行数与页面一致"因此是构造上的性质（已用四组筛选的行数比对核实）
- **`company` 必填是刻意 fail-closed**：缺了它构造出来的是"全部门店混成一条清单"，而导出会把这份错误数据写成一份**看不出毛病**的 xlsx。这与类里既有的"未知类型不静默返回空条件"是同一条理由。导出端点把它收成 400，不是 500
- **`task_status` 从固定口径改成筛选维度（推翻 07 票"固定待补传"）**：补传失败会把任务翻 `已处理` 并从待补传里消失（ADR 0011），于是那批单在本页**没有出口**——只能去上传任务页按企业筛。默认仍是 `待补传`（与上传任务页默认"等待上传"同构），切到"已处理"是补救路径
- **两个日期选择器都不设默认值**（与上传任务页不同）：待补传是积压队列，默认藏起 7 天前的单会被读成"这家店没单了"。**代价是放弃了"关键词时忽略默认范围"那套补偿逻辑**——那个逻辑存在的唯一理由是默认范围，没有默认就没有这个问题
- **编辑只开四个字段**：`from_user_id`/`to_user_id`/`physic_type` 按 ADR 0011 不接受人工录入（手工录平台 ID 几乎必然出错、录错了当时察觉不了）；"往来单位"门店单本就没有值；"所属企业"在本分支里改会把这一行挪出当前清单——那不是"编辑这张单"的语义。服务端 PUT 会把未送的 `ent_name` 写成空串，对零售行等于原值
- **行内按钮按状态换名**：`待补传` 的行叫"补传"，`已处理` 的叫"重传"——同一个端点、同一份实现，只是后者是再来一次。**没有**给"已申报成功"的行禁用重传（与上传任务页口径一致），改为在批量确认框里点名；这是警告不是拦阻
- **批量删除的确认多一句**："删除只作用于本地任务行：该单据若仍未被外部系统上传、且覆盖它那个日期的采集再次运行，它会被重新采集入库"——`(company, djbh)` 去重只在 `upload_tasks`/`upload_logs` 里生效，源库那边没有"已删"的概念。这句话是给"删了就永远没了"这个误解准备的
- **新增 `tests/record_query_test.php`（本票唯一的测试接缝）**：测的是既有的纯函数类，不是新开的业务接缝。理由是这次改动动的是 `tasks/uploaded/failed/export` **四个入口共用的那段代码**，而它此前没有测试——回归风险正好落在这里，而且它无 IO、可在不碰 Web 与库的情况下断言。断言钉的是"漂移了就会出事"的性质（固定口径、参数名→列的映射、`?` 与 params 数量恒等），不是 SQL 字面量
- **交付后仍未做的事**：`104`/`203` 的 from/to 语义（ADR 0010）依旧待外部系统工程师确认，本票只在确认框里继续点名；`from_user_id` 在编辑弹窗里依旧不可见、不可改
