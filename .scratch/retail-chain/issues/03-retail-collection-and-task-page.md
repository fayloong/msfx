## 要交付的行为

运维跑一次采集（或 cron 到点），指定日期的门店单据出现在"上传任务"页上，**每条都带着归属的门店名**；
归属不到的显示"未识别"且一眼看得出来；这些记录不会被任何自动上传链路取走。

## 范围

**新脚本 `scripts/fetch_bills_retail.php`**（命名与位置对齐 `fetch_bills.php`）

- 用 `App\SqlSrvHelper` 现有连接**直接查 4 段式链接服务器名** `dyt.msfx.dbo.zsm_ls` / `zsm_ls_code`（实测可用，全表 `COUNT(*)` 638ms），不需要新连接封装
- 两步 SQL，先头后码：
  - **头**：必须先按 `bill_code` 去重——`321` 存在 14 列值全同的完全重复行（同一单号最多 120 行、无任何区分列），不去重会让下一步按单号取码时追溯码被放大最多 120 倍
  - `bill_time` 是 `varchar(10)` 的 `YYYY-MM-DD`（不是 datetime），字符串范围比较即日期比较
  - 单据类型写死 `104`/`203`/`321`/`116` 四种（`999` 语义未明，用户判定不采）
  - **码**：按单号批量取，`group by bill_code, trace_codes` + `order by` 保证拼接结果确定（一码一行，表里没有排序列且 `bs` 恒为 1）
- 参考 SQL 在 `config/sql.php` 的 `$get_up_task_retail` 是调试残留，**别照抄**（写死单一 `bill_type='203'`、无日期范围、无去重）
- 脚本失败（源库不可用）非零退出且**不写库**

**门店认领**：走 `App\Enterprise::claim()`（工单 01 已实现并有测试覆盖），不要在本票里另写一套匹配

- 按单据类型取 ID 列命中该门店登记过的任一平台 ID（`321`/`116` → `from_user_id`，`104`/`203` → `to_user_id`）
- ID 为空或未命中 → 回退 `oper_ic_name` 与配置门店名精确相等
- 都不命中 → `company='未识别'`，**照常入库**（丢单比错标更危险，必须能看见"有单没被认领"）
- `claim()` 返回 `name_unmatched` 时记一条 JSONL 警告，**不改判定**（ID 认到了、源库名字却对不上任何门店 → 疑似错名/改名/已关店）

**落库**

- `task_status='待补传'`（**不复用 `等待上传`**，语义是"cron 会来取走并上传"）、`source='retail'`、`company` 取认领结果、`credential` 取 `claim()` 返回的 primary 凭据键（**凭据位已声明即预填该键**——密钥还没到手的"待配凭据"门店同样有键，页面据 `credentialConfigured()` 禁用补传；仅当配置结构里连凭据位都没声明时才为 null，见 `tests/enterprise_config_test.php` 用例 3/7）
- `ent_name`（往来单位）**零售链路用不到**：零售单据的对手方 ID 直接来自源表的 `from_user_id` / `to_user_id`，
  **不查 `ent_list`、也不需要往来单位名称**（`ent_list` 是批发 kyt 接口为了把往来单位名换成 `ent_id` 才有的缓存）。这一列留空即可
- 幂等：按 `(company, djbh)` 去重，重复跑不产生新行
- **不设计数门卫**：`data/fetch_bill_counter.json` 那套是为"重视图查询空转"设计的；零售是一次 ~0.6s 的全表扫 + 去重保证幂等，门卫只省 0.6s 却多一份要维护的状态文件
- **不需要拆单**：实测单张单据码数上限 1,718 < 3,500

**页面**

- 上传任务页表格加"所属企业"列；`未识别` 的行显著标记
- **零售行的重传按钮关闭**（隐藏或禁用）：零售补传入口在工单 06 才落地，在此之前点它只会撞上工单 02 设的守卫并报错

**调度**

- 零售采集不调平台 API，无 8-20 点限流约束；加 cron 条目与 `fetch_bills.php` 同频，并在 `CLAUDE.md` 的 cron 时间表补一行（文档随本票同一次提交）

## 实现笔记（超出票面的必要处理）

- **cron 条目尚未安装**：本会话的权限策略拒绝了改 root crontab（新增 root 级常驻任务需用户显式批准）。脚本、文档条目、建议时间都已就绪，人工执行 `crontab -e` 加上表那一行即可（`CLAUDE.md` 的 cron 时间表已注明"尚未写入"）
- **建议条目错开 5 分钟**：`5,35 0,1,2,3,8-23 * * *`（同频、非同刻）。验收期间实测到一次 Web 端 500 —— `/var/log/php-fpm/mashangfangxin-error.log` 00:01:56 `Uncaught Exception: database is locked`（`Database.php:15` 的 `PRAGMA journal_mode=WAL`），撞在 `fetch_bills` 00:00 那轮的写库窗口上：该 PRAGMA 在 `busyTimeout(30000)` **之前**执行，没有 busy 兜底。这是**既有**问题（公共路径、超出本票范围，未改），但零售采集若与批发同刻写会把这个窗口撞得更频繁
- **页面多加了两个下拉选项**（任务状态 `待补传`、来源 `零售采集`）与 `sourceLabels`/`sourceBadges` 的 retail 标签。票面只要求"所属企业列 + 未识别标记 + 零售行禁用重传"，但缺这两项时：门店单据在页面默认筛选（`等待上传`）下根本看不见，"要交付的行为"落不了地；来源列会显示裸英文 `retail` 配灰徽标
- **幂等去重同时看 `upload_logs`**（已上传成功/单据重复的不再入队），对齐 `fetch_bills.php` 的既有口径：人工补传成功后任务行若被删，重采集不该再入队——那是重复申报的入口
- **`SqlSrvHelper::query` 返回空数组无法区分"真没单据"与"查询失败"**，脚本改用 `getLastError()` 判别（`query()` 失败时它非 null），否则源库不可用会被误当成"今天没单"静默通过
- **源库两步查询全部读完才开始写库**：任何一步失败都还没碰 SQLite，"失败不写库"因此是结构性保证而非事后回滚
- **未新增测试接缝**（用户明确约束）：采集 SQL 的去重与码拼接靠人工验收（上面的对数 + 幂等 + 回源核对），没有为可测性把采集拆出一层纯函数

## 2026-09-30 测试阶段口径变更（票面外，用户指定；本票的验收记录仍然有效，但描述的是变更前的口径）

采集 SQL 改成**单条** `zsm_ls LEFT JOIN zsm_ls_code` + **`NOT EXISTS(update_state)` 过滤** + **无 `bill_time` 日期过滤**——
票面写的"两步 SQL（先头后码）"与 ADR 0007 的"去掉 update_state 过滤"**双双被推翻，仅限测试阶段**（回收条件见 ADR 0007 修订注）。

- **去重挪到 PHP 侧**：`321` 的 14 列全同重复行会让连接结果放大最多 120 倍，故追溯码用关联数组去重（保序）、单据头字段取首次出现的行。票面"头必须先按 `bill_code` 去重"这个**结论仍成立**，只是执行位置从 SQL 换成 PHP
- **顺带补了 `physic_type` 列**：照抄来的老 SQL 里没有它，而补传装配要 `physicType`（ADR 0010）——漏掉的话 `104`/`203` 的单会被 SDK 的 `check()` 拒掉且永远补不出去
- **必须 LEFT JOIN 而非内连接**：没码的单也要采，它是待补传队列里值得看见的一条
- **新增 `SqlSrvHelper::queryEach()`**（回调式逐行消费）：原 `query()` 把结果全攒成数组返回，全表连接可能到数十万行，会撞上 CLI 的 `memory_limit=128M`
- **"失败不写库"的判据换了一处**：单条查询下由 `queryEach()` 返回 `false`（配 `getLastError()`）区分"真没单据"与"查询失败"，不再是"空数组 + lastError"
- **未验收**：本变更提交时未在生产库跑过采集（会向生产 SQLite 批量插入），验收记录待补
