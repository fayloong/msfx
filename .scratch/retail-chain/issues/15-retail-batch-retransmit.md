# 15: 上传任务页的「批量重传」支持门店单（按行分流）

- Type: task
- Status: todo
- Blocked by: 无（14 已完成）
- 关联：`docs/adr/0011`（补传的人工触发与失败也翻已处理）、`docs/adr/0012`（凭据按门店取）、`docs/adr/0015`（撤清单的连带后果，本票补的就是它）、`CLAUDE.md`「手动上传」末尾那条**已知缺口**（本票做成后要把它删掉）、`src/api/tasks_batch_retry.php`、`src/RetailRetransmit.php`

## 背景：这条缺口是怎么来的

工单 14（2026-10-01）按用户要求撤掉了手动上传页的"门店补传清单"——它同时是门店单**批量补传**的入口。
上传任务页那个"批量重传"看起来能顶上，实际不能：`api/tasks_batch_retry.php` 把选中的行**一股脑**交给
`UploadService`，而它的守卫（`resolveContext`）对非批发 kyt 的路由**整批拒绝**——批里只要混进一条门店单，
整批都传不出去（fail-closed 是刻意的，见 CLAUDE.md「上传守卫」）。结果：**门店单现在只能逐条补传**。

## 要交付的行为

上传任务页勾选若干行 →「批量重传」→ 端点**按行分流**：

- `source = 'retail'` 的行 → `App\RetailRetransmit`（lsyd 链路），**逐条隔离**：某条被拒（未识别 / 待配凭据 /
  无路由 / 装配缺项）或已不存在只影响它自己，其余照常传
- 其余行 → 现有 `UploadService` 那条路，**行为一字不变**（含它的"任一不合规即整批拒绝"）

页面侧：

- 确认框恢复三处点名（原门店清单版有，撤清单时一并没了）：**补传不可逆**、批里含 `104`/`203`（ADR 0010 的
  发货/收货语义待外部系统工程师确认，一次放大成一批）、批里含**已申报成功**的行（切到"已处理/已上传"
  才选得到；重传是真实调用，平台多半回"单据重复"——**是警告不是拦阻**）
- 进度与汇总沿用既有形状：零售那部分按**单据**计，批发那部分按**子单**计（`RetailRetransmit` 的进度行
  与 `UploadService` 的同形，前端不必分叉）

## 用户拍板的两个决策（2026-10-01）

| 决策点 | 选择 | 后果 |
|--------|------|------|
| "这一行是门店单"的判据 | **`source = 'retail'`** | 覆盖采集来的与手工建的（两者共用这一个值，见 ADR 0015）；`未识别` 行也在内——它们会被 `RetailRetransmit` 的关闸**逐条**拒掉（消息是"「未识别」不是零售企业"），不再像现在这样把整批带下水。按企业类型判（`Enterprise::isRetail`）会漏掉 `未识别` 行，且拦不住"门店行被改错所属企业"这类脏数据 |
| 跨门店勾选 | **允许**，每行按自己的 `company` 取凭据 | 勾选框在上传任务页（全部企业混在一张表），跨店勾选是自然操作。旧版"整批限同一门店"是当时清单属于一家店的产物，在新位置没有安全上的理由——凭据仍按行取，不存在"拿甲店凭据传乙店单"的路径 |

## 范围

### `src/api/tasks_batch_retry.php`（主要改动）

1. 取到行之后**分流**：`$row['source'] === 'retail'` 的一份、其余一份
2. 批发那份：原样调用 `UploadService::upload()`（映射、异常复位逻辑都不动）
3. 零售那份：逐行 `(new RetailRetransmit())->retransmit($task, $db, $onProgress)`，**逐条 try/catch**
   （与已撤的批量补传同一个口径：一条坏单不该让整批停摆）
4. 两部分的进度行都打到**同一个 NDJSON 流**上；`_final` 的汇总口径要么按"批发子单 + 零售单据"合并给出，
   要么分两段给——**取哪种在实现时定一次并写进注释**，别让前端猜
5. ⚠️ **异常复位只作用于批发那批**：现在的 catch 分支会把**整批**任务状态恢复成调用前的样子；
   零售行按 ADR 0011 的口径**不复位**（任务行只在平台调用之后被写，复位会把结果抹成 NULL）

### `src/views/upload_tasks.php`

- 批量重传的确认框补三处点名（文案可照抄 14 票删掉的那份，git 历史里有）
- 其余不动——门店行的单条"补传"按钮、企业徽标、筛选都不受影响

## 不做

- **不动批发那侧的语义**：`UploadService` 的"任一不合规整批拒绝"是刻意的（混批"传一半才报错"更难收拾），
  本票不把它改成逐条隔离
- **不改单条入口**（`tasks_retry.php` / `tasks_retry_retail.php`）与手动上传页
- **不真传平台**：见下

## 验收

**环境**：项目副本（`sqlite3 data/msfx.db ".backup …"` 到 `/tmp`）+ `php -S`，平台侧用**离线桩**
（副本里把 `TopClient::$gatewayUrl` 指向本机桩，桩按 `method` 回平台形状的 XML 并记录出网参数；
仓库里的 vendored SDK 不动）。做法与 14 票同，见 `verify-write-paths-on-a-staged-copy` 的记法/工单 14 的验收节。
**批量补传是不可逆的真实申报：验收一律不真传**，桩的应答要如实写成"桩的应答 ≠ 真传"。

- [ ] 混批（批发行 + 门店行）一次提交：两边的行都到达各自的链路（桩记录的 `method` 可分辨
      `drug.kyt.*` 与 `drugtrace.top.lsyd.*`），且**每行的凭据是它自己那家企业的**（桩记录里核对）
- [ ] 跨门店：一批里两家门店的零售行各自用自己的凭据传出（桩记录里两个 AppKey 可分辨）
- [ ] 逐条隔离：批里放一条待配凭据 / `未识别` 的零售行 → 它单独被拒并给出原因，**其余零售行照常传**
- [ ] 批发侧行为不变：纯批发批次的入参、进度、汇总、异常复位与改动前逐条一致
- [ ] 零售行在异常时不复位（构造一次"零售那部分抛异常"的场景，核对任务行 `updated_at` 未被改动）
- [ ] 页面确认框对含 `104`/`203`、含已申报成功的批分别点名（静态自检 + 用户浏览器实测）
- [ ] 全部测试通过；**客户端交互没在浏览器里跑过**（部署机没有 JS 引擎）——按惯例如实标注
- [ ] 不新增测试接缝（分流是一行的判据、链路本身是 IO），靠上面这些端到端验收
