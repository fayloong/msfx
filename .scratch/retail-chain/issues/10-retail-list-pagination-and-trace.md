## 实现笔记

- **清单重新随列表回 `trace_codes`（推翻 07 票的一条决策）**：07 的取舍是"只回码数，单张最多 34KB，全量发到页面浪费"——那针对的是"整个门店几百张一次性发"，**分页之后这个前提不成立**（一页 20 条最坏约 680KB）。另一条路是点击时按 id 再拉一次，代价是页面上多一套加载态与失败态要维护，省下的只有当页这点带宽。取舍记在接口文件头注释里
- **分页取代 200 条截断（推翻 07 票的另一条决策）**：截断是把"看不全"的后果推给操作者（页面只能提示"仅列出最早的 N 条，处理后再刷新"），分页是把它解决掉。生产库里最大的门店有 1,178 条待补传，截断下要刷新 6 次才能看全
- **`retailRows` 降级为函数内局部变量**：它作为模块级状态存在的最后一个理由是给补传确认框回查单据类型，本票改用 `retailRowIndex` 之后就没有第二个消费者了
- **分页渲染函数是照搬而非提取**：两个页面的脚本各自内联在 IIFE 里，仓库没有共享 JS 文件；既有形态里 `streamFetch` / `appendLog` / `formatProgress` / `esc` 也都是各一份。真要提取得先引入视图级共享 JS 的机制，不属本票范围

**Spec 轴提的三处，已改两处**：

- **翻页会静默重置凭据（Spec 轴指出，真问题，已修）**：`loadRetailTasks` 每次调用都无条件重建凭据下拉的 options，而分页之后**翻页也会走这个函数**——用户选的凭据会被退回第一项。当前配置每家门店只有一个凭据位（`main`），所以观察不到；但那是配置的巧合、不是代码的性质，多套凭据时它就是"翻一页换一套申报主体"。修法：重建前记下当前选择，重建后仍可用就留（换门店时同名凭据位保留也不违和——选的是"哪套授权"）
- **弹窗计数加了 `.filter(Boolean)`，与参照实现不一致（已改）**：参照是裸 `split(',')`。裸 split 还与列表"码数"列（SQL 数逗号 +1）同口径，同一行的两处数字不会打架；带 filter 时尾逗号会让两处差 1
- **"共 N 条待补传"与分页条底部"共 N 条，第 X/Y 页"重复显示同一总数（不采纳）**：卡片头那处是 07 票既有的 UI，且它是分页条渲染失败时唯一的计数出口；分页条那处是"第几页/共几页"的上下文，两者语义不同。拆开的收益不抵改动既有 UI 的风险

**明确不采纳的审查意见（判断题，理由记下来备查）**：

- *"`getPageNumbers` 与分页渲染在上传任务 / 已上传 / 失败记录 / 手动上传四处重复，追溯码弹窗与复制也是第 4 份拷贝"*：属实（`getPageNumbers` 四个视图各一份，本票是第 4 份）。收敛的前提是引入视图级共享 JS（`public/assets/js/`，nginx 能直接服务 `.js`），那要同时改四个页面、把三个既有页面的分页行为一起拖进回归面——超出本票"给门店清单加分页"的范围。仓库对这类重复的既有态度本就是分场景的：`RecordQuery` 那 4 份**后端**筛选拷贝被收敛（它会直接造成"页面筛得出、导出筛不出"），而 `dashboard` 那张卡片被明确留作"第 5 份拷贝，本轮不动"。本票按后者处理，这份重复留给一次专门的前端资源整理
- *"`btn-copy-trace` 与 `btn-copy-log` 同文件内是第二份复制技俩"*：与既有形态一致——上传任务页里这两段也各有一份，本票只是把参照实现搬了过来。同上
- *"`PER_PAGE = 20` 与 `api/tasks.php` 的 `$perPage = 20` 没有共同来源"*：两个端点分属两个页面、各自独立演进，为一个整数引入共享常量类不划算；两边的注释互相指认，取数口径写在各自注释里
