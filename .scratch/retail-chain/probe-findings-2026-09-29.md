# 零售源库探测结论（`zsm_ls` / `zsm_ls_code`）

**日期**：2026-09-29　**方式**：`SqlSrvHelper` 只读探测（`dyt` 链接服务器 → `msfx` 库），全程 SELECT，未写任何表
**脱敏**：门店平台 ID 的**具体值不入仓**（属凭据级信息），将从探测结果直接生成到 `config/enterprises.local.php`（gitignore）。本文件只记录结论与前缀。

---

## 开放问题 C：连接可复用 ✓

同一条 `SqlSrvHelper` 连接（`192.168.2.133` / `hyyy_zyscm`）可**直接查询 4 段式链接服务器名** `dyt.msfx.dbo.zsm_ls`，无需新增连接封装。`SELECT COUNT(*)`（全表 119,522 行）实测 **638ms**。

## 开放问题 D：结构与索引 ✓

**规模**：`zsm_ls` 119,522 行；`zsm_ls_code` 298,430 行。

| zsm_ls 列 | 类型 | 说明 |
|---|---|---|
| bill_code | varchar(50) | 单号 |
| bill_time | **varchar(10)** | **纯日期 `YYYY-MM-DD`**（全表 119,522 行长度均为 10），**非 datetime** |
| bill_type | int | 见下方实际分布 |
| physic_type | int | 全表恒为 `3` |
| from_user_id | varchar(50) | **门店平台 ID（出库方向）** |
| to_user_id | varchar(50) | **门店平台 ID（入库方向）** |
| ref_ent_id | varchar(50) | **全表单一值**——中央主体，**不是门店的** |
| oper_ic_name | varchar(300) | 机构名（**仅 104/203/999 有值，321/116 全空**） |
| states / relation_states | int | **全表恒为 0**——无可用状态过滤 |
| entid | varchar(20) | 全表单一值（中央主体） |
| erpbillcode / customer_id / user_tel | varchar | 未探查（不急） |

| zsm_ls_code 列 | 类型 | 说明 |
|---|---|---|
| bill_code | varchar(500) | |
| trace_codes | varchar(200) | **每行只存 1 个码**（实测最长 20 字符）——列名误导 |
| entid / relation_states / bs | varchar | `bs` 全表恒为 `1` |

**索引**：
- `zsm_ls`：`(bill_code, bill_type, from_user_id, to_user_id, ref_ent_id)`
- `zsm_ls_code`：`(bill_code, trace_codes, entid, relation_states)`
- **`bill_time` 无索引** → 按日期范围采集为全表扫描（~0.6s，可接受）

**关键否定结论**：**两张表都没有任何数量列** → 零售数量对账在源库侧没有本地基线（spec 的 Out of Scope 判定成立，且原因比"暂时没找到办法"更硬）。

## 与 spec 冲突的 6 条事实

1. **门店认领键错**（最重要）。spec §6 定"`oper_ic_name` 与配置门店名精确相等"，但 `oper_ic_name` 对 321/116（**101,288 行，84.7%**）**全空**；只有 104/203（8,153 行）有门店名。**真正的门店标识是 `from_user_id`（321/116 出库方向）与 `to_user_id`（104/203 入库方向），即凭据里的 `entId`**。实测：321/116 的 20 个非空 `from_user_id` **全部 20/20** 都能在 104 的"名字↔ID"对照表里找到门店。
2. **`ref_ent_id` 不是门店的**。全表单一值（中央主体）。spec §3 的"用户已确认 `zsm_ls` 三列语义与上传入参一致"与数据不符——上传时 `refUserId` 必须取**门店自己的** `ref_ent_id`（来自凭据），不能取源表这列。
3. **321 存在大量完全重复行**。同一 `bill_code` 最多出现 **120 行**（14 列值完全相同，无任何区分列）；321 平均 100,637/48,402 ≈ 2.08 行/单。**采集 SQL 必须先对 `zsm_ls` 去重**，否则 `left join zsm_ls_code` 会把追溯码放大 N 倍。
4. **追溯码一码一行**。`zsm_ls_code.trace_codes` 每行 1 个码；一单的码数 = 该 `bill_code` 的行数，实测 **1 ~ 1,718**（< 3500，故零售暂不需要拆单）。**无排序列**（`bs` 恒为 1）→ 组装时须 `DISTINCT` + 显式排序保证确定性。
5. **`bill_type` 有第五种 `999`**：10,081 行（8.4%），不在用户给定的四种里。`from_user_id` = 总部单一值；`to_user_id` 指向连锁门店 6,772 行 + 其他主体 3,142 行 + 空 167 行；与 104 **零 `bill_code` 重叠**；`oper_ic_name` 含 1,593 个名字（像客户名）。
6. **凭据文件的门店名与源库不一致**：`tests/company.txt` 用**半角括号** `()`，源库用**全角** `（）`，5/5 全部不命中。改为 ID 认领后此问题不再影响功能（名字仅用于显示），但配置里的显示名应以源库全角写法为准。
