# 数量对账检查（check_quantity.php）—— 恢复 min_pkg_count 数量对比

## Problem Statement

外部系统负责将单据的追溯码上传到码上放心平台，本项目定位为"检查外部系统上传情况"。但现有检查只能到**单据级**：`check_bill_status.php` 调 `searchbilldetail` 确认"这张单在不在平台上"——该接口返回单据头 + 药品数量（`min_pkg_count`），**不含追溯码明细**。

因此，如果某一单有 100 个追溯码、实际只传了 50 个（其余 50 个因意外未上传），现有检查**发现不了**：单号在平台上存在即判"已上传"。运维人员需要能发现"整单数量未传齐"的检查手段。

早期版本曾尝试以 `min_pkg_count` 对比本地码数（`sumBillDetailCount`），因**量纲问题**大规模误报（90 条"数量不符"中 62 条为量纲假阳性），被 ADR 0002 判死并退化为"只查是否上传"（commit 77f826b）。根本问题未解决：**数量仍然无法核对**。

**2026-08-17 新发现（grilling 会话实测）**：SQL Server 明细视图（出库 `v_pf_phlrmx`、入库 `v_sjdmx_mx`）的 **`shl`（数量）字段就是"已展开到最小包装单位"的数量**——整件行 `shl = baozhshl(包装数) × jlgg(件规格)`、零散行 `shl = lingsshl(零散数量)`，件码→最小包装数的映射一直都在 SQL Server 里，只是当初查的是 `wms_dzjg`（追溯码表）而非明细视图。量纲问题可解，数量对账可行。

## Solution

`scripts/check_quantity.php` 恢复**数量对比**能力，比较口径统一为**最小包装单位数**：

```
本地应有（expected）= SUM(shl)：出库 v_pf_phlrmx（按 djbh）、入库 v_sjdmx_mx（按 ysdjbh 关联）
平台实际（actual）   = Σ min_pkg_count：searchbill.detail 原始单号 → _1 → _2... 直到查不到（跨拆分子单累加）
判定: 全查不到 → '信息不存在'（未上传，现状语义）
      actual ≠ expected → '数量不符'（恢复 ADR 0002 废弃的状态值）
      actual == expected → 已上传，零记录
      本地无 shl / 平台响应解析失败 → 无法核对，跳过（不误报）
```

查询策略 **"相等即停，不等查尽"**：原始单号查到且数量相等即停（未拆分大头单 1 次调用）；原始单号查不到或数量不等则继续查 `_1.._9` 直到查不到（上限 10 次），跨子单累加 `min_pkg_count`。每天 cron 一次（21:10，避让 check_bill_status 8-20 点窗口），默认检查前一天，只告警不补传。

## User Stories

1. 作为运维人员，我想要每天自动检查前一天所有单据的数量是否完整上传，以便及时发现"整单没传齐"而不必逐单核对
2. 作为运维人员，当一单 100 个最小包装单位只传了 50 个时，我想要检查能识别出来并告警，以便通知外部系统补传
3. 作为运维人员，当外部系统拆分上传（`单号_1`/`单号_2`/...）时，我想要各子单的申报数量被汇总后与整单应有数量对比，以便拆分上传不误报
4. 作为运维人员，当单据在平台上完全查不到时，我想要检查判定为未上传（`信息不存在`），以便区分"没传"与"传了但少传"
5. 作为运维人员，我想要检查结果在 Web 端失败记录页可见（与现有失败日志同入口），以便不用登录服务器看日志
6. 作为运维人员，我想要数量相符的单据不产生任何记录，以便检查零噪声、只看有问题的
7. 作为运维人员，我想要检查基线来自 SQL Server 实时拉取，以便本地采集/上传 cron 是否运行都不影响检查
8. 作为运维人员，我想要检查脚本与 `check_bill_status.php` 完全独立，以便各自按自己的 cron 节奏运行、互不干扰
9. 作为运维人员，我想要脚本支持手动指定日期补查，以便漏跑 cron 后能补查历史日期
10. 作为运维人员，我想要单条单据 API 查询异常时跳过该单并计入异常统计，以便网络抖动不影响整批检查
11. 作为运维人员，我想要单药品单据和多药品单据的数量都能正确汇总，以便汇总结果可信
12. 作为运维人员，我想要"数量不符"记录中包含预期数、平台数与子单明细，以便人工复核时能定位到具体差距
13. 作为运维人员，我想要 API 调用保持限速（1s/次），以便不触发平台限流
14. 作为运维人员，我想要拆分子单的查询有数量上限，以便异常数据不会导致脚本死循环
15. 作为运维人员，我想要一天 ~650 单的检查在半小时内完成，以便每天 cron 窗口不与其他任务冲突
16. 作为运维人员，当单据含件码/整件（中包装码）时，我想要数量能正确核对（本地 `shl` 已展开），以便不再出现量纲误报
17. 作为运维人员，当本地明细查不到某单的 `shl` 时，我想要该单被跳过而不是报数量不符，以便异常数据不产生假告警
18. 作为运维人员，当平台响应结构异常/min_pkg_count 字段缺失时，我想要该单被跳过而不是按 0 处理，以便解析问题不伪装成数量差异
19. 作为运维人员，当外部系统拆分上传（原始单号在平台不存在）时，我想要检查不误判"未上传"，以便拆分场景零误报
20. 作为运维人员，我想要数量对账发现的历史误报（如早期量纲假阳性残留）随重跑自动清除，以便无需手工清理

## Implementation Decisions

### 1. 数量基线：TaskFetcher 新增 `fetchBillQuantities($date)`

批量聚合查询，一次返回全部单据的 `SUM(shl)`：
- 出库侧：`v_pf_phlrmx` 按 `djbh` 分组（覆盖 XSO 销售出库 201、JHO 退货出库 202）
- 入库侧：`v_sjdmx_mx` 按 `ysdjbh` 分组（入库单号在 `ysdjbh` 列，`djbh` 是 JHI 前缀临时单——沿用 TaskFetcher 现有 join 模式）
- **用基线单号 `IN` 列表聚合，不用 `rq` 日期过滤**——实测 `rq` 字符串比较在明细视图上不可靠（BETWEEN 返回空而单条 `djbh` 查询正常），`IN` 列表与 `fetchBillsMeta` 基线天然一致
- 单号在基线但明细无行（`SUM(shl)` 为 NULL）→ 该单标记"无法核对"跳过

### 2. 数量语义：`shl` 即"已展开的最小包装单位数"

实测 4 样本验证（本地 `SUM(shl)` == 平台 `min_pkg_count` 求和）：
- 零散出库 XSOWMS00998311：50 = 50
- 件码出库 XSOWMS00997350（1 个中包装码）：5 = 5
- 整件入库 JHGWMS00062697（2 件 × 件规格 300）：600 = 600
- 真实拆分出库 JHOWMS00012659（5973 码展开）：7168 = 3500+3668

整件行 `shl = baozhshl × jlgg`、零散行 `shl = lingsshl`；入库侧 `shl` 与 `rkshl`（实收）近 7 天零差异样本，无歧义。**ADR 0002"两数量纲无法统一"的结论被推翻**（见 ADR 0004）。

### 3. 平台实际：跨拆分子单累加 `min_pkg_count`

- 查询序列：原始单号 → `_1` → `_2`... 直到查不到（上限 10 次，3500 码/批 × 10 远超现实单据）
- **"相等即停"**：任意一步 `实际 == 期望` 立即结束（未拆分大头单只花 1 次调用；实测 JHOWMS00012659 `_2` 累计 7168 相等即停）
- **"不等查尽"**：原始单号查到但数量不等，或原始单号查不到，均继续查子单直到序列结束——防止"原单号+拆分并存"罕见场景漏计
- 实测确认：外部系统拆分命名就是 `单号_N` 格式（JHOWMS00012659_1=3500、_2=3668 真实存在），原始单号查询返回 FAIL_BIZ_NO_PAT_INFO（信息不存在）
- 实测确认：`searchbill.detail` 的 `bill_code` 是**精确匹配**，`%` 通配符被当作字面字符，不支持模糊/前缀搜索；`searchbill`（单据列表）接口 `billCode` 参数同样精确——拆分序列只能枚举 `_N`，无替代查询方式

### 4. 判定三分支 + 无法核对

- 全序列查不到 → `response_status='信息不存在'`（未上传，现状语义不变）
- `actual ≠ expected` → `response_status='数量不符'`（恢复 ADR 0002 废弃的状态值，非成功状态，Web 失败记录页天然可见），`response` 存 `{djbh, rq, expected, actual, sub_bills:[{djbh, count}]}`
- `actual == expected` → 已上传，零记录（与用户故事 6 一致）
- **无法核对跳过**（不写任何记录）：本地 `SUM(shl)` 为 NULL（明细无行）、平台响应解析失败（`sumBillDetailCount` 返回 null）

### 5. ApiClient 恢复 `sumBillDetailCount(array|null $respArray): ?int`

解析 searchbill.detail 响应累加 `min_pkg_count`：
- 单药品=关联数组、多药品=列表（两种结构都支持）
- **返回 `null` = 无法核对**：响应无明细结构、或任一行缺 `min_pkg_count`——缺字段不按 0 处理（防止解析异常伪装成"数量不符"）
- 与 `isBillFound` 同置 ApiClient 静态方法层，测试接缝唯一（见 Testing Decisions）

### 6. 保留的现有语义

- 幂等"先删后写"：每轮先清理目标日期全部旧的 quantity_check 记录再按新判定写入（限流熔断重跑不产生残留、历史误报随重跑自动清除；中途崩溃时记录可能不完整，下次重跑整日清理重写，最终一致）
- API 间隔 1s（比 check_bill_status 的 0.5s 保守——数量对账单次量大）
- 平台限流（App Call Limited）识别后本轮熔断，剩余单据下次运行自动重查
- 运行时机：21:10 每天一次（避让 check_bill_status 8-20 点窗口，并发调同一 AppKey 实测第一单即触发限流）
- API 异常（网络/业务）跳过整单计入异常统计，不写"数量不符"

spec.md（本文件）、`docs/adr/0004-quantity-check-restore-count.md`（新 ADR，记录 shl 发现推翻 ADR 0002 量纲结论）、CLAUDE.md（数量对账流程、常用命令）、CONTEXT.md（"最小包装数"术语）。

## Testing Decisions

- **原则**：只测外部行为（解析函数对真实 API 响应的汇总结果），不测实现细节；不 mock API 调用
- **测试模块**：`ApiClient::sumBillDetailCount()`（恢复 + null 语义）；现有 `isBillFound` 测试原样保留
- **测试文件**：`tests/quantity_check_test.php` 扩展，自包含断言（无框架），`php tests/quantity_check_test.php` 直接运行，失败非零退出——对齐现有 `tests/trace_splitter_test.php` 风格
- **测试数据**：真实 `searchbill.detail` 响应内嵌 JSON：
  - 单药品（关联数组结构）
  - 多药品（列表结构，累加正确）
  - 真实拆分场景样本（JHOWMS00012659 的 `_1`=3500、`_2`=3668 子单响应，断言各自累加正确）
  - 无明细结构 → null（无法核对）
  - 任一行缺 `min_pkg_count` → null（不按 0 处理）
  - 信息不存在响应 → null
- **断言**：汇总数与人工核对值一致；各边界返回 null

## Out of Scope

- 追溯码级明细对账（`querycodeactive` 逐码查询）——已实测不可用（SUCCESS 但无状态列表）；`upbill.detail.withcode` 非收货方视角 FAIL_BIZ_AUTH_ERROR
- `codeprocess` 关系查询方案——实测非关系查询接口（无 code 参数、日期区间批量扫描、queryFlag=1 是关联关系修改）；`shl` 已解决展开问题，不再需要
- 补传缺码（Web 一键补传 / 自动补传）——定位为"只检查告警"，避免与外部系统并发上传冲突
- 修改 `check_bill_status.php` / LogWriter / 前端页面——零 UI 改动
- 拆分映射表持久化——由"逐次查询直到查不到"的运行时策略替代
- 通知渠道（企业微信/邮件等）——当前告警出口为 Web 失败记录页
- 模糊搜索/单据列表替代查询方式——实测均不可用/精确匹配

## Further Notes

- 每日单量约 350~1000 单（均值 ~650），按"相等即停"策略绝大多数单 1 次调用，预计 ~800 次调用 × 1s ≈ 13 分钟，21:10 开跑 ~21:25 结束
- 大单实测：JHOWMS00012655（15444 码，未拆分）平台 16798 vs 本地 16799 **差 1**——疑似真实申报差异（外部系统某行少传 1 个单位），数量对账机制将其检出，待人工确认
- 08-15 平台单据列表 542 张 vs 本地基线 725 单（541 已上传 + 184 未上传），吻合——外部系统当日无拆分
- 子单查询"相等即停"的 break 条件不限于原始单号（s==1），任何一步累计相等即停
- 该检查顺带修正 `check_bill_status.php` 的盲区：外部系统拆分上传后原始单号查不到被误判"未上传"的场景（实测 JHOWMS00012659 原始单号 FAIL_BIZ_NO_PAT_INFO、子单 7168 全部在传）

### 2026-08-17 实现——恢复数量对比（commit 见 9d50b64 之后）

按本 spec 恢复数量对比（fetchBillQuantities + sumBillDetailCount + 三分支判定），08-15 实测验证（204/725 单后触发平台限流熔断，剩余下次自动重查）。**实测发现两类系统性假阳性，经用户确认修正 expected 口径**：

1. **非药品行（消杀用品/器械/商品/食品等）本地有、平台不申报**（平台是药品追溯平台，外部系统按平台规则只传药品码）——35 条"数量不符"中 16 条纯属此类（如消毒液、一次性输液器、纱布、晕车贴），**修正：fetchBillQuantities 聚合时经 spkfk.jixing 剔除非药品行**（关键词：商品/食品/消杀/用品/器械/化妆品/消毒剂/敷料/试剂/材料/设备；spkfk 查不到剂型的行保守保留）。4 样本（零散 50/件码 5/整件 600/拆分 7168）在新口径下不变。
2. **本地零售规格 ≠ 平台生产规格**（氨咖黄敏胶囊 本地 10粒/盒 → 50 盒 vs 平台 500粒/盒 → 1；注射用青霉素钠 20 瓶 vs 平台 1 盒 20瓶/盒）——19 条剩余差异纯属此类，**保留告警**：本地 shl 按本地最小包装（零售规格）计数、平台 min_pkg_count 按平台注册规格（生产包装）申报，同数量不同包装数。机制本身已验证精确（XSOWMS00997406 的 19 行中 18 行逐行相等，仅青霉素钠 20瓶 vs 1盒 差 19）。运维在 Web 失败记录页看到"数量不符"时优先怀疑此两类成因，记录含 expected/actual/sub_bills 可供人工复核。
3. 未确认任何一条为外部系统真实少传的差异（"数量不符"当前是"疑似差异"告警，真实差异与规格差异在现有数据上不可区分）。

### 2026-08-17 基线方向修正（用户反馈）

用户指出：**查询数量仅针对 check_bill_status.php 检查过且状态是"上传成功"的单据**。原 spec 以 SQL Server 单据全量为基线（fetchBillQuantities 按日期拉全部单据），会重复查询/告警未上传的单据。修正：

- **基线改为 upload_logs**（`source='batch_check' AND response_status='上传成功'`，按 rq 筛选，不写库）：08-15 实际 589 单（vs SQL Server 全量 725 单，未上传的 136 单不再重复查询）
