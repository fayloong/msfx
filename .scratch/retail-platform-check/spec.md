# 门店单据在平台上再核查一次（lsyd.query.upbilldetail）

**What to build:** 给门店单加第二条「是否已上传」的判据——**拿该门店自己的凭据去平台问一次**。

现状只有一条判据：源库状态表（`App\RetailExternalUploads::TABLE`，状态闭环每轮采集前跑，票 03）。它免费、每 30 分钟一轮，但有三个盲区：

1. **那张表是外部系统的行为，不是平台的承诺**——外部系统传了单却没写它，本系统永远不知道，任务一直挂在「等待上传」，人只能赌一次补传（撞上「该单据号已存在」返回`单据重复`才算收场）；
2. **状态表没有企业列**——判据只能按裸单号比对，同名单号跨门店会串（ADR 0007 记的已知代价，闭环那层无法消除）；
3. `未识别` 的门店单进不了闭环的失败记录清单（它没有企业类型）。

本票补的是**平台本身的事实**：`alibaba.alihealth.drugtrace.top.lsyd.query.upbilldetail`，参数 `bill_code` + `ref_ent_id`。带 `ref_ent_id` 意味着这条判据**天然按企业隔离**——同样的单号在甲店查到、在乙店查不到是两个独立问题，这正是状态表做不到的那一格。

参照物是批发的 `check_bill_status.php`（来源 1：等待上传任务）与 `check_failed_logs.php`（来源 2：失败记录），本票把两个来源合进**一个零售脚本**——因为两者都要按门店分组取凭据、都要限速，拆成两个脚本会重复这套分组逻辑。

## 探测结果（2026-10-05，新江分店凭据，2 次只读查询）

用新江分店凭据（`ref_ent_id = 61873868e4b032c2577ada38`）各查一次「9-29 补传成功」与「等待上传队列」的单号，响应形状与 kyt 的 searchbill.detail **同款**，`ApiClient::isBillFound()` 的判据**直接适用**：

| 情形 | 单号 | `result.msg_code` | `msg_info` | `response_success` | 附带的 model |
|---|---|---|---|---|---|
| 已上传 | `XLSA0200100185242` | `SUCCESS` | 调用成功 | `true` | 有（单据详情：bill_code/bill_time/bill_type + 药品明细） |
| 未上传 | `XLSA0200100185757` | `FAIL_BIZ_NO_PAT_INFO` | 信息不存在 | `false` | 无（只有 result 三个字段） |

顺手确认的两件事：
- **未上传时也不报错**，是一句规规矩矩的业务响应——判据不用靠异常兜；
- 已上传时返回的 `bill_time`/`bill_type` 与本地 rq/类型一致（本票不做核对，只记在这里：将来要"顺带核对单据元数据"是现成的）。

## 设计

**判据层**：`ApiClient::queryUpbillDetail(string $billCode, string $refEntId)` → `['found' => bool, 'response' => array, 'error' => string]`，与 `searchBillDetail()` 同形状（`found` 由 `isBillFound()` 给，那个静态方法的 docblock 扩到两个接口共用）。入口必须显式传 `ref_ent_id`（照 `queryEntInfo` 的先例），**没有默认值**——用错主体的 ref_ent_id 会把单据判到别人名下。

**判定与落库复用闭环那一套**（`App\RetailExternalUploads`）：本票从 `closeLoop()` 里抽出三段，让「源库状态表判据」与「平台判据」走**同一段**动作判定与落库：

| 抽出的 | 现状位置 | 两个调用方 |
|---|---|---|
| `pendingItems()` 取本地待办（等待上传的门店任务 + 零售企业的非成功记录） | `closeLoop()` 第 1、2 段（内联） | 状态闭环、平台核查 |
| `successKeys(array $djbhs)` 本地已有成功记录（按 `(company, djbh)`） | `closeLoop()` 第 4 段（内联） | 同上 |
| `applyActions(array $actions, array $pending, string $reason)` 翻任务行 / 追加记录 / 记 JSONL | `closeLoop()` 第 5 段（内联） | 同上 |

判定本身 `closureActions()` 已经是纯函数、不动——**平台核查按企业分组调用它**（每组只喂该企业的已上传集合），企业隔离因此是构造上的性质。

**编排层**：`App\RetailPlatformCheck`（照 `App\RetailBatchUpload` 的样式：取数口径是常量、主循环可注入回调、`--dry-run` 自包含可断言）：
- 取数：`source='retail' AND task_status='等待上传'` 的任务行 ∪ 零售企业的非成功日志记录（复用 `pendingItems()`）
- 按 `company` 分组；**`未识别` 与「取不到凭据」（待配凭据 / 不在配置中）的门店整组跳过并计数**——没有凭据就没有 ref_ent_id，这条判据对它们不成立（`未识别` 的任务行仍归源库闭环管，那条判据不需要凭据）
- 每组造一套 `ApiClient::forCredential()`，逐条查平台（`usleep(500000)`，与批发查询同速），只把 `found=true` 的单号收进该企业的已上传集合
- 查询异常（网络错误）**只跳过、不修改**（"不知道"不等于"没上传"——与闭环对源库查不通的态度一致）
- **逐条查询不留 `upload_logs` 痕迹**（只有翻正才由 `applyActions()` 记一条 JSONL，`type=retail_platform_check`）。⚠️ **spec 初稿写的是"每条用返回的 response 写 JSONL"，实现时收窄到这个口径**——与批发的两个检查脚本一致（它们也只在状态变化时写，"查过但没传"只在脚本输出里）。理由：一趟 1,400 条会写 1,400 行噪音，而"这单被查过"这件事在 cron 日志/终端输出里逐条看得见
- 落库走 `closureActions()` + `applyActions()`

**脚本**：`scripts/check_bill_status_retail.php`，`--dry-run` 只列不查（不调平台、不写库、不写 JSONL）、`--limit=N` 小步走、`--company=名,名` 限定门店（取回之后过滤，口径本身不变），flock 防并发（`logs/check_bill_status_retail.lock`，dry-run 不取锁——它一个字节都不写）。

**开销与边界**：`usleep(500000)` 每条（与批发查询同速）。**不做 `last_checked_at` 门卫、也不 touch**（实现时定的口径，与 spec 初稿不同）：本脚本由人手动跑，一趟几千条自带限速；清单还会**随翻正自然收敛**（已上传的翻正后不再是「等待上传」）。批发的 30 分钟门卫是给高频 cron 用的——这里没有那个场景；将来真要挂 cron 时再加（那时 touch 才有意义，现在不 touch，门卫就没有数据可用）。**已知代价**：被翻正的失败记录仍留在待办清单里（它的 `response_status` 还是失败，`pendingItems()` 照取），每次跑都会重查它们——判无动作、不会重复追加，但白花一次调用（要根治得改写那条历史记录，本项目刻意不做）。

## 决策（开工前与用户确认，2026-10-05）

| 决策点 | 选择 | 理由 |
|---|---|---|
| 响应判据怎么定 | **先真调探测**（2 次只读查询） | 用户拍板；结果见上表——省掉了"照 kyt 口径猜 lsyd 错误码"的返工风险。探测用的两个单号都是新江分店的：一个 9-29 补传成功（平台确定有）、一个在等待上传队列里 |
| 调度 | **先手动跑、不挂 cron** | 用户拍板。与 `upload_pending_retail.php` 同一态度：验证充分前不装常驻任务。5 家门店约 2000+ 条待办、@500ms 一趟约 17 分钟，挂了也就是常驻轮询 |
| 覆盖来源 | **两个都做**（等待上传任务 + 失败记录） | 用户拍板。大湖分店压着 627 条补传失败记录，正是"以为失败了、其实平台上早有"的典型场景 |
| 动作语义 | 照**状态闭环**：任务行翻「已处理」+「上传成功」、`request_status` 不动；失败记录**追加**一条「外部上传」记录、不改写历史 | 与闭环同理：本项目没为这张单发起上传请求，写「请求成功」是失真；改写失败记录会让"补传失败过"这段历史消失。批发 `check_failed_logs` 的翻转口径**不照搬**——它翻转的是本项目自己发的请求记录，语义不同 |
| 追加记录用什么来源 | 复用 `retail_external`（「外部上传」） | 对"这单谁传的"这个问题答案相同（不是本项目传的）；判定方式写在 `response` 的出处 JSON 里（`judged_by` 字段），审计轨迹在详情弹窗可见，不必让运维多认一个来源取值 |
| 页面入口 | **不做**（本票只出脚本） | 用户没提；脚本跑出来的结果页面上本来就看得到 |
| 要不要 ADR | **给 ADR 0016 加补注** | "读侧口径"从一条判据扩成两条，是那个 ADR 记的事的延续，新开一条反而割裂 |

## 代价与残留

- **平台调用有成本**：每家门店用自己的 AppKey，不占河药那个限流池；但一趟 2000+ 次调用仍要 17 分钟，故默认手动跑。
- **状态表仍要读**：闭环那条判据不撤——它免费、每 30 分钟一轮，覆盖"任务刚采进来"的高频窗口；平台核查是补它的盲区，不是替代。
- **`未识别` 单这条判据管不了**（没有凭据）：它们的翻正仍只靠源库闭环。
- 探测与实测都要真调平台（只读查询）。本票的离线测试只覆盖分组/跳过/判定编排，真实响应靠探测记录（上面那张表）钉住。
