# 04 · 平台核查看不见 104：单号形态要试两次（`RK` + 源单号）

Status: open
Type: task

## 背景

`lsyd.query.upbilldetail` 是**精确匹配**。外部系统上传 **104（调拨入库）** 时，平台侧单号是
**`RK` + 源库单号**；本项目自己上传（`retail_retry` / `manual`）时用源单号原样。所以同一个源单号
在平台上**可能以两种形态之一存在**，只查源单号会漏掉带前缀的那批。

规则、实测证据与一次误删 34 条真记录的事故经过，见 `docs/adr/0019`。

## 现状（盲区的后果）

`scripts/check_bill_status_retail.php` 只查源单号，于是：

1. **104 的单它一条也看不见**——平台已上传的 104 待办永远翻不成「已处理」，一直挂在队列里。
   全站 104 待办 **474 条**；2026-10-09 抽样 10 条（有凭据的门店）：**4 条其实已在平台**、
   6 条确实没有（徐洞分店那 6 条）。
2. **对这些单执行批量补传只会失败**：平台返回
   `FAIL_BIZ_BILL_DUPLICATE_UPLOAD_BILLCODE_REPEAT_CODE`（码重复流向），报文里点名的是
   `RK` + 单号那张单。2026-10-08 已有 **34 次**这样的失败记录（`retail_retry` + 上传失败），
   失败记录页上会被人当成"补传没成功"。
3. "未上传"的统计对 104 偏高——`--dry-run` 报的数字同样偏悲观。

## 待决

- [ ] **查询侧**：在 `check_bill_status_retail.php` 的查询闭包里，源单号查不到时用 `RK` + 单号再查一次，
      两步都查不到才算"未上传"。（`check_uploaded_retail.php` 已按此实现，见 2026-10-09。）
- [ ] **判定侧**：`ApiClient::isBillFound()` 把 `FAIL_BIZ_ENT_NOT_EXIST` / `FAIL_BIZ_AUTH_ERROR`
      这类**错误码**也判成"单据存在"（它只在 `FAIL_BIZ_NO_PAT_INFO` 时判"未上传"）。凭据的
      `ref_ent_id` 一旦抄错，平台核查会把该店整批待办**凭空翻成「上传成功」**。与 `HTTP_RESPONSE_NOT_WELL_FORMED`
      那条已知残留是同一类问题（"错误响应被读成正常响应"），建议合并成一票。
- [ ] **历史数据**：474 条 104 待办里那批"其实已在平台"的，要不要一次性翻正（跑一轮定向核查）。
      注意它们目前**不在**平台核查的覆盖里，跑之前先决上面第一条。
- [ ] **测试**：查询侧的两步逻辑目前写在脚本闭包里，不可离线断言。若要加用例，先把"该试哪些形态"
      抽成纯函数（例如 `fn(string $djbh): array` 返回候选形态列表），脚本与测试共用一份。
