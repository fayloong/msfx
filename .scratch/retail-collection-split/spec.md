# 零售采集由「过滤」改「分流」（外部已上传可见 + 计数门卫 + 状态闭环 + 备而不用的上传脚本）

> 本文取代 [retail-chain/spec.md](../retail-chain/spec.md) 里与采集口径相关的表述：2026-09-30 的**测试阶段临时口径**（采集 SQL 用 `NOT EXISTS(update_state)` 把外部系统已上传的单整批挡在门外）**就此结束**。
> 关联决策：[ADR 0007](../../docs/adr/0007-retail-no-platform-reconciliation.md)（本次加修订注三）、[ADR 0011](../../docs/adr/0011-retail-retransmit-metadata-and-manual-trigger.md)（补注：上传能力已备、暂不启用）、[ADR 0013](../../docs/adr/0013-retail-two-year-retention.md)（2 年下限，不变）、[ADR 0016](../../docs/adr/0016-retail-upload-state-writeback.md)（回写，读侧口径本次随之扩展）、新 ADR 一篇（分流 + 门卫 + 闭环）。

## Problem Statement

门店单据由外部系统负责上传，本项目只做「可见 + 人工补传」。但现在的采集把**外部系统已上传成功的单整批过滤掉了**（测试阶段的临时口径），于是运维在本系统里根本看不到它们——一张门店单传没传、是谁传的，只能去源库里查。同时：

- 每一轮采集都全量重扫一遍源库，源库什么都没变时也照跑，且日志里看不出「真的没新单」与「脚本压根没跑」的区别；
- 一张单在本项目里以「等待上传」的任务存在，之后外部系统把它传上去了，**本地不会有任何反应**——任务永远挂在补传队列里，人去点补传会白调一次平台（申报不可逆）；
- 将来系统要接管门店上传时，现在只有页面上的「逐条补传 / 批量重传」，没有一个可以挂进 cron 的批量入口，届时要从零写。

## Solution

把采集从「**过滤**」改成「**分流**」：单据全采进来，按源库那张状态表（`update_state`）一分为二——

- **已上传的**（外部系统传的，或本项目补传成功后回写的）→ 写成一条「**外部上传**」记录，进「已上传记录」页，**不**建补传任务；
- **未上传的** → 照旧建「等待上传」任务，由人在上传任务页逐条补传或批量重传。

在此之上补三件事：

1. **状态闭环**：每一轮采集都拿**本地待办清单**（还在「等待上传」的门店任务、补传失败的门店记录）去源库核对，外部系统后来传成了的，本地痕迹自动翻正（任务翻「已处理」，失败页不再报它）。
2. **计数门卫**：采集开跑前先数三个数（当日单据总数 / 已上传 / 未上传），与上次基线比对，**三个数都没变就直接跳过**并在日志里说明原因；基线只在整轮采集成功之后更新。
3. **备而不用的上传能力**：新增一个可手动运行的零售批量上传脚本，复用现有补传链路，默认**不挂 cron、不启用**——门店申报仍然由人决定。

「已上传」的判据**只有一处**：源库 `dyt.bs_msfx.dbo.update_state`（`bill_code` + `bill_state`，成功为 `'1'`）。本项目补传成功后也写它（既有行为，不变）。

## User Stories

1. 作为运维，我想在「已上传记录」页看到外部系统已上传成功的门店单，这样我不用去源库就能回答"这张单到底传没传"。
2. 作为运维，我想让这些记录的来源标成「外部上传」，这样我能一眼分清哪些是本项目补传的、哪些是外部系统传的。
3. 作为运维，我想按「外部上传」筛选已上传记录，这样我能单独核对这一类。
4. 作为运维，我想让导出的「来源」列是中文标签，这样发给同事的表格不用再解释机器值。
5. 作为运维，我不想在「上传任务」页看到已经上传成功的外部单，这样待补传队列里剩下的都是真要处理的。
6. 作为运维，我想在外部系统后来把某张单传上去之后，本地那条「等待上传」的任务自动变成「已处理」，这样我不会对着一张已经传过的单再点一次补传。
7. 作为运维，我想在那之后，之前那条补传失败的记录不再出现在失败记录页，这样失败页上剩下的都是真要处理的。
8. 作为运维，我希望"对着已经传过的单再点一次补传"这种情况尽量不发生，因为平台申报不可逆、白调一次也是浪费。
9. 作为运维，我想让已上传记录里同一张单只出现一行，这样统计口径不会被重复行搞乱。
10. 作为门店操作员，我想让手工新增（在线新增 / xlsx 导入）的行为完全不变，这样这次改动不影响我日常怎么录单。
11. 作为运维，我想让采集在源库没有变化时直接跳过并写明原因，这样日志里能区分「真的没新单」和「脚本没跑」。
12. 作为运维，我想让门卫的基线只在整轮采集成功之后才更新，这样一次中途失败不会被记成"没变化"从而永久跳过。
13. 作为运维，我想在系统初期用一次性入口把最近两年的历史单建成快照（含已上传的），这样上线第一天页面上就有数据。
14. 作为运维，我想在跑快照之前先预演、看到"将写入多少单、多少码"，这样我能判断要不要跑。
15. 作为运维，我想在需要重建快照时重跑同一个入口，且它幂等、不会重复写入。
16. 作为运维，我想让门店数据仍然只保留最近两年（采集合规），这样不会因为这次改动把超期单据放进来。
17. 作为运维，我想知道已上传记录的保留窗口是"写入后三个月"、快照是一次性视图会自然过期，这样我不会以为它会一直留着。
18. 作为将来接手的人，我想有一个现成的零售批量上传脚本（复用现有补传链路），这样系统要接管门店上传时不用从零写。
19. 作为运维，我想让这个上传脚本默认不挂 cron、不启用，这样门店申报的决定权还在人手里。
20. 作为运维，我想让上传脚本跳过「未识别」门店的单并报告跳过数量，这样日志不会被必然失败的条目刷屏。
21. 作为运维，我想让上传脚本支持预演与限量，这样第一次试用可以小步走。
22. 作为运维，我想让并发的采集/上传进程不会互相踩（文件锁），这样不会因为并发而产生重复申报。
23. 作为运维，我想让认领不到门店的单仍然照常入库并标「未识别」，这样不会因为认领失败而丢单。
24. 作为运维，我想让这套判定**全程不调平台查询接口**，这样它不受平台限流窗口的约束，随时可跑。
25. 作为运维，我想让"已上传"的判据只有一处来源，这样不会出现两套互相打架的结论。
26. 作为开发者，我想让这批逻辑落在可单独测试的模块里、而不是埋在脚本里，这样它能像现有模块一样被断言覆盖。
27. 作为运维，我想让批发链路、补传的三关 fail-closed、三个检查脚本的口径一个字都不变，这样这次改动不会波及正在跑的自动链路。
28. 作为未来的维护者，我想在文档里看到这次口径反转的理由与已知代价，这样回看时不会以为它是随手改的。

## Implementation Decisions

### 1. 采集：去过滤、加判据、按判据分流

- 采集 SQL 去掉 `NOT EXISTS(update_state)` 过滤，改为在结果里多取一个**已上传标志列**（该单号在 `update_state` 里存在即为真）。**必须用 `EXISTS` 子查询，不能用 JOIN**——那张表无主键无唯一约束，**实测 67,856 行里有 82 个单号是多行**（80 个两行、1 个三行），JOIN 会把结果集放大。
- 分流规则：
  - 标志为真 → 写一条外部上传记录，**不建任务行**；若该 `(company, djbh)` 本地已有成功记录，整条跳过（幂等）。
  - 标志为假 → 现有建任务逻辑**一字不变**（认领、三列元数据、`source='retail'`、`task_status='等待上传'`）。
- 参数：保留现状（无参＝当日；指定日期；`--all`）。新增 `--dry-run`：只统计并打印"将写入 N 单 / M 码"，不落库。
- `--all` 语义更新为「**最近两年的全量快照**」（2 年下限不变）：跳过门卫，把窗口内所有单按新口径落库——已上传的成记录、未上传的**不建任务**（见下条"已定"的口径）。它是**一次性入口**，跑一次即可，不挂 cron。
- **快照的真实规模（2026-10-02 实测，非估算）**：两年窗口 **104,995 张单据**、LEFT JOIN 后 **558,666 行**（PHP 侧逐行消费的规模，必须走既有的逐行消费接口）；窗口内**约 3.7 万张未在 `update_state` 里**。
  ⚠️ **2026-10-02 票 05 首跑更正**：**104,995 是行数不是单数**——`zsm_ls` 自己是带重复行的（321 平均 2.08 行/单），去重后窗口内只有 **54,085 单 / 558,981 行**；"3.7 万未上传"也是拿行数减行数的粗估，真值是 **6,251 单**，其中 6,245 单本地早有痕迹、**真正"看不见"的只有 6 单**（与门卫票 04 撞见的是同一个坑）。口径本身不变（未上传不建任务），但"一次会灌三万七千条任务"这个理由不成立。实测详见票 05 与 CLAUDE.md 的采集章节。
- **快照只写「已上传」记录，历史未上传的不建任务（已定）**：若按日常分流规则跑，一次 `--all` 会建出约三万七千条「等待上传」——人工处理不现实，且会把"待补传"这个工作清单的信号淹没。快照的用途是"初期让页面上有历史可看"，**工作队列由日常采集按日累积**（今天采今天的、明天采明天的）。代价是窗口内未上传的历史单在本系统里不可见——所以快照结束必须打印「窗口内未上传 N 张，未建任务」，让欠账是**可查的数**，而不是一个看不见的洞。
- 源库读取失败、显式超期日期拒绝、认领失败照常入库并记 JSONL 警告——全部维持现状。

### 2. 计数门卫（新模块 `App\RetailCollectionGate`）

- 三个数：**当日总数 / 已上传 / 未上传**，范围与 cron 采集一致（当日 + 四种门店单据类型）。第三个是前两个的派生值，一并存下来便于人工对账。
- 基线文件独立于批发的计数基线（两个脚本共写一个文件会互相踩），形状：

  ```json
  { "date": "YYYY-MM-DD", "total": 0, "uploaded": 0, "unuploaded": 0 }
  ```

- 判定：日期相同 **且三个数都没变** → 打印原因后正常退出（非错误退出码）。
- **基线只在整轮采集成功之后写**（源库读完 + 全部落库完成）；任何异常路径都不更新——否则"落库跑到一半失败"会让计数看起来没变，从此永久跳过。这条照搬批发采集既有铁律。
- 日期不匹配、文件缺失、文件损坏 → 一律视为"无基线"，照常采集。
- `--all`、`--dry-run` 均绕过门卫。
- **计数 SQL 的形状（实测踩过的坑）**：SQL Server **不允许**在聚合里套子查询——`SUM(CASE WHEN EXISTS(...) THEN 1 ELSE 0 END)` 会直接报「不能对包含聚合或子查询的表达式执行聚合函数」。可用形状是把状态表去重成派生表再 LEFT JOIN：

  ```sql
  select count(*) as total, count(a.bill_code) as uploaded,
         count(*) - count(a.bill_code) as unuploaded
    from <单据头表> ls
    left join (select distinct bill_code from <状态表>) a on a.bill_code = ls.bill_code
   where ... and ls.bill_time = ?
  ```

  去重派生表不能省（状态表无唯一约束、实测有 82 个单号多行，直接 JOIN 会放大）。注意**非聚合**的 `case when exists(...) then 1 else 0 end` 是允许的——采集查询因此不受这条限制。
- **实测成本（2026-10-02）**：门卫计数 **47–59ms**（冷启动 761ms）；当日采集查询 **80–153ms**。**门卫省的是本地去重、认领与写库，不是源库扫描**——采集本身只有百毫秒级，别把它当性能优化；它的价值在于"日志里能区分'真的没新单'与'脚本压根没跑'"。

### 3. 状态闭环（并入 `App\RetailExternalUploads`）

- **触发方式：按本地待办清单查，不按日期扫源库**。待办清单＝还在「等待上传」的门店任务 `(company, djbh)` ＋ 零售企业的补传失败记录 `(company, djbh)`；按批（沿用现有的 IN 分块大小）去 `update_state` 做 `IN` 查询。这样可以**跨日**覆盖：昨天的单今天被外部系统传了，一样能翻正（若只挂在"当次采集结果"上，日期窗口会让它永远漏掉）。
- 每轮都跑，**不受门卫约束**（它不扫源库大表；清单通常几十到几百条）。
- 命中后的动作：
  - 任务行 → 翻 `已处理` + `上传成功`（与"失败也算已处理"同一口径；**保留痕迹，不删行**）。
  - 失败记录 → **不改写历史**，改为**追加**一条外部上传记录（失败页那条会被既有的同单号判重自动隐藏）。避免出现"同一单两行成功"与"来源失真"。
  - 本地已有成功记录 → 只翻任务行，不新建记录。
- **红线**：定位一律用 `(company, djbh)`，**绝不用裸 `djbh`**——裸单号会串到别家企业的同名单号（生产库里 `djbh` 并不唯一）。
- 只碰零售：任务行按 `source='retail'` 筛，失败记录按企业类型筛（零售企业），批发行一律不动。
- 每次翻转记一条 JSONL（含企业、单号、本地原痕迹类型），**不写进上传日志表**（避免与那条记录重复）。

### 4. 外部上传记录的形状（`upload_logs`）

- `source='retail_external'`、`response_status='上传成功'`
- `company` / `credential` 取自认领结果（认不到门店仍是 `未识别`，照写）
- `rq` 取源表单据日期、`trace_codes` 照写、`task_id=0`
- `request_status` 留 `NULL`——**本项目没有发起请求**，写「请求成功」是失真
- `response` 写一小段 JSON 说明出处（外部系统上传、判据来自源库状态表），让"API 返回详情"弹窗里看得见它为什么在这儿
- **不变量**：同一 `(company, djbh)` 最多一条成功记录。

### 5. 来源标签收口（新模块 `App\LogSource`）

- 现状是三份 JS map、键集互不相同，且 `quantity_check` 三页都没有、页面直出机器值（已知缺口）。本次收成**一份 PHP 常量**：取值 → 中文标签 / 徽标色 / 下拉选项。
- 两个日志页的视图输出成 JS map、导出直接用同一份。任务页不需要新增（外部单不建任务行）。
- 新增取值标签：「**外部上传**」；**顺带补上 `quantity_check`**。
- 行为变化（已确认）：导出的「来源」列由机器值变成中文标签。

### 6. 零售批量上传脚本（新脚本，**不挂 cron**）

- 取数：`task_status='等待上传' AND source='retail'`，**排除 `company='未识别'`**（必被守卫拒，取来只是刷屏），结束时打印"跳过未识别 N 条"。
- **不新写上传逻辑**：逐条交现有的补传实现（它是"上传一条门店单据的唯一实现"，补传 / 批量重传 / 手工建单都走它）。
- **门卫**：文件锁防并发 ＋ 队列为空秒退；**不加"数量未变就跳过"那类计数门卫**——上传不可逆，跳过判据写错就是"该传的没传"，而它省下的只是几次查询。
- 默认**真传**（将来是给 cron 用的），带 `--dry-run`（只列不传）与 `--limit=N`。
- 附带文档事实：ADR 0011 定的「补传只能人工触发、没有自动重试」**被这个脚本反转**（一旦启用）。ADR 里要同时记下**能力已备**与**暂不启用**。

### 7. 不动的部分

- 补传链路的**三关 fail-closed** 与上传装配、批发全链路、三个检查脚本只查批发主体、2 年下限、三个月清理判据、失败页与仪表盘既有的判重口径。
- `App\UpdateStateWriter` 的写入语义一字不动；只把它的表名常量提出来共用，避免第二处硬编码表名。
- **清理判据不动**：已上传记录仍按 `created_at` 三个月清理（快照是一次性视图，三个月后自然过期；需要重建就再跑一次 `--all`）。

## Testing Decisions

**好测试的标准**：只测外部行为——给定输入得到什么输出/什么决定，不测私有方法、不断言 SQL 字符串、不依赖真实数据库。本项目的测试形态是**自包含断言脚本**（无 PHPUnit），每个新模块配一个，跑法与其他测试一致。

**复用而不新增接缝**：补传实现（上传脚本直接调，不上测）、2 年下限模块（采集合规）、记录查询模块（页面口径，不动）。

**脚本本身不进测试**：采集脚本与上传脚本只做取数、参数与输出，逻辑都在上面三个类里——与现有"脚本薄、逻辑进类"的分工一致。

**既有测试先例**：2 年保留期的边界用例（截止日当天保留、跨年、闰日）、记录查询的参数与列映射用例、企业配置的"辨别力"用例（摘掉关键行为即变红）——新测试照这个写法，**必须带辨别力**：把门卫的"成功后才更新基线"去掉，对应用例要变红。

**人工/半自动验证（非断言）**：

- 门卫：连跑两次采集，第二次应打印"三个数没变，跳过"。
- 分流：`--dry-run` 跑一次当日采集，核对"已上传 / 未上传"的数量与源库口径一致。
- 快照：`--all --dry-run` 看量级（这一步同时回答了"两年快照有多少单多少码"）。
- **写路径在项目副本上验**（复制项目与库到临时目录 + 起独立 PHP 服务），不在生产库上试写。
- 源库只读探测**已完成（2026-10-02）**：两表列名、状态表现状（67,856 行、`bill_state` 全为 `'1'`、82 个单号多行）、门卫与采集查询的实测成本、两年窗口规模——结论已并入上面的实现决策。

## Out of Scope

- **不启用**零售自动上传：新脚本不挂 cron、不改任何既有 cron 条目。
- 不改补传的三关 fail-closed、上传装配与平台调用策略（间隔、重试）。
- 不改批发链路、三个检查脚本的取数口径（仍只查批发主体）。
- 不改三个月清理判据——**接受"已上传记录只能翻到近三个月"**，快照是一次性视图。
- 不做零售的**数量对账/平台查询**：本机制全程离线，沿用"零售不调平台查询接口"的既有决策。
- 不给源库表加索引（`bill_time` 无索引的事实保留，代价记入 ADR）。
- 不修仪表盘那处第 5 份筛选拷贝、以及 `quantity_check` 之外的其它已知显示缺口。
- 不处理源库 `999` 类型单据（语义未明，用户判定不采）。

## Further Notes

- **源库只读探测结果（2026-10-02，全程 SELECT）**：① 判据表确认无误——`update_state` 就是 `(bill_code, bill_state)`、**`bill_state` 全为 `'1'`**（不存在需要区分的其它取值）；`zsm_ls_code` 只有 `bill_code / trace_codes / entid / relation_states / bs`，**没有 `bill_state`**——先前记岔的表名到此关闭。② 该表 **67,856 行 / 67,774 个去重单号**，比当天更早记录的 67,842 行**多了 14 行**，说明它**正在被写**（外部系统仍在往它写）。③ **近几日的已上传比例很低**（10-02：3/94；09-29：38/366），而两年窗口整体约 65% 已被标记成已上传——**原因已确认：外部系统近期故障、正在修复**。含义：故障期间每天几百张未上传单会堆进补传队列（今日 91 张），靠人的「补传 / 批量重传」消化；等它修好、把欠账补传上去，我们的闭环会再自动把本地痕迹翻正——**这正是闭环存在的意义**。
- **口径已全部定稿（2026-10-02）**：快照只写已上传记录、历史未上传的不建任务（见 §1 最后一条）。
