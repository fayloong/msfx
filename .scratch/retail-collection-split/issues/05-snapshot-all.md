## 交付记录（2026-10-02）

**落点**：`App\RetailExternalUploads` 加 `ACTION_COUNT_ONLY` + `decide()` 的第四个参数 `buildTasks`（默认 true，日常一字不改）+ `tally()`；`App\Database::transaction()`（新，把一个写批次包进一次 `BEGIN IMMEDIATE`/`COMMIT`）；`scripts/fetch_bills_retail.php` 改成流式 + 参数解析（`--all` / `--dry-run`，顺序随意、互斥规则一条）；测试加用例 8/9。

**逐行消费怎么落的（用户拍板：单条 SQL + `order by ls.bill_code` 分批 flush）**：SQL 保持一条，多一个 `order by ls.bill_code` 让同一单号的行连续；PHP 侧按键切换，收尾的单据攒成一批（`RETAIL_WRITE_BATCH = 500`）就查本地痕迹 → 判定 → 一次事务落库。内存峰值实测 6–12 MB。

**⚠️ 验收第 4 条的"不能攒进内存"没能复现**：把 HEAD 上的旧写法（全攒进 `$bills` 再统一落库）拿到副本上、`-d memory_limit=128M` 跑 `--all`，**跑得过**，内存峰值实测 **84.5 MB**（上限的 66%）。原因是窗口里只有 54,085 单而不是票面估的 104,995（那是行数）——旧的估算把行数当单数，于是把内存也估成了两倍。流式改法因此**不是**一次救火：它的价值是内存与窗口规模无关（窗口再长一倍必溢），以及顺带把落库变成分批事务——**后者才是硬需求**（单条隐式事务 = 一次 fsync，实测 21–28 ms/条；47,813 条按现状要等 25–30 分钟磁盘）。已在脚本头部与 CLAUDE.md 里如实写明，免得后人以为它救过一次溢出。

**为什么不只是"别攒内存"**：落库必须攒批提交——SQLite 每条语句一个隐式事务＝一次 fsync，本机实测 **21–28 ms/条**，47,813 条记录按现状要等 25–30 分钟磁盘；每批 500 条一次提交后整轮写库 ~20 秒。这是本票量出来的一条硬事实（`Database::transaction()` 的由来）。

**顺带的一条口径变化**：落库与读源库**交错**了（旧写法是"源库全读完才开始写"）。中途失败会留下已落库的那几批——靠落库幂等（按 `(company, djbh)` 跳过已有的）兜住，重跑补齐；门卫"基线只在整轮成功后写"也随之兜住（抛异常即不写基线 → 下轮重采）。

**票面量级更正**：spec/票面写的"104,995 张单据 / 约三万七千张未上传"是**行数**口径（`105,015 行` 与 `105,015 − 状态表 67,856 行`）——与门卫票 04 撞见的是同一个坑（`count(*)` 数的是 `zsm_ls` 自己的重复行，321 平均 2.08 行/单）。**真相：54,085 单、未上传 6,251 单、其中 6,245 单本地早有痕迹、真正"看不见"的只有 6 张。** 口径本身（未上传不建任务）不变，但"一次会灌三万七千条任务"这个理由不成立——已在 CLAUDE.md 里记下。

**首跑数字（生产库真跑，跑前 `.backup` 到 `/root/msfx-backup-2026-10-02-1210.db`，全程只读源库）**：预演 32.8 秒（数字与副本逐字相同）→ 真跑 **88.5 秒 / 内存峰值 12 MB / 退出码 0**：`upload_logs` 44,266 → **92,079**、`retail_external` 13 → **47,826**、`upload_tasks` **48,997 一条没多**、基线文件一字未动；**幂等**（副本与生产各重跑一次）→ 0 写入、54,079 全跳过；**对账**：源库直查 `54085 / 47834 / 6251` 与脚本逐字相等。

**两处刻意的小决策**：① 预演**不打印逐条认领告警**（只报计数），否则几万条告警会把"看量级"这件事埋掉，且写 JSONL 就违反"不落任何库"；真跑照打；② 那句"窗口内未上传 N 单"打印的是**三个数**（未上传总数 N、其中已有痕迹的 M、其余未建任务的 K），因为"欠账"是"未上传**且本地无痕**"＝K——本地已有任务行的未上传单在补传队列里看得见，不该算欠账，也不该被重复写。

**code-review 收口（两轴）**：修掉的全是文档/措辞与一处重复字面量——spec 里那句与实现相反的"未上传的成任务"、CLAUDE.md 那句已被流式推翻的"源库读完才开始写库"、"窗口内未上传 N 单"的欠账口径（N/M/K 三个数要分清）、三处过时的"三万七千"与"六万多条"、`RETAIL_WRITE_BATCH` 直接引 `IN_CHUNK_SIZE` 而不是再写一遍 500。两处**判断为不必改**、留档：① `flushRetailBatch()`（约 140 行 I/O 编排）留在脚本里——与票 05 之前的写法同址（老脚本本就把认领/落库写在闭包内），判定/统计/形状全在类里，且用户明说"别新造类"；② `$tally` 的动作键（类管）与单据事实键（脚本管）分开累加——加键要动两处，但两个owner 各管各的口径反而更好读，没到非合不可的程度。
