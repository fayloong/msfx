# 04: 计数门卫

**What to build:** 采集开跑前先数三个数（当日单据总数 / 已上传 / 未上传），与上次基线一致就跳过整轮并在日志里写明原因。交付给运维：日志从此能区分"今天真没新单"与"脚本压根没跑"，源库没事时也不再白跑本地那一套（去重、认领、写库）。

**Blocked by:** 02（改的是同一个采集脚本的流程）

**Status:** done（2026-10-02）

- [x] 一条 SQL 取三个数，形状是「状态表去重成派生表 + `LEFT JOIN` + `count()`」：

  ```sql
  select count(*) as total, count(a.bill_code) as uploaded,
         count(*) - count(a.bill_code) as unuploaded
    from <单据头> ls
    left join (select distinct bill_code from <状态表>) a on a.bill_code = ls.bill_code
   where ... and ls.bill_time = ?
  ```

  （去重派生表不能省；**聚合里套子查询在 SQL Server 上直接报错**——实测踩过）
  - 落点 `App\RetailCollectionGate::counts()`——**一条只读 SQL、源库上就这一次往返**（票面实测 47–59ms），全程不调码上放心
  - ⚠️ **票面这段示例 SQL 漏了一处：左表也得去重**。`zsm_ls` **自己**就有完全重复行（321 平均 **2.08 行/单**、最多 120 行、14 列值全同，见 `.scratch/retail-chain/probe-findings-2026-09-29.md` 第 3 条），`count(*)` 数出来的是**行数**而不是单据数。首跑副本实测 **111 行 vs 采集的 55 张单（≈2.02×）**——而"当日总数"这行字是要给运维看的（本票的交付物就是日志可读性），翻倍的数字只会让人以为门卫坏了。改成 `from (select distinct bill_code from zsm_ls where …) ls` 后 `total` 与采集脚本自己那句「拉取到 N 张单据」**逐字相等**
  - 单据类型清单由调用方传（`RETAIL_BILL_TYPES`，采集脚本里那一份）、2 年下限取自 `RetailRetention`——**门卫数的范围必须与采集的范围逐字一致**：数窄了会跳过"有单要采"的那一轮，多出来的单要等别的单挪动计数才被采到。故 `counts()` 不自己写死类型清单，只接调用方给的那份

- [x] 基线**只在整轮采集成功后**写：落库中途失败、源库读取失败都不更新

**决策记录（票面没写、实现时定的）**：

- **`guard()` 用闭包注入采集整轮**（而不是"先采集、再调 save()"）：这是唯一能让"失败不写基线"被真正断言的形状——脚本层写两句调用，测试就只能靠人去读代码守这条铁律。代价是采集那 110 行被包进一个闭包、多一层缩进，收益是这条铁律从"约定"变成"构造"
- **`?string $date` 兼作绕过开关**：`--all` 时 `$date` 本就是 null（不加等值日期条件），门卫的判据又是"某一天的三个数"——没有那一天就没有门卫。故 `date === null` 直接放行，不多传一个 `bool $bypass`（那是同一件事的第二个说法）
- **计数失败照常采集**（与批发那边**刻意相反**）：批发的 `fetch_bills.php` 计数失败即跳过本次（源库不可用时采集同样无法进行），零售这边不行——门卫跳过的是一整轮采集，而零售没有第二道兜底（漏采就是整天单据在页面上不存在）。方向必须朝"宁可多跑一轮，绝不让采集停摆"
- **计数失败时不写基线**（哪怕采集成功）：手里没有三个数就没有资格写——把旧数写回去会让"计数一直失败"的这几天看起来像"一直没变化"，那正是永久跳过的那条路
- **门卫插在闭环之后**：照票 03 收口时留下的接力注释接的（见 `scripts/fetch_bills_retail.php` 里那段 ⚠️）。门卫的判定只看"源库有没有新东西"，而闭环要收拾的恰恰是"本地有痕迹、源库有新东西"的那批——顺序反了就是永久漏翻
- **左表去重超出票面字面**：票面示例 SQL 只写了状态表去重，实测 111 vs 55 说明它漏了 `zsm_ls` 自身的重复行。按票面的**意图**（"当日单据总数"、范围与采集一致）改，而不是照抄它的字面；理由与实测数字写在 `counts()` 的 docblock 里

**code-review 收口（本票已改）**：

- **`counts()` 的 2 年下限改成由调用方传**（原先方法内自己调一次 `RetailRetention::cutoffDate()`）：脚本开头已算过一份给采集 SQL 用，两处各算各的时，跨零点的那一跑两个范围会差一天——而"范围不一致"正是门卫最危险的失效方式（数窄了＝跳过有单要采的那一轮）。现在类型清单与下限都从同一处传进去，只剩 `bill_time = ?` 那半句仍是两处各写（见欠账）
- **`final class` 去掉**：仓内其余 21 个 `src/` 类无一是 `final`，本类是这个 `final` 的唯一出处——一致性比"防继承"那点收益值钱，尤其这个类没有任何要防的子类化场景
- **`guard()` 返回的 `counts` 键措辞改准**：原 docblock 写"供打印"，但生产调用方并不单独打印它（三个数已经在 `reason` 那句话里）；它真正的用途是让"这一轮到底有没有数到数"能被直接问出来（测试断言的就是它）。行为不变，只改说明

**已知欠账（本票未处理，如实记下）**：

- **`--dry-run` 的绕行尚未接线**：参数本身是票 05 的，本票只留了注释与同一个 `date=null` 分支。票 05 若把它实现成"照样走 guard 但 collect 空转"，就会在 dry-run 之后写下基线——**下一轮会因此少采一轮**，接线时必须真的绕过
- **门卫省不掉源库那一趟扫描**（票面实测：门卫计数 47–59ms、采集查询 80–153ms，冷启动 761ms）：它省的是本地去重、认领与写库。价值在日志可读性，不在性能——这条要写进票 07 的 ADR 代价清单
- **`total` 与"当日单据总数"的定义依赖 `bill_code` 非空**：采集侧 PHP 会跳过 `trim(bill_code)===''` 的行，门卫侧按 `select distinct bill_code` 数（空串/`NULL` 也算一个值）。当日实测两者相等（55 = 55），未在源库上验证是否存在空单号行——真出现时门卫会多算 1，属安全方向（多半跑一轮）
- **门卫的基线读写是仓内第二份**（与批发 `fetch_bills.php` 那段内联的门卫逻辑同形）：批发那份读 `{date,count}`、计数失败即跳过本次，零售这份读 `{date,total,uploaded,unuploaded}`、计数失败照常采集——**策略确实不同**（都写在类注释里），但"读文件 → 校验形状 → 比日期 → 成功后写"这套骨架是抄了一遍。抽一个共享的基线类型（策略由调用方注入）能让两份变一份，代价是要动批发脚本——本票的约束是"批发链路一个字段不动"，故留作欠账
- **计数 SQL 与采集 SQL 的"当日范围"仍是两处各写**（`bill_time >= ? and bill_time = ?` 那半句）：类型清单与 2 年下限已由调用方统一传入（见收口第 1 条），但这半句没有单一来源。改它要把采集 SQL 的范围片段也提出来共用，属结构改动，本票不做
- **`total` 与"当日单据总数"的口径边界**已在上一条记明（空单号各行处理不同，未见实例，方向安全）
