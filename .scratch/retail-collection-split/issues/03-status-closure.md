**决策记录（票面没写、实现时定的）**：
- **闭环放在采集之前**（而不是之后）：它不依赖本批采到什么，采集失败或空批次都不该让它漏跑一轮；而它追加的成功记录会让**同轮**采集的 `decide()` 判 SKIP——两条路径对"已上传"给的是同一个结论，不会一边写记录一边又建任务（这个顺序在票 02 的 `decide(uploaded, hasTask, hasSuccess)` 上验算过四种组合）
- **源库查不通时一条都不翻**，只记 JSONL 警告并返回：凭半份答案翻痕迹会把没上传的单标成已上传，"不知道"不等于"没上传"。`SqlSrvHelper::query()` 对失败返回 `[]`（与"查到零行"同形），故这里必须用 `queryEach()` 的返回值区分
- **任务行的 `resp` 写一段出处 JSON**（与记录同款）：任务页虽然不渲染它，但留着补传失败时的旧响应会让人以为是这次上传的返回
- **同一键的两类痕迹，元数据取先遇到的那行**（`??=`）：任务行优先，它的 `trace_codes` 是采集/手工建单当场落下的那份
- **失败清单不照抄失败页的 `NOT EXISTS` 判重**：那条判重的效果由 `closureActions()` 的 `hasSuccess` 承担（结果等价），而在这里把 SQL 抄一份就是第三处拷贝

**已知欠账（本票未处理，如实记下）**：
- **"成功口径"又多一处**：`closeLoop()` 里那句 `response_status IN ('上传成功','单据重复')`（票 02 已记该欠账——仓内现有 6 处，SQL 的 `IN` 与 PHP 的 `in_array` 形状不同）。code-review 给的具体化建议：把这两个字面量提成常量供 `RecordQuery` 与 `closeLoop()` 同取
- **本地判据的大小写不对称**（低危、当前不可达）：源库那侧刻意 `strtoupper` 拉平，本地那侧（`$success` 的键与那条 IN 查询）是大小写敏感的——本地真出现同一单号的两种写法时会重复追加一条成功记录（失败页那条也翻不掉）。实测生产库 `upload_tasks`/`upload_logs` 非大写单号**各 0 行**；真要修得让 `djbh` 的 SQL 比较也 `COLLATE NOCASE`（索引失效的代价），不在本票
- **`未识别` 的任务行也会被翻正**（按 `source='retail'` 筛，它确实是一张门店单）：翻正是对的，但它**不在**失败记录那条清单里（`Enterprise::isRetail('未识别')` 为 false）——不对称，且后者在实践中不可达（补传三关把它拒在写日志之前），故留着。实测里造了一条 `未识别` 任务行，行为符合上述描述
